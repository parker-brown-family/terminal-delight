# Keep provider authority outside the workload

Planning only; there is no implementation slice or approved online grant. The offline namespace, directory-descriptor validation, environment rebuild and process-bound TD broker remain the starting boundary.

An outside provider broker owns the credential and outbound transport. At launch the trusted supervisor fixes the provider identity, allowed API operations, lifetime, request/response size and spend budget. It gives the workload a per-run capability to that route. The capability cannot name a destination, expose the underlying key or expand its own budget. The broker rechecks the live grant before accepting a request and records acceptance separately from provider completion and consumption by the workload.

The smallest candidate transport is a typed provider adapter over an inherited channel. That preserves the offline profile's ban on arbitrary sockets and avoids treating an HTTP proxy as safe merely because it has an allowlist. A native agent may require a compatible transport adapter; that compatibility is unmeasured and is a blocker to selecting this design, not a reason to silently restore network access. A transparent proxy is an alternative only after its destination resolution, redirect handling, TLS ownership, request bodies and credential injection have an explicit contract and adversarial tests.

The workload cannot inspect the outside broker's filesystem or processes. Credentials stay out of mounted files, environment, arguments, inherited general-purpose descriptors, responses and logs. Broker failures return typed unavailable/denied/unknown results. A reconnect identifies the original run and generation; it never adopts another run's grant. Rate, byte and spend limits are enforced by code, with an explicit unknown-cost policy before a provider request is sent.

The provider can return instructions or malicious content. The workload can act on them only within its file/TD scope. Neither provider content nor a weaker workload's message authorizes a Standard terminal action. A future delegation route must bind origin, intended recipient, purpose, budget and deadline, and the recipient must itself be constrained to that route's effects. There is no automatic route into the existing unrestricted agent-management implementation.

Before program design, select one harness/provider combination and write the transport contract. Qualification then needs positive useful-work controls and negative destination, credential, process, filesystem, quota, revocation, restart and confused-recipient cases. No implementation begins merely because the offline tests pass. The current plan leaves provider compatibility, TLS/streaming behavior, cost accounting, runtime limits and operator grant UI explicitly undecided.
