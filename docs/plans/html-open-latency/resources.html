What Faster Opening Costs

To speed up HTML opening across 30–50 Terminal Delight panes, save the finished page pictures on disk. The disk cache currently holds 58 rendered versions in 229 MiB. Keeping nine browser pages alive used 1.93 GiB of RAM.

01Stored Artifacts

Declaring an artifact stores its link and label; it does not render the page. The original HTML stays where its author saved it. Completed renders live in the shared cache below, with a 256 MiB budget across panes and windows.

/home/parker/.cache/terminal-delight/pages/

The cache holds compressed page pictures and layout data. Eviction removes the least recently used entries after storage, so temporary writes can exceed the budget. Linux may also cache these files in reclaimable RAM.

02Open Browser Pages

Fresh rendering opens a page in TD’s shared Chromium process. I retained nine pages using the real renderer, then closed them. The faster Vulkan mode reduced RAM but used additional graphics memory.

Three ordinary glass briefs, each opened three times, at 968 × 1400 CSS pixels and scale 1.6. One resource run per mode. The source closes the browser after five minutes without an engine call. Temporary profiles normally live under /run/user/1000/terminal-delight/; the experiment’s profile files occupied about 2.6 MiB in the default run.

03Thirty to Fifty Panes

TD keeps its own compressed pictures and decoded pixels while a document remains open, including when its pane is hidden. For the nine sampled views, those add 48 MiB of PNGs and 281 MiB of decoded pixel data. Native display textures cost extra; their actual driver allocation was not measured.

04Recommended Strategy

Use the nine most recently visited panes to rank preparation, beginning with the focused pane’s newest artifact. Run one cancellable job at a time, close its browser page when capture finishes, and retain the completed disk snapshot. Release decoded images from hidden documents while preserving notes and scroll position.

The next check is how quickly a hidden document reopens after its images are released. The revised plan tests that with 9, 30 and 50 panes before rollout. It keeps the 200–300 ms ambition for prepared opens. The earlier speed measurements also show why Vulkan’s first-open delay needs repair.

These are proposed changes. The application still behaves as before; the combined implementation plan awaits approval.

05Opening and Reading

The next gains should make the first screen complete sooner and keep your place while work changes. I would prioritize these four refinements within the existing resource limits.

RefinementWhat you experienceCost and evidence
Capture the visible areaThe whole first screen arrives together. Cached pages read the visible pictures first too.At the tested size, 2,240 rows are visible but two 2,048-row bands are captured. About 45% fewer pixels is available to test; elapsed-time savings are unknown.
Prepare on intentA short pause over an artifact, or selecting it with the keyboard, lets preparation begin before the click.One job; brief dwell; cancellation when attention moves. An experiment whose benefit must exceed wasted captures.
Keep the passage in viewAn agent can add a section above without sending you to another paragraph.Remember a stable section anchor and offset. Small metadata; fall back explicitly when that anchor disappears.
Stay responsive under loadOpening, scrolling and Escape take priority while other panes prepare.Measure the slowest 5% of opens with 50 panes. Proposed prepared-open target: 95% within 500 ms, alongside the 250 ms median goal.

I would build visible-area capture and passage continuity first, then qualify preparation on intent. The responsiveness target belongs in acceptance from the start. All four remain proposals; no further speedup has been measured.
