Chromium's Hidden Work

A brief you have never opened now paints its first screen in 486 ms instead of 673 on a quiet machine, and Chromium uses less memory doing it. That is not the fourfold you asked for: most of what is left is Chromium drawing the glass on the CPU.

01 Two renderers nobody saw

Every fresh open makes a browser context of its own, so one brief can never read another's storage. A trace of one open showed that Chromium 152 does more than load the page into that context. It also starts the address bar's new dropdown, chrome://omnibox-popup.top-chrome, in a renderer of its own and runs about 190 ms of its script, for a window headless Chromium never shows. It keeps a spare renderer that no new context can use, and it runs the GPU process, a component extension and the network service as separate processes. The dropdown is also why last round's spare-page experiment cost 90 MiB: every extra context dragged one in.

02 One trip instead of five

Switching those off took about 70 ms and close to a third of the held memory off each open. The rest came from waiting less. A screenshot clipped to the first screen made Chromium re-emulate the viewport and redraw every glass pane four times; the first screen is now photographed as the page already shows it, and a test compares every pixel against the clipped picture at scales 1, 1.25, 1.6 and 2. The eight set-up calls go out as one batch, and the screenshot starts while the probe is still reading the page. In the window itself, the cache check, the open, the screenshot and its decode used to come back to the UI thread between each step, waiting for the next frame of a window drawing twenty panes. They now run as one background task, and the first screen arrives decoded.

The under-load row was measured with a ready page still in the branch, so it slightly flatters the merged code. Four read-only review rounds from Codex found seven real problems, all fixed in their own commits. The worst was a page left open in Chromium when its view closed mid-open, a leak that predates this work; a guard now owns every opened page until its view adopts it. The engine's 94 real-Chromium tests and the document view's 215 unit tests pass; the full app suite passed 3,255 of 3,256, the miss being the known load-sensitive pane-identity test. 04 What is still slow

Inside the 411 ms, Chromium loads the page and draws it, and on this machine it draws every glass pane's blur on the CPU. That is now the larger share, and it grows with load. Three things could still move it. Keeping one page ready for the next open saved about 60 ms for about 48 MiB; you declined that kind of trade last round, so it is kept on a saved branch rather than shipped. Drawing with the GPU was measured last round at 220 MiB and a slower first open. The glass itself is the third: fewer blurred layers in the house look would cut drawing for every brief, at a cost to how the briefs look. The first open after the browser has idled out for five minutes still pays its start, about 0.4 s.
