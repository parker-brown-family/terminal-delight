Opening Speed

Opening a brief should feel immediate. The renderer reproduced your two-second wait, and an existing graphics option cut it substantially—but made the first open worse.

01The Wait

A recent glass brief took 2.35 seconds to fill the visible area of the page, called its viewport. Reading the file and notes cost less than a millisecond. Capturing the page into pictures consumed most of the delay. TD already keeps its browser running between opens, saves completed page images and draws the visible area first. Vulkan, an alternative graphics mode already supported by TD, made those captures faster.

02The First Open

Starting a fresh Vulkan browser produced a 6.2–8.3 second first viewport. Later opens fell to about 0.6 seconds. That penalty repeated, so simply enabling Vulkan would make some opens much worse.

03Before the Click

A completed render already reads from the cache in 1–6 milliseconds. Decoding and putting it on screen still take time, but this gives prepared opens a credible route toward 10×. TD knows the newest declared artifact before you open it.

The subsequent resource check found nine retained browser pages cost 1.93 GiB of RAM. The revised plan uses recent panes to rank preparation, closes browser pages after capture and releases hidden image buffers. Keep the existing disk budget. A changed file, local asset or frame size must invalidate reuse.

04The Build

I recommend one implementation pass: measure from pressing Alt+O to seeing the page, make capture cheaper without a worse first open, then prepare the newest artifact. Target 4× for ordinary opens and 200–300 ms for prepared opens. The latter is the 10× ambition, still to be proven.

The verification includes actual pixels, note positions, keyboard navigation, edits, resized frames and cancelled opens. The graphics mode’s startup must improve before it becomes the default. A large new document opened immediately remains a separate case.
