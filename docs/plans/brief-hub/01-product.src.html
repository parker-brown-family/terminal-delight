One brief server for the whole box, started by systemd, opened by every link

Every brief you open, from Terminal Delight's desktop link or anywhere else, should land on one local server that saves your notes into the file as you type them. Today each brief gets its own server and Terminal Delight never uses them. This page asks you to approve what that should feel like before anything is designed.

01 Today: one server per brief, and the desktop link skips them all

Saving notes into a brief from a browser works only through brief.py review, which starts a separate service on its own port for each brief and keeps that port forever so the browser's unsaved notes stay reachable. Three are running right now at about 9 MB each, with four ports remembered. Forty briefs would be forty services, forty ports and about 350 MB, none of them stopped when you are done.

Terminal Delight's document pane never uses any of them. When a brief is handed from the pane to the desktop, it passes the file path to xdg-open, so the browser opens file://, which can only keep notes in that browser's storage. That is the path your clip-library notes took.

02 The proposal: one hub, always there, never owned by a window

One brief hub serves every brief on this machine at one fixed address, http://127.0.0.1:8781/. It belongs to systemd, not to Terminal Delight, because several Terminal Delight windows run at once and the house rule is that a shared service never lives in a pane (the APES daemon and lean-ctx moved out of panes for this reason). systemd listens on the port and starts the hub on the first request, so it costs nothing until a brief is opened, and restarts it if it dies.

Terminal Delight, brief.py review and anything else ask the hub for a brief's address, then open that. The browser always sees one origin, so its storage never has to be chased across ports again.

03 What you would notice

  • Terminal Delight's desktop link opens the hub. A brief floating in a pane, handed to the desktop, opens in your browser at its hub address and saves every note into the file. A plain HTML page that is not a brief still opens as a file.
  • Nothing to start. No brief.py review by hand; the first click starts the hub.
  • One address per brief that never changes, so a bookmark or a link pasted in chat keeps working.
  • An index at http://127.0.0.1:8781/ listing the briefs the hub has opened, newest first, with how many notes each holds. Optional; see the questions.
  • Briefs with video and pictures work, since the hub serves the files beside each brief the way review mode now does.

04 What stays safe

A port on 127.0.0.1 is reachable by any web page open in your browser, so the hub keeps today's rules and adds one. Pages are served only at an address carrying an unguessable capability for that brief. Writes are accepted only from the brief's own page, and only into its notes and reading-time sections. A brief is registered with the hub only through a socket on disk that only your user can open, never over HTTP, so no web page can make the hub serve a file of its choosing.

05 What I need from you

Approve the shape: one hub per machine, owned by systemd, started on first use, with Terminal Delight as a client rather than its host?

Recommended. Started by Terminal Delight, it would belong to one of several windows.

Should every route to the desktop go through the hub for a brief: the floating pane's desktop hand-off, the attention rail, and clicked file:// links to a brief in the terminal?

Recommended: all three, for any file that carries a notes section.

Do you want the index page of every brief the hub has opened?

Cheap; a taste call.

Retire the per-brief services once the hub works, after each has saved anything still waiting in its browser?

Recommended. Each stops only once nothing is waiting, so no unsaved note is stranded.
