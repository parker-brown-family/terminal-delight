Terminal Delight can update itself

You asked for an in-app updater with a stable and a dev channel, safe swaps and a way back, then said go all the way. It is built: ⚙ CONFIG › UPDATES and terminal-delight update. It has been tested against a real published AppImage and a live session host. An independent review found thirteen problems, and all of them are fixed. This page is what to read before trusting it.

The panel opens from ⚙ CONFIG and shows what you run, now including the commit, which TD could not tell you before. It shows how TD was installed and what your channel offers. 02 The one rule every swap obeys

An update cannot just replace a file. The file the launcher points at is what every new window starts from, and each workspace's session host runs whatever build started it. Swap in a build that talks to hosts differently, and the next window to open meets a host it cannot read. So every install, every rollback and every staged install goes through one check.

"Vouched for" means the other session's host runs byte for byte the program this window runs, or the one this window's own host runs. Bytes are compared rather than asking that host's program about itself, because an older build may not answer, and starting it to find out could open a window.

Before any install or rollback, TD makes a verified backup of your settings and small records (Threshing Floor, agent records, notes, handovers) in ~/.local/share/terminal-delight-backups/, outside TD's own directories so that uninstalling TD leaves it alone. The five newest are kept, plus any backup that Roll back still points at. The download is trusted only as far as its published checksum, and the panel never says "signed". A release with no checksum is shown with a link and is never installed.

05 What the review caught, and what is still unproven

The reviewer was meant to come from another provider, but Codex is out of quota until 3 November, 23:36, and Gemini's CLI refuses this account. So one round was run by a Claude agent that wrote none of this code, and the Codex round is still owed. It found thirteen problems, and the worst five could put a window in front of a host it cannot talk to. Every one is fixed, and each fix has a test:

  • Rollback and install --now swapped while a host ran. Both now go through the rule in figure 1.
  • Restart everything installed before stopping the host. It now stops the host, waits until it is gone, then swaps. If the swap fails at that point, it reopens the window on the old build with your layout.
  • Hosts that answered badly counted as no host. Any socket that answers at all now counts.
  • A staged build could come back unwanted. It is now dropped on a channel switch, on a rollback, and when the install was changed another way since it was staged.
  • The dev channel could say "up to date" when GitHub could not compare the two commits. It now says unknown and offers the build.
  • Rollback could record the wrong build. The way back now names the build it really keeps, and installing the same build twice no longer overwrites it.
  • The wire fingerprint missed a type the host sends the window. It now covers vt/pump.rs.
  • An inherited APPIMAGE could make a launcher build replace an AppImage. Detection now requires the program to run from inside the image.
  • The remaining findings: a pruned backup, two late rename failures, the dev host-restart notice, and two dev branches overwriting each other's build. All are fixed.

Not proven yet.

  • Restart window, Restart everything and a cold-start install have never run on a real display. This box's only display is your working seat. They belong in the November 9–12 qualification run, together with the ten real updates.
  • The dev-build CI job first runs after the merge. Until then the Dev channel shows the source-build commands.
  • Agents resuming after a full restart relies on the existing session restore. This work did not exercise it.

06 Calls I made that you did not

  1. The fingerprint errs wide. Any change to the terminal core's code counts as a wire change, so core work will usually be staged for a cold start rather than reach you as "Restart window". The rio-vt 0.5.29 move is an example: it was built and measured to stay compatible, and the hash still calls it different. Narrowing the hash by hand would risk a window that silently misreads a host. The better fix is a recorded replay that CI checks (issue 1267). Until that lands, the updater errs safe.
  2. On your machine many updates will be staged, not swapped. Each workspace's host must run a build that can be vouched for, and your hosts often run older builds than your windows. That is the honest answer, but it means more cold starts than the Gate 1 page suggested.
  3. The network goes through curl, not a Rust HTTP library. Nothing new is linked. The requests go only to GitHub's public listings, with no identifier.
  4. One rolling public dev build, published only from the newest dev/* branch, as the dev-build prerelease, never Latest.
  5. Restart everything refuses while another workspace's session runs. Close those first.
