## process-model

terminal-delight is a single Rust binary (crate `terminal-delight`, app/Cargo.toml, built on gpui from a pinned zed-upstream sibling checkout plus alacritty_terminal). Everything the binary can be is decided in `fn main()` at app/src/main.rs:18333 by string-comparing argv[1], in this order: (1) `--td-emit-demo` (main.rs:18337) diverges into `demo::emit_and_block()` (app/src/demo.rs:27) — prints PTY-sized lorem-ipsum and blocks, no window; (2) `ctl` (main.rs:18346) exits via `ctl::run_cli` (app/src/ctl.rs:873) — a pure CLI client that resolves scope (--pid / --all / --workspace / owning-window) to per-pid unix control sockets (`ctl::socket_path`, ctl.rs:321) and does one line-based request/response per target; (3) `mcp` (main.rs:18355) exits via `ctl::run_mcp_cli` (ctl.rs:1095) — a stdio JSON-RPC relay that forwards each stdin line as `mcp rpc <json>` to a RUNNING window's socket (it exists because the in-process stdio transport would need the MCP client to be the GUI's parent, and it never is); (4) `agent-usage` (main.rs:18365) exits via `usage::run_cli` (app/src/usage.rs:428) — runs compiled-in vendor usage collectors, verbs update/list/where; (5) `agent-vitals` (main.rs:18375) exits via `vitals::run_cli` (app/src/vitals.rs:1729) — computes the three bars for a transcript JSONL as JSON, kept diffable against scripts/td-agent-vitals.mjs; (6) `probe` (main.rs:18384) exits via `probe_cli` (main.rs:18260) — read-only forensics on another terminal's shell pid via `session::probe_external`, JSON on stdout. All six are headless: no gpui, no window, plain process exit.

Anything that survives that chain hits the flag gate `flag_reply` (main.rs:18320, called at 18391): ONLY a first argument leading with `-` is judged — `--version`/`-V` and `--help`/`-h` are answered (exit 0), any other `-`-leading flag is refused with usage (exit 2). A bare UNKNOWN positional — `terminal-delight foo`, or a typo'd subcommand like `terminal-delight clt` — returns None from the gate and falls through into the full GUI boot: `alacritty_terminal::tty::setup_env()` (main.rs:18408), scratch-vs-adopt decision (main.rs:18422-18464: TD_SCRATCH / TD_SEED_CWD / TD_SEED_RESUME / TD_DEMO_STATE force a non-owning scratch window; otherwise `instance::resolve_session()` at app/src/instance.rs:299 adopts the most-recently-saved unclaimed session via flock, or mints a fresh id), then `application().run(...)` (main.rs:18466) opens the gpui window. This fall-through is deliberate and test-pinned: `subcommands_and_bare_arguments_still_reach_the_window` (main.rs:17172-17180) asserts `flag_reply(Some("ctl")) == None` and that positionals like `/home/me/src` reach the window, explicitly reserving bare arguments for a future "open in this directory" feature — this is the behaviour behind issue #314: an unknown/mistyped subcommand silently boots a GUI window that then adopts or creates a session on disk. The doc comment on `flag_reply` (main.rs:18306-18319) records the earlier half of the same wound: `--version` once sailed into `open_window`, claimed the next free session key, and left one-pane throwaway sessions behind whenever a build script probed the binary; the gate fixed flags but deliberately not bare words.

Once the GUI path runs, the process claims workspace identity before any window exists: `instance::bind` (instance.rs:86) binds the session key + flock, `instance::adopt_legacy` migrates the pre-multi-session master state, `scratch_decision` (main.rs:18199, pure and tested) decides scratch mode + pane seed, and `window_title` (main.rs:18222) encodes the session key into the WM title. Inside `application().run`: theme::init, palette::init, `cx.on_app_quit -> instance::release()` (frees the flock at quit-start so close-then-reopen re-claims instead of racing PTY teardown), then one `cx.open_window` creating `Workspace::new_demo` / `new_scratch` / `new` (main.rs:18575-18581). Each running GUI window also serves: `ctl::start` (ctl.rs:491) listens on its own pid-keyed unix socket, answering ping/paint/tabs/adopt and `mcp rpc <json>` — the latter routed through `mcp_transport::respond` (app/src/mcp_transport.rs), a four-thread stdio-adjacent server (reader/ticker/notifier/writer) around the read-only MCP policy in app/src/mcp.rs (disabled by default, observe-only, never writes to a PTY). Sockets are not unlinked on exit; clients sweep stale ones on failed connect.

### Client-server implications

The client/server seam already exists and is exercised daily: every GUI window is a server on its own pid-keyed unix socket (ctl.rs), and the `ctl` and `mcp` subcommands are pure clients of it — same binary, but those code paths touch no gpui at runtime and exit as plain subprocesses. The wire contract is deliberately minimal (one text line in, one line out; `mcp rpc <json>` carries a verbatim JSON-RPC payload; MCP_NONE sentinel for notification-no-reply), so a split client would need only a socket path and a line protocol, no linking. The headless verbs (agent-usage, agent-vitals, probe) are already server-free pure computations. What makes a fuller split hard: (1) there is no daemon — discovery is scanning the socket dir and sweeping stale sockets, and multi-window scope resolution leans on Hyprland IPC, so "the server" is N per-window processes, not one; (2) all authoritative state lives on the gpui main thread — mcp_transport's ticker must marshal every snapshot through &App with a 5s budget, so any richer server API inherits that latency/coupling; (3) session identity (flock claim in instance::resolve_session) is taken in main() before the window opens, inside the GUI path — a headless server owning sessions would have to lift that out; (4) the dispatch itself is fragile at the edge issue #314 names: any new subcommand must be string-matched BEFORE the flag gate in main(), because an unrecognised bare word falls through to GUI boot and mutates on-disk session state — a client binary typo'ing a verb against today's binary gets a phantom window, and the test at main.rs:17172 pins that fall-through as intended (reserved for a future "open here" positional), so changing it is a decision, not a bugfix.

## ipc-surface

Terminal Delight's inter-process surface centres on one seam: every GUI process listens on its own unix control socket at $XDG_RUNTIME_DIR/terminal-delight/ctl-<pid>.sock (fallback /tmp/terminal-delight-<uid>/, dir pinned 0700), created by ctl::start() from Workspace::build (app/src/main.rs ~2943, unconditional for every window). The wire protocol is one text line in, one line out: `ping`→`pong`, `paint on|off|toggle|status`, `mcp status|on|off`, `mcp writes on|off`, `mcp expose agents|all`, `adopt {"cwd":...,"run":...}` (open a pane, optionally run a resume line — td-send's target), `tabs [<json ops>]` (ops: name/group/ungroup/color/group_color/collapse, addressed by TabRef::Index or TabRef::Pane(shell pid)), and `mcp rpc <json>` which carries a whole JSON-RPC line to the MCP handler. Replies are `ok`/`ok N`/`on`/`off`/`pong`/`err <why>`, plus the `mcp-none` sentinel for JSON-RPC notifications. Mutations are queued over an mpsc to a 150ms gpui ticker (ctl::Req::{Set,Toggle,Adopt,McpPolicy,Tabs}); status reads come from atomic mirrors so nothing blocks the accept loop except `mcp rpc`, which gets its own thread. The same binary is the client: `terminal-delight ctl ...` resolves scope via --pid, --all (readdir of the socket dir), --workspace (Hyprland IPC socket: j/activeworkspace + j/clients filtered to class "terminal-delight", pid→socket path), or Owning — walking its own /proc parent chain until an ancestor pid owns a socket, which is also how `ctl tab` finds both the window AND the caller's own pane (the last ancestor before the window is the pane's shell). Stale sockets are swept on both sides; there is no unlink-on-exit.

The MCP seam rides the same machinery. app/src/mcp.rs is the pure protocol (JSON-RPC 2.0, MCP rev 2025-06-18, server name "terminal-delight"): methods initialize/ping/tools/list/tools/call/resources/list/prompts/list/logging/setLevel; tools list_panes, pane_events (pid, limit≤200, tails the agent's own ~/.claude/projects/<slug>/<id>.jsonl or ~/.codex rollout via mcp_tail.rs, 256KB tail), get_pane_config / set_pane_config (targets = pane pid or "outer"; GradeReport of 12 uniform 0..100 channels + crawl bool; ConfigPatch is PATCH-semantics with deny_unknown_fields, and also carries `logo` and the leave_note-fed `note`), leave_note (title≤40 chars, text≤10 words, pin/clear → sticky.rs paper, rides the config pipeline), and grep (case-insensitive substring over exposed panes' scrollback, ≤50000 lines/pane, 50 matches/pane). Policy is McpConfig{enabled:false, expose:AgentsOnly|All, events:true, writable:false} persisted in the session toml (ws.mcp + ws.save), settable from the robot panel, the ctl verbs, or env (TD_MCP_WRITE forces writable at boot). mcp_transport.rs supplies two transports over one main-thread "bridge": a stdio NDJSON server (reader/notifier/writer threads + gpui ticker) started only when the process is launched with TD_MCP set — it alone gets the push feed (notifications/message with agent_appeared/agent_vanished/tool_call, ~1Hz snapshots diffed by mcp::Watcher, gated on the initialize handshake and log level) — and the always-started bridge (start_bridge with push=None) that serves the ctl socket's `mcp rpc` verb through mcp_transport::respond(), a one-line-in/one-line-out function with a 5s snapshot budget. Because a desktop-launched GUI can never have the MCP client as its parent, `terminal-delight mcp` (ctl::run_mcp_cli) is the stdio relay an agent registers as its MCP server: it resolves the hosting window via --pid → parent-chain walk → the single discovered socket (refusing to guess among several), then forwards each stdin line as `mcp rpc <line>` with a 10s budget.

The remaining seams: subcommand CLIs dispatched in fn main (app/src/main.rs ~18333) before any gpui — `probe <pid>` (session::probe_external → JSON {shell_pid,fg_pid,kind,comm,cwd,cmdline,resume}, used by scripts/td-send to decide a faithful Omarchy tile migration, which then does `ctl ping --workspace active` and `ctl adopt --cwd --run`, or spawns a seeded window via TD_SCRATCH/TD_SEED_CWD/TD_SEED_RESUME with setsid), `agent-usage` (usage.rs: runs compiled-in collectors, atomically publishes one JSON record per subscription into $XDG_STATE_HOME/terminal-delight/agents/usage/, and reads $XDG_STATE_HOME/omarchy/agents/usage/ too, newest updatedAt wins — the Σ usage face's data), and `agent-vitals` (vitals.rs: whole-transcript parse → window/fatigue/relevance JSON, differential oracle against scripts/td-agent-vitals.mjs). Hyprland is spoken to directly on $XDG_RUNTIME_DIR/hypr/<HYPRLAND_INSTANCE_SIGNATURE>/.socket.sock (j/activeworkspace, j/clients, and focus via the Omarchy-Lua `dispatch hl.dsp.focus({window="pid:N"})` with classic focuswindow fallback). Single-instance is per SESSION, not per app: instance.rs arbitrates ownership of ~/.config/terminal-delight/sessions/<id>.toml with a kernel flock on <id>.lock (non-blocking, fail-closed to a scratch window, released early at quit-start with persistence disarmed first); $TD_SESSION is precedence-#1 naming; the pre-upgrade machine-global lock at $XDG_RUNTIME_DIR/terminal-delight-master.lock is only probed. TD is also an MCP *host* (plugins.rs): it launches plugin MCP servers over stdio NDJSON with a 10s deadline, discovered from ~/.config/terminal-delight/plugins/*/plugin.json. notify.rs shells out to notify-send (action click → Hyprland focus + tab jump); keepalive.rs (TD_KEEPALIVE opt-in) is the one deliberate PTY write, done in-process, not over any socket.

### Client-server implications

Facts that make a client/server split easy: (1) The protocol core is already transport-agnostic — mcp::handle_line_with is a pure function of (line, Snapshot, tail/apply/search closures), and mcp_transport::respond() is a single line-in/line-out entry point that two transports (stdio and the ctl socket) already share; a third transport needs only to call it. (2) Framing is newline-delimited text everywhere (one-line ctl verbs, NDJSON JSON-RPC), trivially carried over any stream. (3) All GUI-state touches funnel through ONE main-thread bridge (BRIDGE mpsc + 40ms ticker, UiReq::Snapshot/Apply/Search) with explicit budgets (5s snapshot, 150ms ctl apply tick, 8s/10s nested write budgets on the mcp-rpc path), so a server split inherits a well-defined latency and back-pressure model. (4) The ctl client already does fan-out and per-target reporting (pid-tab-separated reply lines, exit 0/2), so multi-window addressing is a solved pattern. Facts that make it hard: (1) Addressing and discovery are irreducibly machine-local — sockets are keyed by pid in the filename, targets in the tool API are shell pids, and the Owning/relay resolution walks /proc/<pid>/stat parent chains; none of it survives a network hop, and pane identity's durable form (the resume-command session string) is explicitly NOT the addressing key the write APIs take. (2) Trust is same-user-by-filesystem: parse_adopt says validation is "protocol hygiene, not a security boundary", and `adopt` spawns arbitrary commands (--run), so any transport that leaves the 0700 runtime dir turns a paint toggle surface into unauthenticated RCE. (3) Each window is its own server over only its own panes ("It only ever sees its own instance's panes"); there is no aggregator process — cross-window views exist only as client-side fan-out (ctl --all), and MCP policy is per-window state persisted in that window's session toml. (4) The event feed is derived by tailing agent transcripts on the local home dir (~/.claude/projects/..., ~/.codex/...) from the GUI process, not from an event bus — a remote server needs those files. (5) The push feed is stdio-only by construction (start_bridge(push=None) for the ctl path), so the relay every in-pane agent actually uses gets no notifications/message; any server split that keeps the relay keeps that gap. (6) Usage/vitals are file-contract seams (JSON records in XDG state dirs, newest-updatedAt-wins) already designed for a foreign writer (Omarchy's collectors) — that seam splits for free.

### Open questions

- instance.rs (test comment, line ~1069) asserts 'TD exports TD_SESSION into every pane it opens', but no set_var/env-export site exists in app/src outside tests and term.rs::spawn_in sets no per-pane env — is the export gone (a stale comment) or inherited process-wide from the launcher? Matters for anything that would rely on TD_SESSION inside panes.
- The push notification feed (notifications/message) reaches only a TD_MCP stdio parent; agents connecting through the `terminal-delight mcp` relay (the normal path for a desktop-launched window) get no push feed because start_bridge is called with push=None — confirmed in code, but is that a deliberate contract or a gap the server split should close?
- Nested budgets on the relay path are tight: relay client 10s ≥ ctl mcp-rpc worker write 8s ≥ bridge snapshot/apply 5s, plus the 150ms ctl tick — headroom under a busy UI (e.g. a 50000-line grep across many panes inside one 5s Search budget) is unmeasured.
- usage.rs collectors shell out to python3 (~line 400) — the vendor-collector contract lives in app/src/vendor/README.md and was not read; whether the Codex app-server RPC collector opens its own IPC seam is unverified.
- ctl socket files are never unlinked on exit by design; the client sweeps unconnectable ones, but a recycled pid whose new owner is NOT terminal-delight would leave a stale-looking socket that discover() still lists until a send fails — benign today, but an addressing hazard for any registry built on the socket-dir listing.

## session-core

A live Terminal Delight session is one Linux process running one gpui App, whose single crate lives at app/ (package "terminal-delight", app/Cargo.toml). The alacritty boundary is NOT a fork: alacritty_terminal 0.26.0 comes stock from crates.io (app/Cargo.lock, source = registry). The forked dependency is gpui — a pinned Zed checkout (zed_rev abbe85a3321b… recorded in [package.metadata.terminal-delight] in app/Cargo.toml, checked out as a sibling ../zed-upstream/ by scripts/prepare-gpui.sh) carrying six out-of-repo patches (docs/patches/0001-td-crt-pass, 0002-focus-blur, 0002-sever-gpl-crates, 0003-text-crawl, 0004-warp-tube-cap-32, 0005-glyph-transform). The fork owns rendering effects only (CRT barrel pass, blur, glyph transforms); all terminal emulation is upstream alacritty_terminal. PTY lifecycle is app/src/term.rs: spawn_in() calls tty::new (the user's shell, optionally in a restored cwd), clones the PTY master fd, records shell_pid, builds Term::new(Config::default(), …) — meaning a 10,000-line scrollback cap from alacritty's default — and starts alacritty's EventLoop, which owns the PTY reader thread and VTE parser. The resulting term::Session struct is the whole emulation handle: term: Arc<FairMutex<Term<EventProxy>>>, notifier (bytes in), events: UnboundedReceiver<TermEvent> (events out), master: Option<File> (for tcgetpgrp forensics), shell_pid, and a monotonic generation counter bumped on every event. Dropping the pane drops the Session, and that drop IS the close — the PTY dies with the entity (comment at main.rs:77-82).

The data model is: Workspace (main.rs:1975, a gpui entity, one per window) → tabs: Vec<Tab> (main.rs:627) → each Tab has root: Node where Node = Tree<Entity<TerminalView>> (main.rs:106-117) — a binary split tree (Leaf | Split{id, dir, ratio, a, b}, MAX_PANES=8 per window) whose structural logic is generic over the leaf payload and testable without gpui. TerminalView (app/src/pane.rs:1786-1957) is the pane: it owns session: term::Session plus title/name/logo/mode/appearance/sticky-note/bell state and a large amount of frame-transient render state. TerminalView::new_restored (pane.rs:2455) spawns the shell, types the agent-resume command into the PTY as keystrokes, and starts three detached gpui async tasks: the event pump (drains session.events, bounces TermEvent::PtyWrite back through the notifier at pane.rs:2963), an 800ms /proc foreground-mode watcher, and a 120ms effects/thinking-scan clock. Window-to-session binding is app/src/instance.rs: identity is a session id owning ~/.config/terminal-delight/sessions/<id>.toml, claimed via kernel flock on sessions/<id>.lock (dies with the process, SIGKILL-safe); launch adopts the most-recently-saved unclaimed session ($TD_SESSION overrides; Hyprland workspace is only a ranking hint); losers become non-persisting "scratch" windows.

Persistence — the part that already answers "what would a server own" — is a deliberate two-source design. (1) The StateFile (main.rs:1043) serialises everything TD considers durable: window bounds, theme/warp, tab/group structure, and per-leaf SavedNode {appearance, cwd, resume, name, logo, note}. It is written by Workspace::save (main.rs:3015) through persist_primary_state (main.rs:1250) — atomic tmp+rename (session::write_atomic, 0600/0700), ~10 rotated backups, and a "catastrophic shrink" guard that refuses unintended >50% pane/tab loss. A 30s checkpoint (main.rs:2903-2922) re-snapshots live state; crash loses at most 30s of recency. (2) The live-work content of a pane is NOT internal state at all — it is re-derived from the kernel and the agents' own stores at save time: session::capture (app/src/session.rs:59) does tcgetpgrp on the PTY master → /proc/<fg>/cwd and cmdline, then agent_resume (session.rs:176) synthesises "claude --resume <id>" via a fallback chain (push-ledger at ~/.local/state/terminal-delight/agent-ledger/<pid>.json, open-fd scan of /proc/<pid>/fd, cmdline args, transcript-birth-time match, ~/.claude/history.jsonl, newest-jsonl). Restore types that command into a fresh PTY. Scrollback is the one thing owned purely in process memory: it lives inside alacritty's Grid behind the FairMutex, capped at 10k lines, never persisted; the FOCUS reader's Arc<doc::Document> is a memoised derivation of it keyed on the generation counter. recover.rs turns orphaned on-disk agent transcripts into a resurrect manifest, so even a lost pane's conversation is recoverable — but its shell history, non-agent foreground programs (ProbeKind::Other: vim, htop — explicitly classified non-faithful, session.rs:922-1005), and scrollback are gone.

### Client-server implications

Facts that make a split easier: (1) The emulation core is already server-shaped — term::Session's entire surface is bytes-in (Notifier), TermEvent-out (an unbounded channel), resize(), and two plain kernel handles (master fd, shell_pid); it and the whole durable-state layer (session.rs, instance.rs, recover.rs, the Tree<L> structural ops, the SavedNode/StateFile serde model) are deliberately std+libc-only and unit-tested without gpui. (2) The app already treats the GUI process as mortal: everything it considers durable is a 30s-checkpointed TOML per session (layout tree + per-leaf cwd/resume/appearance/note), written atomically with backups and a shrink guard, and restore is "spawn shell in cwd, type the resume line" — i.e. the durable unit is a *recipe to rebuild*, not live state. (3) Session ownership is a kernel flock that a server process could hold exactly as the GUI does today. (4) An out-of-process control plane already exists (ctl socket per pid; MCP over stdio and over the socket). Facts that make it hard: (1) The PTY master fds, the shell/agent child processes, and alacritty's EventLoop reader threads live in the GUI process — GUI death kills every shell and agent; nothing streams PTY output anywhere else. (2) Scrollback (up to 10k lines/pane) exists only inside Term's Grid behind an in-process FairMutex and is never persisted; a server owning "nothing lost" must own the Term (or the raw byte stream) itself. (3) Grid access is not channelised: pane.rs locks session.term directly and indexes cells in dozens of places (render, hit-tests, the 120ms thinking scan, FOCUS document builds), so the read path is shared-memory, not message-passing. (4) TerminalView conflates the session handle with a gpui entity (FocusHandle, cx.spawn tasks, EventEmitters, Instant-based clocks, RefCell memos), and Workspace mixes the durable model (tabs/groups) into ~100 fields of frame-transient gpui state; theme truth lives in gpui Globals. (5) Capture/mode-detection/keepalive all read /proc of processes local to the PTY, and MCP snapshots require a gpui main-thread round-trip today. What a server would have needed to own for a GUI death to lose nothing, per this code: the PTY masters + child processes (and the EventLoop pump), the Term grids or their byte streams (scrollback + alt screen), the flock claims, and the capture/persist loop — everything else (layout, appearance, resume identity) is already on disk within 30s, and agent conversations are independently recoverable from the agents' own transcript stores (recover.rs).

### Open questions

- Is scrollback persistence actually a goal? The current design deliberately loses it (10k-line in-memory cap, never written) and leans on agents' own transcripts for continuity — a server split that owns PTYs preserves it for free, but nothing in the code expresses a requirement for it.
- Non-resumable foreground programs (session.rs ProbeKind::Other — vim, htop, anything not shell/agent/tmux-attach) are explicitly classified unfaithful to migrate; a server owning the PTY would keep them alive, changing that contract — is that the intent of the split?
- The per-session flock (instance.rs) assumes one local process owns a session; who holds the claim in a client/server world, and does adoption-by-recency (with Hyprland workspace as a ranking hint) still make sense when sessions outlive windows?
- Grid reads are shared-memory throughout pane.rs (term.lock() in render/hit-test/scan paths, ~120ms cadence); would a split put the Term server-side behind the generation-counter/diff protocol, or keep a client-side Term replica fed by the raw byte stream?
- MAX_PANES=8 and one-Workspace-per-window are GUI-process constants (main.rs:75); it is unstated whether a server session would keep the same shape or decouple pane count from window capacity.
- The vendored omarchy-agent-usage collectors (app/src/vendor/) and the keepalive/vitals sweeps read local /proc and local transcript files — with a remote client these must run wherever the PTYs run, which the current module layout supports (std-only) but nothing currently routes.

## persistence

Terminal Delight (live tree /home/parker/Work/terminal-delight, Rust app under app/src/) persists everything durable as small TOML/JSON files under ~/.config/terminal-delight and ~/.local/state, and treats the running process tree as expendable. The unit of persistence is a per-window "session": app/src/instance.rs resolves a session id (`$TD_SESSION` → adopt the most-recently-saved unheld session, workspace as a ranking hint only → fresh ordinal), claims it with a kernel flock on `sessions/<id>.lock` (fail-closed to a non-persisting scratch window if arbitration fails, `claim_in` instance.rs:471), and reads/writes `~/.config/terminal-delight/sessions/<id>.toml`. That file (struct `StateFile`, app/src/main.rs:1043) holds: active tab, window bounds `win`, UI scale, outer theme choice + warp + tracking, pane count, tab list (name, fill/text colours, group id) with the full split tree, per-leaf `PaneTheme` appearance override, cwd, a synthesized agent resume command, pane name, logo path, and the sticky note (title/text/seed/pinned — `SavedNote` main.rs:409, `sticky::Saved` app/src/sticky.rs:108), plus tab groups, MCP policy (`mcp::McpConfig` incl. the writes toggle), focus_inherit, anchor_top, lang, and last_workspace. Saves go through one chokepoint `persist_primary_state` (main.rs:1250): atomic tmp+fsync+rename 0600 (`session::write_atomic` app/src/session.rs:74), a catastrophic-shrink guard that refuses saves losing >half the panes/tabs of a non-trivial session and stashes `<key>.toml.last-good` (main.rs:1189-1266), and 10 rotated timestamped backups under `sessions/backups/<key>/` (main.rs:1207). Saves fire at ~44 user-action call sites, immediately on the ✕ close button (main.rs:11321-11330), and from a 30s background checkpoint (main.rs:2898-2922) — so a crash loses at most 30s of metadata recency, never the layout. `on_app_quit` releases the flock at quit-start (main.rs:18476, instance.rs:98) so an immediate reopen re-adopts; SIGKILL can never wedge a session because the flock dies with the fd.

- `docs/plans/client-server/00-status.md` — The split's gate-status doc; names this sweep as Gate-2 recon input

### Client-server implications

Easy: all durable state already funnels through two tiny seams — one path accessor (instance::config_dir) and one write chokepoint (persist_primary_state → session::write_atomic) — and the on-disk unit (a per-session TOML small enough to parse on every save for the shrink guard) is trivially relocatable behind a server; the control plane already speaks newline JSON-RPC on two transports (TD_MCP stdio + the ctl unix socket) with a main-thread bridge (mcp_transport::start_bridge), and scratch/demo windows already model a zero-persistence client. Hard, and the actual reason a server would exist: the irreplaceable state is the live process tree, which today is not persisted at all — PTY masters, shells, agents, and scrollback die with the GUI process, and "restore" is respawn-plus-typing (pane.rs:2455), with conversation continuity outsourced to claude/codex's own transcript stores via a five-level forensic scrape (session.rs:176-232) that exists ONLY because process death severs the pane↔session binding; a server that keeps PTYs alive obsoletes that whole chain plus the 30s checkpoint's reason for being. Host-locality assumptions are pervasive: session ownership is a kernel flock on a local file (instance.rs — same-filesystem semantics), capture reads /proc/<pid>/cwd and tcgetpgrp on local fds every save, sockets live in $XDG_RUNTIME_DIR tmpfs keyed by pid, and workspace hints come from the local Hyprland socket — so the persistence/ownership layer must live wherever the PTYs live. Two windows fighting over one session is already solved fail-closed (claim_in refuses unarbitrated ownership; release() disarms persistence before freeing the lock so a corpse can't clobber its successor) — this is precisely the arbitration a server would centralize.

## prior-art

The client-server split is already a live, formally-staged effort: docs/plans/client-server/00-status.md (untracked, created 2026-09-08 in the live tree) defines the feature as "a long-lived server owning live sessions (PTYs, panes, state) and attachable clients (GUI, CLI, MCP)", run through the 4-gate software-factory workflow — Gate 1 (Product) in progress awaiting Parker's answers (asked 2026-09-08), Gates 2-4 pending, and this sweep is the recon it names for Gate 2. The idea has been deliberated twice before and declined twice, each time with reasons recorded. The 2026-06-20 competitive review (docs/2026-06-20-competitive-feature-mining-and-launch-plan-review.md, "Multiplexer / SSH domains / persistent sessions" row) ruled it "Skip — ~30k LOC; conflicts with local-first single-binary; the useful 20% is the CLI write API". The 2026-08-29 foundation interrogation (docs/2026-08-29-foundation-interrogation-zed-gpui-quickshell.md §5) re-examined it as option 2 of 3 ("TD server split — the wezterm-mux / iTerm2 / VS Code ptyHost pattern"), chose "Reincarnation++" instead (hook-captured session ids per Quil, scrollback ghosting, CLI-flag re-assertion — since ticketed as issue #180), ruled out a tmux/zellij mux substrate as architecture, and left the daemon "staged behind a trigger: build the daemon when mid-turn losses or logout frequency measurably hurt", with an explicit composition promise: the daemon "slots under this model — live PTYs answer crash/logout, reincarnation stays the reboot answer — the two layers compose, so nothing built now is throwaway". It also verified the substrate is free on this box (Arch ships KillUserProcesses=no, Linger=yes is set, so a systemd --user daemon survives logout) and catalogued the field: wezterm-mux, VS Code ptyHost + the 2026-08-26 Agent Host, zmx (server-side libghostty-vt snapshots), shpool, zellij resurrection.

On GitHub, the 2026-09-08 phantom-window incident is issues #312-#314: #312 (rebuild from the live line) documents that the stale-fork build lacked every headless subcommand — ctl, mcp, agent-usage, agent-vitals, probe — so each CLI-style invocation booted the full GUI and flashed scratch windows on every wool-wall tick and MCP connect; #313 (collapse the two checkouts) records that the agent toolchain resolves to the stale fork and leaves the canonical-checkout choice explicitly to the operator; #314 requires an unknown subcommand to error instead of launching the GUI (with the design note that a bare launch and flag args must still launch the GUI). A second cluster is external clients already straining against the single-process model: #302 (ctl can create but not select a pane; "eight agents, one window pid"; its invalidation criteria raise pane-identity stability and whether outside-addressability is wanted at all), #308 (tab writes are ctl-socket-only, invisible to MCP, and silently skip unresolvable targets while the MCP Apply round-trip in app/src/mcp_transport.rs already does truthful per-target outcomes; flags the ctl-ungated vs TD_MCP_WRITE-gated asymmetry as a decision to take deliberately), #300 (extract agent-vitals into a bin that builds without gpui — the engine is already display-independent), #215 (the `terminal-delight mcp` stdio relay resolves its window by /proc parent-walk, which dies inside tmux; suggested fix is a TD_WINDOW_PID env stamp), and the not-yet-approved intake pair #285 (push agent state via Claude Code hooks instead of /proc+transcript inference) and #284 (answer a permission hold off-pane via the PermissionRequest HTTP hook; notes multi-surface authentication is unsolved). A third cluster is session identity/ownership as the recurring hard problem: #311 (a bare-launched pane reports its neighbour's session id and pane_events tails the wrong transcript — unknown filled with a confident wrong value), #299/#272/#151 (same-cwd session cross-wiring and wrong-agent rebinds), the closed lock-model bugs #188 (claim fails open, two windows co-own a session), #189 (quit-start release window), #194/#191 (per-workspace session keys), and #196 (no UI to reach any saved session but the newest).

Net: nothing has ever ruled the split out permanently — both prior "no" verdicts were "not yet, and here is the trigger", and the wished-for composition (daemon under reincarnation) is on record. What changed since 2026-08-29 is that the trigger class arguably fired: a logout incident already forced a hand-rebuilt tmux rescue (recorded in the foundation doc), and five open issues are external surfaces (Wool wall, conclave's field, bar widgets, off-pane permission answering) each wanting a stable, display-independent server surface that today only exists as per-window sockets inside the GUI binary.

### Client-server implications

Facts on record that bear on the split. (1) Both prior refusals were conditional and the composition is pre-designed: the foundation doc's verdict says the daemon, if built, slots UNDER reincarnation — live PTYs answer crash/logout, reincarnation answers reboot — so #180's Reincarnation++ work is declared non-throwaway. (2) The substrate is verified free on this box: KillUserProcesses=no and Linger=yes, so a systemd --user server survives logout and starts at boot; zmx proves server-side VT snapshots with the same class of core. (3) IPC seams already exist but are per-window and fragile: each GUI process owns ctl-<pid>.sock with the binary doubling as client; the MCP stdio relay finds its window by /proc parent-walk, which fails under tmux (#215) and forces --pid with multiple windows — evidence that 'which server do I mean' is already an unsolved addressing problem. (4) Session identity is the hard kernel: pane→session binding is inference (fd scans, birth-time) and has produced cross-wiring bugs four times (#311, #299, #272, #151), and single-ownership locking failed open twice (#188, #189) — a server owning sessions centralizes exactly what is repeatedly mis-derived today, and #311's 'done when' (unknown session stays unknown, may be filled push-style by a hook) plus intake #285 (hook-fed state) sketch the ground-truth channel a server would want. (5) All headless verbs live inside the GUI binary; an unknown verb launches the GUI (#314), a stale binary regressed every headless caller at once (#312), and #300 already asks for the first gpui-free extraction — the phantom-window incident is a measured cost of client and server sharing one binary and one dispatch ladder. (6) Write-path policy is split: MCP writes gate on TD_MCP_WRITE with per-target outcome reporting; ctl writes are ungated and ack the queue write, not the outcome (#308) — a unified server protocol has to pick one policy deliberately. (7) Demand-side pull is documented: Wool wants vitals without the terminal installed (#300), conclave's field wants a focus verb (#302), off-pane permission answering wants an ingest endpoint with multi-surface auth (#284), and the June review's 'moat' framing (local-first agent wall) is an argument FOR a local server, not against one — the thing it declined was tmux-style multiplexing surface area, not a process split per se.
