# GUI in the TUI

Prior-art survey for Terminal Delight · 2026-09-24 · run with research-delight

Two posts started this. In one, a retro CRT shows a Windows 95 settings dialog sitting inside a terminal layout, and a reply jokes that inside the GUI you can open another TUI. In the other, Boyd's Jev-plays-Pokémon dashboard draws a live Game Boy screen as crisp pixels beside its text panels. The feature Terminal Delight wants sits between the two. Ctrl+click a Markdown file, an HTML brief or an image in terminal output and it opens inside TD, in a split or as a floating square, and later programs running in TD get to draw real pixels themselves. The question for this survey was who has already built pieces of that, how they did it, and which one idea from each TD should take.

The survey ran as a research-delight plan: a declared rubric (what each project is, licence, language, how the pixels get there, where they draw, input model, activity, overlap with TD, one idea to take, one trap, sources), gap-targeted rounds, and a gate that rejects any value without a source or an explicit flag. Thirty-two projects were seeded; the first round's gatherers bubbled up twenty more. 51 of 52 subjects met the Definition of Done; mean completeness 99%. The one subject that never closed is the "HYPERION TUI" artwork itself, which three rounds could not tie to any software.

Every claim below carries one of three labels. *Measured* means read on a primary source this session: the project's repo, its docs, a source file, or `gh api` output. *Inferred* means taken from a secondary write-up or a search summary, or reasoned from a primary source. *Hunch* means a guess, stated as one. Nothing was built or run; every claim about behaviour comes from code or docs.

## What should shape TD's design

1. **Someone already ships the gesture Parker described.** In cmux, a Ghostty-based macOS terminal for coding agents, Cmd+clicking a Markdown path opens a live-reloading Markdown viewer in a split beside the terminal, and Cmd+clicking an HTML file opens it in a browser pane. Agents open the same viewer with `cmux markdown open plan.md`, and commands that arrive over its socket are not allowed to steal focus. What cmux lacks is the floating square. [measured: the Markdown and HTML routes are merged pull requests in manaflow-ai/cmux]

2. **cmux's bug list is TD's test plan for the click.** Cmd+clicking `src/main.py:1292`, the format every agent and compiler prints, opens Safari; `file://` URLs get mangled; paths with trailing punctuation were read as URLs; soft-wrapped URLs failed; clicks were swallowed inside fullscreen TUIs that capture the mouse; the Markdown viewer went blank after a resize or a drag to another column. Zed shows the fix for the hardest of these: it resolves a relative path against the working directory that was current when that line was printed, and only opens once a hover has resolved the target. [measured: cmux issues and changelog; Zed's `cwd_history` in crates/terminal]

3. **The first half of the feature needs no graphics protocol at all.** A viewer that TD draws itself, as a gpui pane or a floating element, is ordinary UI. It does not depend on alacritty_terminal learning anything. Zed, on TD's exact stack (gpui + alacritty_terminal), opens a clicked image as a gpui ImageView tab and a clicked Markdown file as an editor tab with a preview beside it on request, and has never drawn a pixel inside its terminal grid. For Markdown, TD already owns a renderer: markdown-delight turns comrak's syntax tree into gpui elements on the same gpui checkout, though it still shows images as their link text and raw HTML as literal lines. [measured]

4. **The second half, programs drawing pixels, cannot ride on stock alacritty_terminal.** Its parser (vte 0.15) drops the `ESC _` bytes that carry Kitty graphics, and its DCS hooks, which Sixel needs, only log. Alacritty's maintainer has declined image support twice this year, on 2026-07-07 and again on the day of this run, when he pointed at euporie's screenshots and wrote that making GUIs in a terminal is "actively working to make terminals and terminal applications worse". Zed closed its own terminal-images request as not planned and pointed at Alacritty. TD has to own this layer. [measured]

5. **Two Rust code paths already exist under licences TD can use, plus a decoder crate.** ayosec's long-running Alacritty fork puts Sixel inside the alacritty_terminal crate (about 1.6k added lines plus a patched `vte-graphics`), so TD would write only the gpui paint, but it is Sixel-only and a version behind TD (0.25.2-dev against 0.26). rio-vt, Rio's extracted VT core (MIT, alacritty_terminal lineage), already parses Kitty graphics with Unicode placeholders, Sixel and iTerm2, and hands decoded images out as events; Rio's maintainer proposed it as a drop-in for Zed's gpui terminal, and although Zed closed that pull request unmerged, its diff maps the API differences. icy_sixel is a streaming Sixel decoder crate. The two cheapest routes to try are vendoring the fork's crate half (Sixel now, with a Kitty decoder added later, as a community cosmic-term fork did in about 1.5k lines) or lifting rio-vt's Kitty and Sixel modules into a pre-parser in front of alacritty_terminal. A pre-parser has to track the cursor and emit cursor moves itself; the vendored crate does not. [measured facts; the trade-off is inferred]

6. **Implement Kitty graphics first, with Unicode placeholders, and leave Sixel for later.** Ghostty made exactly that choice and refuses Sixel. Placeholders put the image inside grid cells: the program prints U+10EEEE characters whose colour and combining marks name the image, row and column, so scrolling, splits, reflow and clipping come from the grid for free. ratatui-image's only Kitty path and yazi's preferred driver both use it, Zellij and tmux both shipped bugs where images escaped their pane, and herdr spent several releases on image occlusion. Omarchy's default terminal, Foot, is Sixel-only, so Sixel is what a stock Omarchy desktop can show today; that is the case for doing it second rather than never. [measured for Ghostty, the clients and the multiplexer bugs; the ordering is inferred]

7. **Clients find a terminal by asking it, or by recognising its name, and TD must be honest on both paths.** notcurses, ratatui-image, viuer, yazi, presenterm and euporie send the Kitty query (`a=q`) followed by a device-attributes request and trust whichever reply comes first. chafa, timg, mcat, the original rtv and Boyd's Jev client look at `TERM`, `TERM_PROGRAM` or the XTVERSION string and fall back to half-blocks for anything they do not know. The gatherers merged every probe into one conformance checklist (it is in the run's bubbles): DA1, XTVERSION, `CSI 14 t` / `16 t` / `18 t`, XTSMGRAPHICS, the Kitty query for each transmission medium, colour queries, synchronized output and SGR-pixel mouse. Answer each truthfully, report a stable `TerminalDelight <version>` name, send one-line upstream patches to the name-matchers, and never borrow Ghostty's or kitty's identity. [measured]

8. **Pixel size per pane is the first question every image client asks, and TD half-answers it today.** TD passes real cell sizes to each pane's pty on every resize, so tools that read `ws_xpixel`/`ws_ypixel` (mpv, ueberzug++, mcat, tdf, w3m) will size correctly. But reading `app/src/host.rs` in this worktree, the `CSI 14 t` reply is built from the geometry captured when the pane was spawned, so after a resize it should report the old size, and `CSI 16 t` (cell size in pixels) goes unanswered because vte 0.15 only dispatches 14, 18, 22 and 23. gpui's fractional cell widths are also truncated to integers on the way into the pty. [inferred from reading the code; not run]

9. **The projects that make a terminal a window manager converged on one verb and four placements.** kitty's open-actions table, herdr's `[[link_handlers]]`, Wave's `wsh view` and `wsh web open -r`, and cat9's `open(target, placement)` all route by MIME type or regex to a viewer, and they all ended up with split, tab, float, and "in place", where the viewer temporarily replaces the current pane and restores it on close (Zellij's in-place panes, herdr's overlay, cat9's swallow). For TD that is `td open <path> [--float|--split|--in-place]`, with Ctrl+click, the CLI and an agent's request all going through the same router. [measured for each project; the synthesis is inferred]

10. **Make the floating square a real pane that converts both ways, and keep the keyboard in TD's hands.** tmux 3.8's release candidate lets a tiled pane float and a floating pane tile, with explicit modal flags; Extraterm pops inline output out into a tab; Zellij keeps floats on one layer that a single key shows or hides, with pinned floats that stay up. EAF shows why TD's keymap must see every key first, so close, dock and move keep working over a browser or PDF. twin and foot's URL mode show the keyboard-only version: every window movable and listable, and a label on every visible path. [measured]

11. **Trust follows who asked.** In Terminology, a user's click may fall back to launching an external program, but a popup that program output requested can only render inside the terminal and never reaches `xdg-open`. cmux applies the same idea to focus: an open request from an agent never moves focus. TD's router should carry one flag, user or program, that decides whether anything outside TD may run. kitty's spec adds the file-transfer rules: refuse device, socket and `/proc` paths, delete temp files only from known temp directories, and return identical errors so a remote client cannot probe the filesystem. [measured]

12. **HTML on Linux in gpui has no drop-in webview.** gpui-component's wry-based webview says it supports only macOS and Windows and draws on top of the gpui window, covering anything behind it. EAF and ueberzug++ lay a separate OS window over a pane, which on Hyprland means guessing positions from scale and IPC. Carbonyl shows what owning a browser engine costs: a Chromium fork that takes over an hour to build and has not shipped since February 2023. The options left are a Rust HTML renderer drawing into a gpui image (Blitz, or Servo, which Parker's servo-reader already drives headless), or a static snapshot first (mcat renders Markdown and HTML to a PNG through headless Chromium) with a live view later. [measured facts; the ranking is inferred]

## Closest prior art to what Parker described

**cmux** is the closest match to the click. It ships the exact gesture (a click on a Markdown path in terminal output opens a live viewer in a split, a click on HTML opens a browser pane) in a terminal built for running many agents, and it lets agents open the same viewer from a CLI. It is macOS-only Swift on libghostty under GPL-3.0, so TD takes its behaviour and its bug list, not its code. [measured]

**Zed's terminal** is the closest match to the architecture. It is gpui and alacritty_terminal, TD's own stack, and it already turns a Ctrl+click in terminal output into a gpui pane item, an image viewer or a Markdown preview, with per-line working-directory resolution that TD can copy almost line for line. It is also the cautionary half: it closed in-terminal images as not planned and has none. [measured]

**Terminology** is the closest match to the floating square. Clicking a media link in Enlightenment's terminal pops the image or video up as a layer inside the terminal window, Escape closes it, and its `tycat` helper reserves a block of cells for inline media. Its trust rule (user clicks may leave the terminal, program requests may not) is the one to copy. Its private escape protocol, which passes file paths instead of pixels, is the part to avoid. [measured]

Three more sit close behind. Wave Terminal tiles preview, web and terminal blocks side by side and has `wsh view -m` for a magnified view, but never detects paths in terminal output. herdr, Omarchy's default agent workspace, has Ctrl+click link handlers, popup and overlay placements, and Kitty images re-emitted to the host. kitty defines the graphics protocol, and its open-actions table is the router grammar to copy. The derived "closeness" column in the table counts shared traits and ranks herdr, Warp and dmux-rs highest; the ranking above weighs the click-to-viewer path more heavily than trait count does. [inferred]

For the second half of the feature, programs drawing pixels, the nearest code rather than the nearest product is rio-vt and ayosec's alacritty fork, both on TD's side of the licence line. [measured]

## The two posts Parker shared

**Boyd's Jev-plays-Pokémon dashboard** is `npx jev-plays-pokemon`, an MIT Node client from Andrew Boyd of Standard Agents, the company behind dmux. The server renders the whole dashboard as a terminal byte stream; the client writes it straight through, adds a chat panel, and draws the Game Boy screen with the Kitty graphics protocol. Each 160×144 frame is upscaled four times with nearest-neighbour sampling on the client, because, in the source's own words, "Terminals scale Kitty images with smoothing, which blurs pixel art", then zlib-compressed and placed over a cell box at up to 15 frames a second. Where Kitty isn't available, the stream's own half-block cells show instead. So the crisp pixels in the screenshot are Kitty graphics, not Sixel or half-blocks. Run inside TD, the client would still draw half-blocks until someone passes `--kitty`, because it turns Kitty on only for Ghostty, WezTerm or kitty, and never inside tmux. TD could also spare every pixel-art client the 16-fold byte cost by scaling small images with nearest-neighbour itself. The web page says Jev entered the Hall of Fame on 2026-09-23; the npm package was first published 2026-09-16. [measured from the package source and the site; that the screenshot came from a Kitty-capable terminal is inferred]

**The "HYPERION TUI v2.7.19" artwork** could not be tied to any software. The post by Fred Nix (an Omarchy plugin author) crediting Boyd's idea could not be read: x.com answered 402, the xcancel mirror 451, and the Servo reader's engine is not built on this box. GitHub repository and code searches, the web, both men's public GitHub activity and nixfred.com turned up nothing with a Windows 95 dialog or that version string. The best reading is that it is concept art for an idea. One coincidence is recorded and not asserted: kygura/hyperion, a Go terminal console for a Jev trading runtime, opened a pull request the same day. [hunch]

## Verified claims from the outside summary

### (a) Omarchy's default terminal

The summary is half right. Foot is the default: the live manual says "Foot is the default terminal for Omarchy", and at the v4.0.4 tag `default/xdg-terminal-exec/hyprland-xdg-terminals.list` names `foot.desktop`. The supported alternatives are three, not two: "We fully support Alacritty, Ghostty, and Kitty as options as well", and `bin/omarchy-install-terminal` accepts `alacritty|foot|ghostty|kitty`. The older Omarchy 3 manual still says Alacritty is the default. [measured: https://omarchy.org/manual/terminal/ and github.com/basecamp/omarchy at v4.0.4]

### (b) rtv at Laotian-telephonebell2559/rtv

The repository is not legitimate. It was judged from metadata only; nothing was cloned, downloaded, built or run. It is a copy of Santitub/rtv: eight of its eleven commits were authored by Santitub on 2026-08-20, three days before the copy was created on 2026-08-23 by an account opened 2026-08-12, with two public repositories, no followers and issues disabled. The uploader's own commits add a 487,623-byte zip inside `src/` and rewrite every outbound README link (the build badge, the FFmpeg builds, the clone URL, yt-dlp, even the example video URLs) to the uploader's GitHub Pages site, whose page has two download buttons for a zip of the same size. Its topics are unrelated bait (voice-cloning, reddit, visual-studio). The description in the summary (Rust, FFmpeg playback, Kitty and Sixel, audio sync, MIT/Apache-2.0) is true of the original, Santitub/rtv: three stars, one day of commits, a release on 2026-08-20. Do not link or cite the copy. [measured via `gh api`]

### (c) Carbonyl

The summary is accurate, with three caveats. Carbonyl is real Chromium, a modified headless shell with a Rust core, and its README claims "pretty much all Web APIs including WebGL, WebGPU, audio and video playback". The picture is half-block characters, two square pixels per cell, rendered at a 1/7 device scale factor; Sixel and Kitty renderers exist only as unmerged pull requests. Audio comes out of the sound system of the machine running Carbonyl, not through the terminal (over SSH you forward PulseAudio yourself). And it has been dormant since v0.0.3 in February 2023, with an open "Is project alive?" issue and a community-fork proposal. [measured]

#### Wave Terminal — terminal, web and preview blocks

- **What** (measured) — Wave Terminal is an open-source, AI-integrated desktop terminal (Electron front end, Go backend) whose tabs are tiled 'blocks'. ### B · Terminals that draw pixels for programs

#### Kitty — graphics protocol, kittens, icat, overlays

- **What** (measured) — GPU terminal emulator whose author wrote the Kitty graphics protocol (APC G), the de facto modern way for programs to put raster images and animations into a terminal. It also ships kittens (icat displays images; hints labels paths and URLs) and open-actions, which decide what happens when you click a file or hyperlink.
- **How** (measured) — Kitty graphics protocol, which kitty defines and hosts: APC `ESC _G<k=v,...>;<base64>ESC \`. Image data arrives by one of four transmission mediums: direct in the escape (t=d), a file path (t=f), a temp file (t=t) or POSIX shared memory (t=s). Images are uploaded once by id and then placed as placements with z-index; negative z draws under text, and below INT32_MIN/2 also under non-default cell backgrounds. Also supported: relative placements (P=/Q= parent), client- and terminal-driven animation (a=f frames, since 0.20.0), and Unicode placeholders, where the codepoint U+10EEEE carries the image id in its foreground colour and diacritics carry the row and column, so images survive tmux and vim. kitty has no Sixel support. Rendering is native OpenGL textures.
- **Take for TD** (inferred) — Copy kitty's open-actions table as TD's Ctrl+click router. It is an ordered, first-match-wins list of rules. Each rule has criteria (protocol, mime, ext, file glob, url regex) and an action with ${FILE_PATH}, ${URL} and ${FILE} substituted. Ship defaults along these lines: image/* opens a floating square in the current pane; text/markdown and text/html open a split-pane viewer; anything else goes to xdg-open. TD's actions are its own pane types rather than kitty's `launch --type=overlay`, but the rule grammar, the ordering and the substitution variables transfer unchanged, and a user who knows kitty can already write TD rules.
- **Avoid** (measured) — The file and shared-memory transmission mediums (t=f, t=t, t=s) come with mandatory security rules. The terminal must refuse device, socket and other special files, and may refuse /proc, /sys and /dev. It may delete a temp file only when it sits in a known temp dir and its path contains `tty-graphics-protocol`. And every file-access failure must return an identical error, so a remote or sandboxed client cannot learn which files exist. Start TD with t=d (direct) only. Add t=f, t=t and t=s later, and only with these rules implemented and tested.

#### WezTerm

- **What** (measured) — Cross-platform GPU terminal emulator and multiplexer in Rust, configured in Lua. It lets programs draw images through the iTerm2 inline-image protocol (with a built-in `wezterm imgcat`), Sixel and a partial Kitty graphics implementation.

#### Ghostty

- **What** (measured) — Fast, native-UI GPU terminal emulator in Zig. For programs it implements the Kitty graphics protocol, including Unicode placeholders and, since August 2026 on main, animation. It deliberately refuses Sixel. Its VT core is also shipped as an embeddable library, libghostty, which exposes Kitty graphics to other apps.
- **How** (measured) — Kitty graphics protocol only, APC G. It covers storage, placements, Unicode placeholders (graphics_unicode.zig) and animation (graphics_animation.zig). Frames are composed eagerly into full RGBA buffers, unlike kitty's lazy delta chain, trading memory for simplicity. Image bytes are capped per screen by `image-storage-limit`, default 320 MB and separate for the primary and alternate screens; setting it to 0 disables all image protocols. No Sixel: Mitchell Hashimoto said on 2024-11-22 that 'Ghostty will not support sixels', and Sixel was removed from the TODO list in PR #2772.

Put a per-screen image byte budget in TD's config, primary and alternate counted separately, and make 0 the single kill switch for every image protocol. With about 20 agent panes open, a per-pane budget with a global ceiling is what stops one `icat` loop from eating the box.
- **Avoid** (measured) — Cache image textures across frames. Ghostling, the libghostty demo, gained a Kitty renderer in PR #13 (273 lines), and Mitchell's PR text says: 'This has very bad performance... our render loop recreates and destroys the 2D image texture on every frame.' In gpui, an image asset rebuilt per frame repeats that mistake. Key textures by image id and a content hash, and re-upload only when the protocol mutates the image.

#### Rio

- **What** (measured) — Hardware-accelerated terminal in Rust, aimed at desktops and browsers. It implements Sixel, iTerm2 inline images and the Kitty graphics protocol. Its VT core is published as the `rio-vt` crate. The crate descends from alacritty_terminal: its Crosswords module was 'originally taken from' alacritty_terminal's term/mod.rs, and its Sixel parser was 'retired from' ayosec's alacritty PR #4763.

#### Contour

- **What** (measured) — Modern C++/Qt terminal with the widest image-protocol coverage in this cluster. It has Sixel, ReGIS vector graphics, Kitty graphics (added in 0.7.0), iTerm2 inline images, and its own experimental Good Image Protocol (GIP). #### iTerm2 — OSC 1337 inline images

- **What** (measured) — macOS terminal that originated the OSC 1337 inline-images protocol and `imgcat`. As of 3.7 it also implements the Kitty graphics protocol, placeholders included, and decodes Sixel through a bundled libsixel. Semantic History makes Cmd-click on a filename in output open it.
- **How** (measured) — OSC 1337: `ESC ] 1337 ; File=[args] : <base64> ^G`. Arguments are name (base64), size, width and height (N cells, Npx, N% or auto), preserveAspectRatio and inline (1 displays the file, 0 downloads it). Since 3.5 there is a multipart form, MultipartFile, then FilePart chunks, then FileEnd, which avoids tmux size limits. Animated GIFs have been supported since 2.9.20150512. Kitty APC G is also supported, handled by KittyImageController.swift. Sixel DCS goes through libsixel, decoded in the sandboxed process `iTerm2SandboxedWorker`.
- **Take for TD** (inferred) — Resolve a clicked relative path against the working directory at the moment that line was printed, not the pane's current cwd. iTerm2's Semantic History records a cwd per line (\5) through shell integration. TD's agent panes print paths like `docs/brief.html` from wherever the agent was, often a different directory from the shell's cwd now. Stamp each grid line with the last OSC 7 cwd seen (or the agent's reported cwd), and look up that stamp on Ctrl+click.
- **Avoid** (measured) — Do not decode images in-process with a C library. CVE-2026-44637 is a heap out-of-bounds write in libsixel's SIXEL decoder, and iTerm2 reached it 'directly' from bytes written to the terminal, so any `cat` of a crafted file could trigger it. iTerm2 had at least confined decoding to a sandboxed worker (PR #679, merged 2026-06-26). TD should decode in memory-safe Rust, where the ayosec and Rio Sixel parsers already exist, and cap dimensions before allocating.

#### Alacritty (upstream) — the engine TD runs on, and why it refuses images

- **What** (measured) — Minimal OpenGL terminal whose `alacritty_terminal` crate is TD's VT engine. Upstream deliberately has no image protocol. Issue #910 (open since 2017, 225 comments) and ayosec's PR #4763 (open since 2021, 255 comments) are kept open but will not be merged. #### tmux — display-popup, image passthrough

- **What** (measured) — The reference terminal multiplexer (server/client; sessions, windows, panes). For graphical content it has display-popup (modal floating overlay running a command, since 3.2), floating panes (3.7: non-modal panes above the tiled layout with full escape-sequence support; 3.8-rc adds modal panes, keyboard move/resize and float↔tile conversion), allow-passthrough so programs can tunnel raw escapes (Kitty/iTerm2 images) to the outer terminal, and built-in SIXEL when compiled with --enable-sixel (3.4). Kitty graphics are not in any release; PR #5445 is open.
- **How** (measured) — Draws no pixels itself. SIXEL (3.4+, --enable-sixel): tmux parses SIXEL from a pane, stores the image server-side (image.c, image-sixel.c) and re-sends it to each attached client that supports SIXEL, scaled and placed for that client; images are removed before reflow, saved/restored across the alternate screen (3.6), capped at 20 (3.6). Anything else only via allow-passthrough (`ESC P tmux; … ESC \` wrapping), which bypasses tmux's grid. Kitty graphics: unreleased — #4902 proof-of-concept branch ta/kitty-img, #5274 (Unicode-placeholder version, closed 2026-08-05), and open PR #5445 (mgrant0) which cuts Kitty and SIXEL images into cell-sized rectangles so they work around floating panes and scroll into copy mode.
- **Take for TD** (inferred) — Make TD's floating square a real pane that converts both ways: tmux 3.8 lets break-pane float a tiled pane and join-pane tile a floating one, keeps floats as full panes (same escape handling), and adds explicit modal flags (-O modal, -K all keys to it, -C close on click outside, -A stay above zoom). TD should give its floating square the same verbs, 'pop out to float' and 'dock into a split', plus a modal flag and click-outside-to-close, so an image or Markdown square opened small can be promoted into the layout without reopening it.
- **Avoid** (inferred) — Don't let program images be a free overlay keyed to screen coordinates. tmux's passthrough and early Kitty overlay route could not clip images to their pane or scroll them, which is why maintainers are rebuilding Kitty support as grid-resident cell rectangles (#5274, #5445), and #5445 found that whether a terminal moves image pixels with a scrolled region ('imagescroll') is a separate, per-terminal capability (mintty drops them; WezTerm and Ghostty move them). TD should anchor every Kitty/Sixel placement to cells in the alacritty_terminal grid and scrollback and redraw from that model, never trust the renderer to carry pixels along.
- **Sources** — https://github.com/tmux/tmux https://github.com/tmux/tmux/blob/master/CHANGES https://github.com/tmux/tmux/blob/master/tmux.1 https://github.com/tmux/tmux/pull/5445 https://github.com/tmux/tmux/issues/4902 https://github.com/tmux/tmux/pull/5274 https://github.com/tmux/tmux/releases

#### Zellij — floating panes, plugins

- **What** (measured) — Rust terminal workspace / multiplexer with tiled, stacked and floating panes (the floating layer toggles as a whole; single floating panes can be pinned always-on-top since 0.42), a WebAssembly plugin system whose plugins render ANSI text UIs, a browser web client (0.43+, PWA in 0.45), and image support: its own Sixel implementation since 0.31 and a Kitty graphics protocol implementation since 0.45.
- **How** (measured) — Zellij emulates a terminal per pane and re-encodes images for the host; it draws no pixels itself. Sixel is implemented in the pane grid since 0.31.0 and advertised only if the attached terminal also supports it (0.45, #5432). Kitty graphics: 'a full protocol implementation… minus the heavier animations and unicode placeholders', so images 'just work' with no passthrough; opt out with `support_kitty_image_protocol false` (PR #5428, merged 2026-07-31). Plugins cannot show pixels: render() output is treated as UTF-8 ANSI, with built-in Table/Ribbon/Nested List/Text components.
- **Take for TD** (inferred) — Treat TD's floating squares as one per-tab floating layer with a pin flag: one key shows or hides every square at once, and a pinned square (toggled by clicking its frame, a key, the CLI or the API) stays on top even when the layer is hidden, as Zellij's pinned floating panes do for logs, compiler output or htop. It gives the Markdown/image square a clear lifetime, glanceable while working or cleared with one key, without closing it.
- **Avoid** (measured) — Image placements that aren't bound to pane visibility leak across panes. In 0.45.0 a yazi image preview stayed on screen after its stacked pane was hidden and showed through whatever pane was switched to (#5512); earlier, yazi images rendered in the wrong place unless the pane was fullscreen (#4101), partly because apps like Yazi hard-code Zellij env-var checks (PR #5428). Every TD image or viewer must follow its pane's visibility and geometry (hide, stack, zoom, tab switch) and be deleted with it.

#### Arcan + cat9 + durden

- **What** (measured) — Arcan is a display server and 'desktop engine': a Lua-scripted multimedia engine plus the SHMIF IPC and TUI API, which aims to replace terminal escape protocols altogether. Durden is its tiling/stacking desktop. Cat9 is a Lua user shell for Lash (Arcan's TUI command line) in which every command becomes a tracked job whose output can be folded, reused, popped out as a window or, through `open`, embedded as media (image, PDF, video) decoded by a separate afsrv_decode process into a clipped region of the shell's own window.
- **How** (measured) — Native display-server compositing, no escape-sequence graphics. cat9 `open` runs `file -b --mime-type`, maps image/* to proto=image, video/audio to proto=media, application/pdf to proto=pdf and text to proto=text, then hands the job to an afsrv_decode frameserver (a one-shot separate process) in a new window requested from the window manager; pixels travel over SHMIF shared memory. The 2017 design post lists 'Crazy encoding schemes for representing non-character data – such as Sixel' among the problems TUI replaces.
- **Take for TD** (inferred) — One `open(target, placement)` verb with a MIME router and a small placement vocabulary. cat9 sniffs the type, picks a decoder, then asks for split / split-direction / tab / swallow / embed; swallow replaces the current window until closed and embed anchors the result to a row of the job that produced it, folding and hiding with it, while the user can still drag it out. TD's Ctrl+click, a `td open` CLI and any OSC request should all call one such function: `.md` → Markdown viewer, `.html` → web view, `image/*` → image view, with placement ∈ {split, vsplit, tab, float, swallow, embed-at-row}.
- **Avoid** (inferred) — Don't make the feature depend on programs adopting a new protocol. Arcan's embedding works because clients speak SHMIF/TUI instead of ECMA-48, and the price shows: cat9 says installing is 'not for the faint of heart', legacy tty programs need a `!`/`p!` escape into a terminal emulator, and the project has stayed niche (cat9 526 stars; GitHub mirror 'going defunct'). TD should get Ctrl+click opening entirely from its own side (path/URL detection, OSC 8) and accept the protocols programs already emit (Kitty, Sixel) for pixels.
- **Sources** — https://github.com/letoram/cat9 https://github.com/letoram/cat9/blob/sub/README.md https://github.com/letoram/cat9/blob/sub/cat9/default/open.lua https://github.com/letoram/arcan https://github.com/letoram/arcan/blob/master/README.md https://github.com/letoram/arcan/blob/master/COPYING https://github.com/letoram/durden https://arcan-fe.com/2022/04/02/the-day-of-a-new-command-line-interface-shell/ https://arcan-fe.com/2022/10/15/whipping-up-a-new-shell-lashcat9/ https://arcan-fe.com/2017/07/12/the-dawn-of-a-new-command-line-interface/

#### herdr — agent workspace runtime (Omarchy's default)

- **What** (measured) — Rust 'terminal workspace manager' and background server that keeps agent and shell panes running across detach (workspaces → tabs → panes), marks every agent pane working / blocked / idle / done, exposes a CLI and socket API that agents themselves drive, and supports manifest plugins with panes and Ctrl-click link handlers. It runs inside any host terminal and since 0.9.0 shows pane images by re-emitting Kitty graphics to compatible hosts. Omarchy v4.0.4 installs it (omarchy-base.packages line 52) and binds it to Super+Ctrl+Return.
- **How** (measured) — Kitty graphics protocol, re-emitted. libghostty-vt parses each pane's stream, Kitty images included (herdr caps image storage at 64 MiB and supplies a PNG-decode callback); the client composes placements per surface with visibility states Main / Popup / Hidden and an occlusion map, then writes Kitty APCs to the host. Direct file transfer (t=t) is used only after a silent 1x1 query proves the local Ghostty consumes it (src/client/image_files.rs). On by default since 0.9.0 (`terminal.kitty_graphics = false` to disable); Unicode placeholders render (#136).
- **Take for TD** (inferred) — Adopt herdr's click-routing contract as TD's config shape: a `[[link_handlers]]` table of {id, regex over the clicked URL, action}, checked in order, fired on Ctrl-click, which also receives OSC 8 `file://` clicks (0.9.0) and hands the action the clicked URL plus source-pane context. Pair it with herdr's placement enum (overlay | popup | split | tab | zoomed), where overlay is a temporary zoomed view that restores the previous focus and zoom on close. herdr ships on Parker's own Omarchy desktop, so matching its vocabulary lets the same handlers and habits carry over.
- **Avoid** (inferred) — Don't build TD's image path as a re-emitter, and don't inherit herdr's workarounds. Because herdr sits inside another terminal it must re-encode Kitty graphics per client, probe transfer modes, and patch occlusion case by case: oversized images blocked smaller ones, replacements redrew one row at a time (#3033, #3166, #3549), replaced host images leaked (#947, #948), and popups at first hid all images rather than only overlapped ones (fixed 0.9.1). It also has to use Ctrl-click because a captured mouse report cannot carry Cmd/Super. TD draws with gpui and sees real modifiers, so images and floating squares should be scene-graph layers with native occlusion.

#### dmux-rs — native Rust tmux control-mode renderer for dmux

- **What** (measured) — Standard Agents' Rust rewrite of dmux's front end. Instead of an Ink sidebar driving tmux by shelling out, it attaches as a tmux control-mode client, keeps its own VT grid per pane (alacritty_terminal 0.25), composites the panes plus a native overlay UI (sidebar, menus, settings, diff pager, toasts) and paints the host terminal itself. It ships as a 'first-party test ring' that self-updates every minute and auto-files rendering-divergence issues.
- **How** (measured) — Host-terminal cells, plus Kitty graphics for its own chrome only: crates/dmux-host/src/kitty.rs is a 'Stateful Kitty graphics encoder for small direct-RGBA overlays' (upload once per asset key, move placements by reusing image/placement ids so Kitty replaces them without flicker; an 'experiment/kitty-accent-cursor-motion' branch merged 2026-08-25). Program images inside panes are not passed through: ROADMAP lists 'Images (kitty graphics translation) ⏳'.
- **Take for TD** (inferred) — Copy the shadow verifier. dmux-rs runs a second, independent VT parser over the same byte stream (tmux's grid), compares every settled pane cell-for-cell against its alacritty_terminal grid, and on a mismatch writes an incident with both grids plus a seed-anchored raw byte recording; `--replay-incident` reproduces it offline and fixed incidents go into a corpus replayed in CI forever. TD should do the same before adding Kitty/Sixel and viewer placements on top of alacritty_terminal: record pane bytes, replay them into a reference parser, and lock every divergence into a test corpus.
- **Avoid** (inferred) — Picking alacritty_terminal leaves graphics to you: dmux-rs, on the same engine, still lists pane images as '⏳ later', and upstream Alacritty's maintainer said on 2026-07-07 that Alacritty should not implement Sixel because 'Many of the usecases you've listed are things I never want to see in my terminal'. Don't plan TD's Kitty/Sixel support as waiting for alacritty_terminal; budget a TD-owned graphics parser and image store beside the grid from the start.

### D · Programs that put pixels in a terminal

#### ueberzug++

- **What** (measured) — Überzug++: a C++ daemon, drop-in replacement for the defunct ueberzug. Host programs (lf, yazi, vifm, ranger, fzf scripts, image.nvim) send it JSON add/remove commands over stdin or a unix socket, and it paints a raster image (including GIF and animated WebP) into a column/row box. It renders no documents, only images.
- **How** (measured) — Six backends, selected by -o or config.json: x11 and wayland (a separate borderless, unfocusable compositor window per image, placed over the terminal), and kitty, sixel, iterm2, chafa (escape sequences written to the terminal). Escape-code probing is OFF by default (--use-escape-codes [0]). By default it reads TIOCGWINSZ for pixel size, marks iterm2 from TERM_PROGRAM (WezTerm, iTerm.app), and marks x11/wayland available from the session. Detection is last-wins in the order sixel < kitty < iterm2 < x11 < wayland, with chafa if nothing is found. So on Hyprland it picks the overlay window even inside a kitty-capable terminal. With probing on, it sends `ESC_Gi=31,s=1,v=1,a=q,t=d,f=24;AAAA ESC\ CSI c` (kitty), `CSI ?1;1;0S` (XTSMGRAPHICS sixel), and `CSI 14t` then `CSI ?2;1;0S` for pixel size.
- **Take for TD** (inferred) — Report exact per-pane pixel sizes in TIOCGWINSZ: ws_xpixel/ws_ypixel should equal cols×cell width and rows×cell height of the pane, not of the window. Also answer CSI 14t for the pane. Ueberzugpp derives font size and padding from these numbers, and its guess_padding() computes zero padding only when the pixels divide exactly by cols. mcat, tdf and w3m read the same fields.
- **Avoid** (inferred) — Nothing should fall back to overlay windows inside TD. The Wayland backend positions against the whole Hyprland client window plus guessed padding, and it knows nothing about TD's own splits. Whenever monitor scale is above 1 it halves coordinates and adds 10 px (`res_x/2 + 10`), which is only right at 2×. Issues for wrong position and scale on Hyprland/Sway (#122) and wrong workspace (#223) are still open. And because it prefers wayland over kitty, a user with ueberzugpp installed gets overlay windows unless the host program detects TD's graphics first.

#### awrit — Chromium in Kitty

- **What** (measured) — awrit (Actual Web Rendering In Terminal): a full Chromium browser, run as Electron offscreen rendering, whose painted frames stream into a terminal that speaks the Kitty graphics protocol. It has a web-tech toolbar and Chrome extensions, and mouse and keyboard drive the page. The repo is archived; the author cites limited time and rising security issues, and points macOS users to cmux.
- **How** (measured) — Kitty graphics protocol only. Electron `offscreen: true` emits `paint` events carrying a BGRA bitmap. awrit converts it to RGBA, writes it to POSIX shared memory and transmits `f=32,t=s,a=T,C=1,q=2`. The fast path uses kitty animation: frame 1 is a paused container image, each webview paint loads as an animation frame (`a=f,r=N,X=1`), and that frame is composited into the visible one at the layout rect (`a=c,C=1,x,y,w,h`). At startup it probes three capabilities, 100 ms timeout each: load a 1×1 image (`f=24,t=d,i=4294111295`), load a frame (`a=f,r=2`), and composite (`a=c,C=1,r=2,c=1`). If frames or compose fail, a fallback re-sends the whole bitmap at a cell-plus-pixel offset (`X=,Y=`) on every paint. The code notes that Ghostty 'and probably most other terminals only support a very small subset'.
- **Take for TD** (inferred) — Implement kitty-graphics shared-memory transmission (t=s) plus animation-frame load and compose (a=f with r=; a=c with x,y,w,h,C=1), and answer awrit's three-step probe OK. Then every Chromium repaint becomes a dirty-rect composite into one resident image instead of a full-frame re-upload. Put awrit's three probe strings in TD's conformance test verbatim.
- **Avoid** (inferred) — Don't copy awrit's architecture for TD's own HTML pane. It ships a whole Electron/Chromium, the author archived it over security issues, and every frame crosses shared memory as a full BGRA bitmap. TD already owns the GPU and can embed a web view directly. awrit matters only as a client TD should be able to host. Also, a terminal that answers a=q OK but lacks a=f/a=c pushes awrit onto the slow full-frame fallback, so answer each frame probe truthfully.

#### Carbonyl — Chromium in a terminal

- **What** (measured) — A Chromium-based browser that runs inside a terminal: a modified Chromium headless shell (the runtime) loads a Rust core (libcarbonyl) that turns Blink/Skia output into terminal cells. README: 'It supports pretty much all Web APIs including WebGL, WebGPU, audio and video playback, animations'.
- **How** (measured) — Unicode lower half block U+2584 with 24-bit colour: background = top pixel, foreground = bottom pixel, so each cell is two square pixels. Text is NOT rasterised: a custom Skia device (TextCaptureDevice) intercepts glyph runs and sends them over Mojo (CarbonylRenderService.DrawText) to be printed as real characters. - **Take for TD** (inferred) — Render at the destination resolution, and keep text as text. Carbonyl beats browsh ~50x on CPU because it lays the page out at the terminal's resolution instead of downscaling a full framebuffer, and it prints glyphs as characters instead of pixels. For TD's HTML-brief pane: size the webview/rasteriser to the pane's pixel box and re-lay-out on resize, never render big and scale.
- **Avoid** (inferred) — Owning a browser engine is a maintenance cliff: a Chromium fork that takes over an hour to build froze at v0.0.3 in Feb 2023 with an ageing Chromium inside. TD should borrow the platform's webview (or hand off to the browser) for HTML, not vendor an engine.

#### browsh

- **What** (measured) — Browsh: a text-based browser backed by real headless Firefox. A web extension serialises each page's text and pixel colours, and a Go 'interfacer' renders them in a TTY or serves them over HTTP to other browsers. It targets low-bandwidth SSH/Mosh browsing while keeping modern JavaScript support.
- **How** (measured) — Unicode half-blocks, no graphics protocol. The web extension takes two screenshots of the visible DOM, one with text hidden and one with text drawn in a full-block glyph font, and samples background and text colours from them. On the Go side, a cell holding text shows the real DOM character in its colour. Any other cell becomes '▄', with the background colour as the top 'pixel' and the foreground as the bottom one: 2 vertical pixels per cell, in 24-bit colour via tcell.
- **Take for TD** (inferred) — Keep a text layer under every rendered document. Browsh keeps page text as real characters in the grid and page graphics as pixels, by screenshotting with the text hidden. When TD renders a Markdown or HTML brief as pixels in a pane or float, it should also keep that brief's plain text addressable, so that TD's grep and pane_events tooling and its agents can read and search it. Pixels alone are invisible to them.
- **Avoid** (inferred) — Half-block rendering caps a page at 2 vertical pixels per cell and loses glyph-level detail, and browsh hasn't shipped a release since January 2024. For a GPU terminal it is only a fallback for panes where TD's protocols go undetected (for example over nested SSH), not a model for TD's own HTML view.

#### presenterm

- **What** (measured) — presenterm: a Rust tool that turns Markdown into terminal slideshows, with themes, layouts, speaker notes, executable code blocks and images. #### w3m — text browser with inline images (kitty/sixel/iTerm2)

- **What** (measured) — w3m: the classic C pager and text web browser. The maintained fork is Debian's tats/w3m. It renders HTML, tables included, as text and can show inline images through several terminal image methods.
- **How** (measured) — The `inline_img_protocol` option picks the method. 0 (the default) is an external command, w3mimgdisplay, which draws straight onto the terminal's X11 window found through WINDOWID, or onto the Linux framebuffer. 1 is OSC 5379 for mlterm (`-ri`). 2 is Sixel through img2sixel (`-sixel`). 3 is iTerm2 OSC 1337. 4 is Kitty: each image is converted to PNG with ImageMagick `convert` and sent as `ESC_G f=100,a=T` with a source crop x,y,w,h and a cell box c,r, in m=1/m=0 chunks. It is the smallest slice that a real client uses, and the same verbs cover presenterm's and mcat's simple paths. Animation, t=s and placeholders come after.
- **Avoid** (inferred) — w3m's default image path (w3mimgdisplay over X11 WINDOWID) paints outside the terminal's control and does nothing useful on Hyprland, and its kitty mode shells out to ImageMagick for every image. #### glow — text-only Markdown renderer (contrast case)

- **What** (measured) — Glow: Charm's Markdown renderer, both a CLI and a TUI pager and file browser. It renders Markdown to ANSI-styled text using glamour stylesheets. It is included as the contrast case: it draws text only, never pixels.

TD's open-on-click should resolve the OSC 8 URI against the pane's cwd and open it in a split or float.

#### icy_sixel — pure-Rust Sixel encoder and streaming decoder

- **What** (measured) — A pure-Rust Sixel library with an encoder (Wu quantisation and Floyd-Steinberg dithering) and a clean-room, SIMD-accelerated decoder to RGBA. Version 0.7.0 adds a streaming decoder a terminal host can feed from its escape parser: begin_frame() after the parser has consumed the DCS header and 'q', or begin_dcs() from 'ESC P', then feed()/finish(). ratatui-image and viuer use it as their encoder.
- **How** (measured) — Host-side Sixel decode: SixelDecoder yields RGBA plus a palette that persists across images (finish() commits palette changes). Honours P1 (pixel aspect) and P2 (background/transparency). Streaming feed() reports bytes consumed and statuses NeedMoreData, Terminated(byte), Complete (ST consumed) or Cancelled (CAN/SUB). Measured by the author: 1-KiB-chunk streaming within about 5% of batch decode (6.49 ms for a photo on a Ryzen 9950X3D).
- **Take for TD** (inferred) — Wire icy_sixel's begin_frame() into TD's DCS path: when the escape parser reports hook(params, ..., action 'q'), open a frame with DcsSettings(P1, P2, ...); forward put() bytes in batches (1 KiB or larger, since byte-at-a-time is 1.7-2.2x slower); call finish() on ST and upload the RGBA as a gpui texture anchored at the cursor cell.
- **Avoid** (measured) — It is not a memory budget. Limits are generous (six-pixel bands up to 1,000,000 pixels, input height up to 999,996) and the README warns streaming 'is not constant-memory image storage'. Any decode error kills the session and the outer parser must discard the rest of that DCS. TD needs its own per-pane byte and pixel caps in front of it.

#### rio-vt — Rio's embeddable VT core with Sixel, iTerm2 and Kitty graphics parsing

- **What** (measured) — rio-vt is Rio terminal's VT core, published as its own crate in 2026 with no renderer or GPU dependencies: escape parser, grid ('crosswords', Alacritty-derived) with scrollback, PTY event model. It is a sibling of alacritty_terminal with its own grid, event and PTY model, and a swap would touch every pane, selection and search path TD already has. #### Boyd's Jev-plays-Pokemon dashboard (@0xBOYD)

- **What** (measured) — `npx jev-plays-pokemon` — a Node.js terminal client for 'Jev plays Pokémon Red'. The server renders the whole dashboard as a terminal byte stream (tag 0x01) plus raw game frames (tag 0x03); the client writes the stream verbatim, adds a Jev-moderated chat panel, and overlays the Game Boy screen as a Kitty graphics image. Web twin at jev-plays-pokemon.standardagents.ai, which says 'Jev beat the Elite Four and the Champion and entered the Hall of Fame on September 23, 2026' and credits 'an experiment by 0xBoyd'.
- **How** (measured) — Kitty graphics protocol. Each 160×144 RGB frame is upscaled 4× nearest-neighbour on the client ('Terminals scale Kitty images with smoothing, which blurs pixel art. A picture sent at a whole multiple of the Game Boy size keeps sharp pixel edges'), zlib-deflated and sent as ESC_G a=T,f=24,o=z,s=640,v=576,i=77,p=1,c=<cols>,r=<rows>,C=1,q=2 in 4096-byte chunks, at most 15 fps. Fallback: the stream's own half-block cells. So the 'crisp pixels' in Boyd's screenshot are Kitty graphics, not Sixel or half-blocks.
- **Take for TD** (inferred) — Scale images nearest-neighbour when enlarging by a whole factor (or when the source is small), so pixel art stays crisp without every client pre-upscaling 4× and paying 16× the bytes. Boyd had to work around smoothing on the client; TD can fix it in the host.
- **Avoid** (measured) — Detection by environment: kittySupported() returns false under TMUX and true only for TERM_PROGRAM=ghostty|WezTerm or KITTY_WINDOW_ID. In TD this client draws half-blocks unless run with --kitty. Don't impersonate another terminal's TERM_PROGRAM; set an honest one, answer the Kitty a=q query, and send upstream patches for query-based detection.
