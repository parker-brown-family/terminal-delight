# libghostty-vt 0.2.1 probe: notes, in the order I hit them

1. crates.io has libghostty-vt 0.2.1 (sys crate also 0.2.1); the sys README says it builds with Zig by default, and its build.rs `git clone`s ghostty at a pinned commit (a887df42, 2026-07-11) into OUT_DIR at build time, so the first build needs network and Zig on PATH.
2. build.rs only passes `--global-cache-dir` to Zig when `GHOSTTY_ZIG_SYSTEM_DIR` is set, so by default Zig's package downloads land in `~/.cache/zig`; I set `ZIG_GLOBAL_CACHE_DIR` (and `CARGO_HOME`, `CARGO_TARGET_DIR`) to keep everything in the workspace. The README doesn't mention this. The Zig cache came to 424 MB and target/ to 473 MB.
3. Environment, not the library: the agent harness's shell allowlist rejected my first two attempts to start the background build (a `$(...)` and a bare script name); `bash build.sh` got through.
4. First successful build: 223 s (3m43s), cold, `--release`, with a stub main. Nearly all of it was the ghostty clone and the Zig build. Later rebuilds of the probe took about 5 s.
5. `TerminalOptions` has no cell pixel size. The only way to set it is `resize(cols, rows, cell_w, cell_h)` after `new()`, and I learned that from the kitty-graphics module example, not from the `Options` docs.
6. The `png` feature's `RustPngDecoder` can't be used from outside the crate: it has a private field and no `new()` or `Default`. Its doc example calls `ghostty::kitty::graphics` and `RustPngDecoder::new()`, neither of which exists, and passes a bare decoder where `set_png_decoder` expects `Option<Box<dyn DecodePng>>`. Reading the code, it also reserves capacity without setting a length, so `next_frame` would get an empty buffer. I wrote my own 25-line decoder on the `png` crate and dropped the feature.
7. The kitty-graphics docs say graphics must be enabled by setting a non-zero storage limit. The default is already 10,000,000 bytes, so that step isn't needed.
8. Kitty loading media default to direct-only: file, temp-file and shared-memory are all off. The recording sends the picture as a file path (`t=f`), so with defaults you get zero placements and no error, because `vt_write` never fails. You also get zero placements if no PNG decoder is installed. The Rust docs don't mention the media default; I found it in ghostty's `Terminal.zig`. The probe turns all three media on, as a desktop terminal would.
9. About the input, not the library: icat.bin's `t=f` payload points at `/tmp/claude-1000/.../scratchpad/test.png` (640x400, 16-bit RGBA). The placement exists only because that file is still on this machine. The temp-file and shm files named in the two capability queries are gone, so those queries come back `EINVAL: invalid data`.
10. DA1 (`ESC [ c`): the library replies `ESC [ ? 62 ; 22 c` with no handler installed, and still replies when `on_device_attributes` returns `None`. The doc says returning `None` means "silently ignore". I confirmed this with a small experiment (probe/examples/defaults.rs).
11. The probe itself compiled on the first try. The placement iterator, `grid_size`, `viewport_pos`, `rect` + `point_from_grid_ref`, `on_pty_write`, and per-row `Selection` + `format_selection_alloc` all behaved as documented.
12. The picture's image id is 2147483647. icat sent no `i=`, so the library picked the id itself (i32::MAX). Correct, but it looks odd in the output.
13. `max_scrollback` is documented as lines in both the Rust docs and the C header ("Maximum number of lines to keep in scrollback history"), but it is a byte budget: ghostty's `Screen.zig` says so, and it is rounded to whole pages. With 10,000 the terminal held 620 rows (580 history) after text.bin. It held the same 620 with 1, 100,000 and 1,000,000. 10,000,000 held 9,134 rows; unlimited held 18,809 (all of text.bin after wrapping). There is no way to ask for exactly 10,000 lines (probe/examples/scrollback.rs).
14. The icat recording leaves no text on screen, so the visible-lines list is empty. That is the correct answer for this input.
