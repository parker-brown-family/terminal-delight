# rio-vt 0.5.28 probe: notes, in the order I hit them

1. icat.bin carries the PNG by absolute file path (`t=f`, `/tmp/claude-1000/.../scratchpad/test.png`), outside the workspace, so the result depends on that file still existing. It does (640x400 RGBA PNG).
2. The three `a=q` probes in icat.bin point at things that are gone on replay (a direct 1x1 RGB payload, a `/dev/shm` temp file, a POSIX shm object), so one `OK` and two `ENOENT` replies are the expected answers here, not a bug.
3. Documentation mismatch: the README feature table says the default is "(none), lean core" and lists only rio-window/renderer/x11/wayland. `Cargo.toml` actually has `default = ["pty"]`, and the README never mentions `pty` or `graphics` at all. I found them through `cargo info rio-vt`.
4. A dependency pin looked like a trap: rio-vt enables `parking_lot` with the `nightly` feature. It built fine on stable 1.98, so this turned out to be a non-issue.
5. Environment, not rio-vt: my first timed build was rejected by the local shell allowlist (a `( time ... )` subshell). I re-ran it with `date` stamps instead.
6. First successful build (`cargo build --release`, cold, every dependency including `image`, `skrifa` and `read-fonts` from the `graphics` feature): 1 min 43 s. An incremental rebuild of the probe alone takes 3.7 s.
7. Documentation mismatch: the README's "Receiving events" snippet implements `fn event(&self) -> (Option<RioEvent>, bool)` and calls it "the only required method". `EventListener` has no `event` method, and every method has a default, so that snippet would not compile. The `kitty_image` example gets it right because it only overrides `send_event`.
8. There is no documented API for reading placements back. The README and examples only show images arriving as `RioEvent::UpdateGraphics` pixel queues. Positions live in the raw public field `term.graphics.kitty_placements`, a `FxHashMap<(image_id, placement_id), KittyPlacement>`. I found it by grepping the source.
9. `KittyPlacement::dest_row` is an absolute, scrollback-aware row (`lines_evicted + history_size + screen row`). You have to convert it to a screen row yourself, using the formula copied from `place_kitty_overlay`. This is documented only in source comments.
10. Kitty cell geometry only reaches the graphics layer through `CrosswordsSize::new_with_dimensions`. `CrosswordsSize::new` (the README quickstart) leaves the cell size at 0, and `place_kitty_overlay` returns early on a 0 cell size, so every kitty placement would be silently dropped. I read this in the source and did not test it.
11. The image with no `i=` comes back as image id 2147483648 (0x80000000), with the same placement id. That is deliberate: auto-ids come from the high half of u32. Only a source comment explains it.
12. Replies (kitty responses, DA1) arrive as `RioEvent::PtyWrite(route_id, String)`, which is a String and not bytes. That was fine here. Some other queries (text-area size, colour) come back as separate request events the embedder has to answer; none fired here.
13. No per-line text helper is documented. `Square::c()` alone drops combining marks, so I used `term.bounds_to_string(Pos, Pos)` one row at a time. It handles combining marks and wide characters correctly (the `a` + U+0308 in text.bin reads back as `ä`).
14. The probe compiled on the first attempt with no errors and no warnings.
15. The `graphics` feature is required for this recording. I checked by building without it: PNG (`f=100`) decoding compiles to an error stub, the image produces no placement, and nothing says so, because `q=2` suppresses the error reply. Meanwhile the `f=24` support query still answers `OK`, so a client would be told images work.
16. 4096-byte chunking splits multibyte UTF-8 at chunk edges. It was handled correctly: 0 U+FFFD across all 10,040 held rows, and the last screen lines match the tail of text.bin.
