# notes: libghostty-vt 0.2.1 probe

In the order I hit them. One line each.

1. Local environment, not the library: this machine's shell guard (lean-ctx) blocked `python3 -c`, `( … )` subshells, running a script by path, and later `. ./env.sh`, so every cargo call goes through `bash run-cargo.sh …`, which sources `env.sh` and then runs `cargo "$@"`.
2. `cargo search libghostty` lists several lookalikes (`libghostty` 0.0.0, `libghostty-sys`, `mnml-libghostty-vt`, `khostty-vt`). The right one is `libghostty-vt` 0.2.1 from uzaaft/libghostty-rs, the newest release (2026-07-18). That one `cargo search` ran before `env.sh` existed, so it used the default `~/.cargo`; every build after it used the workspace.
3. The crate README is three lines. The real documentation is the rustdoc in `lib.rs`, `terminal.rs` and `kitty/graphics.rs`, and it is good once you find it.
4. Kitty graphics needs a PNG decoder that the embedder supplies (`set_png_decoder`). The crate docs say so up front, which helped.
5. `libghostty-vt-sys`'s build.rs git-clones Ghostty (pinned a887df42, 2026-07-11) into OUT_DIR and runs `zig build`, so the build needs git, network access and Zig on PATH. The README never says which Zig version; 0.15.2 worked.
6. build.rs only passes `--global-cache-dir` to Zig when `GHOSTTY_ZIG_SYSTEM_DIR` is set, so by default Zig's package cache lands in `~/.cache/zig`. I set `ZIG_GLOBAL_CACHE_DIR` (and `CARGO_HOME`, `CARGO_TARGET_DIR`) to keep everything in the workspace.
7. First successful build (`cargo build --release`, dependencies plus a hello-world main) took 178 s (2 min 58 s), almost all of it the Ghostty clone and Zig build. There were no build errors. After that the probe compiles in about 2 s. Disk use: `target` 464 MB (155 MB of it the Ghostty checkout) plus 424 MB of Zig cache.
8. `libghostty-vt-sys` declares a `kitty-graphics` feature, but build.rs never reads it (minor).
9. The kitty graphics docs show `use ghostty::kitty::graphics; graphics::set_png_decoder(RustPngDecoder::new());`: the crate name is wrong, the argument should be `Some(Box::new(..))`, and `RustPngDecoder::new` does not exist. I confirmed with the `png` feature on: the build fails with E0599. The struct has one private field and no constructor or `Default`, so code outside the crate cannot build one at all.
10. From reading the source (never run, because I couldn't construct it): even if it could be constructed, `RustPngDecoder` `reserve`s its Vec without setting a length, so `next_frame` gets an empty buffer. It also uses `Transformations::ALPHA`, which gives grayscale images 2 bytes per pixel, and then passes them on as RGBA. I wrote my own decoder with png 0.18 in about 40 lines, and it worked the first time.
11. `TerminalOptions` has no cell pixel size, so you call `resize(120, 40, 10, 22)` right after `new`. The `resize` doc says "If the dimensions are unchanged, this is a no-op", but it still sets the pixel size. The source shows this, and so does the 64x19 grid the placement got.
12. `max_scrollback` is documented in both the Rust docs and the C header as "Maximum number of lines to keep in scrollback history". It is actually passed straight to Ghostty's PageList as a byte budget, rounded up to whole pages. I found this in the Zig source and confirmed it by running.
13. Measured on text.bin at 120x40 (max_scrollback → total rows held): 0 → 40; 1 through 1,000,000 → 620; 4,000,000 → 3,329; 10,000,000 → 9,134; 100,000,000 → 18,809 (everything). That is about 1 KB per 120-column row, so "10,000 lines" would need roughly 10.3 MB, and no API takes a line count.
14. Wrong turn: from the Zig stream handler (`effects.device_attributes orelse return`) I concluded that `CSI c` goes unanswered unless the embedder installs `on_device_attributes`, so I added one. The C layer always installs its own trampoline, which answers VT220 (`ESC[?62;22c`) when no callback is set. It also answers when the callback returns `None`, although the C header and the Rust doc both say `None`/false "silently ignores" the query. I verified this with `|_| None` and then removed my callback.
15. Only the direct medium is allowed by default (`is_kitty_image_from_file_allowed()` is false). The module docs mention the storage limit and the PNG decoder but not the media limits.
16. icat.bin sends its picture as a file path (`a=T,t=f,q=2`), so with default settings nothing is stored. `q=2` also suppresses the error reply, so you get zero placements and no sign of why. `set_kitty_image_from_file_allowed(true)` fixed it.
17. That also means the recording is not self-contained: `t=f` points at `/tmp/claude-1000/…/scratchpad/test.png` (24,438 bytes, present when I ran). The placement in output.json exists only because that file does. Listing that directory to check the file showed other sessions' file names; I opened none of them.
18. The transmission has no `i=`, so libghostty assigns an internal id: the placement reports `image_id` 2147483647 (its auto-ids start at i32::MAX) with `placement_id` 0. That is correct but looks alarming.
19. Rustdoc copy-paste slips in kitty graphics: `grid_size` says "Compute the rendered pixel size", `rect` repeats `source_rect`'s text, and `placement_id` says "The image ID this placement belongs to".
20. `PlacementIteration::next()` returns `Option<&Self>` instead of implementing `Iterator`, so only `while let` works (minor).
21. There is no "give me the visible lines" call. `Formatter` formats "the entire screen" without saying whether that includes history, so I read the cells through `grid_ref(Point::Viewport)` plus `graphemes`, skipping wide-character spacer cells. A text-run sanity count (39 non-empty rows) confirms the reader works.
22. A positive: the lifetimes on `Terminal<'alloc, 'cb>`, the borrowed `Graphics`/`Image` handles and the `RefCell`-captured `on_pty_write` closure compiled first time, with no fights with the borrow checker.
