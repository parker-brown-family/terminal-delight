damage_tracking yes — Term::damage() returns TermDamage::Full or TermDamage::Partial, an iterator of LineDamageBounds { line, left, right } for viewport rows changed since the last reset_damage(); selection and the vi cursor are excluded, and scrolling with a display offset reports Full
state_snapshot partial — Grid<T> (cells, scrollback, cursor) derives Serialize/Deserialize under the default `serde` feature, but Term — modes, cursor style, colours, tab stops, keyboard-mode and title stacks — and the parser state have no serialize or replay API. TD already wrote its own: gridwire.rs re-encodes the grid as VT bytes and both sides compare grid_hash.
threading_and_loop By default the library owns the loop: EventLoop::spawn starts a "PTY reader" thread that owns the PTY, takes a lease plus an unfair lock on Arc<FairMutex<Term>> and calls Processor::advance on up to 1 MiB at a time. It includes a PTY layer (tty::Pty over rustix-openpty; ConPTY on Windows). Under this option the embedder owns the loop: Term is a plain struct with no internal locking, Processor::advance(&mut term, bytes) is public, and TD must flush a pending synchronized update (Processor::stop_sync / sync_bytes_count, both public) before acting on a graphics command.
reply_channel Replies are events, not writes: Term calls EventListener::send_event(Event::PtyWrite(String)) for DA, DSR and mode reports, and TextAreaSizeRequest / ColorRequest / ClipboardLoad carry formatter closures. Nothing in the library writes them to the PTY; the embedder does, which is how TD answers exactly once in the host (host.rs:744) while the window replica swallows PtyWrite and TextAreaSizeRequest (term.rs:95-101). Kitty a=q replies would be written by TD's own loop, since vte never sees the query.
td_migration host.rs: replace EventLoop::new(…).spawn() (host.rs:726-729) with a TD reader per pane that splits the stream at Kitty APC terminators, advances the Processor for the bytes before each, then handles the command with &mut Term; re-prove the attach fence (host.rs:18-29), which today relies on alacritty's lease discipline; the TeeReader (host.rs:134-180) becomes a step inside TD's loop. socketpty.rs: shrinks to a socket read in TD's loop, and the two hand-copied pub(crate) poll tokens (:40-50) go away. term.rs: window-owned panes move from EventLoop/Notifier to the same loop; the PtyWrite bounce and the replica's reply filter stay. gridwire.rs: grid encoding and grid_hash unchanged; add re-sending referenced images on attach. pane.rs: the 51 grid reads stay; the renderer learns to draw U+10EEEE cells from an image store. main.rs, pane/bench.rs: no change (they only use WindowSize, tty::setup_env, TermMode). No fork.
biggest_risk Owning the loop means re-proving, against code TD now owns, the one hard invariant of the host/window split — every byte lands on exactly one side of an attach snapshot — while a stream splitter that disagrees with vte about where a string ends (CAN/SUB, ESC inside OSC, buffered synchronized updates) corrupts panes without failing loudly.

threading_and_loop The embedder owns the loop: it reads its PTY and pushes bytes with vterm_input_write, and all callbacks fire synchronously inside that call. No PTY layer. No locks or atomics anywhere in the library, so a VTerm is single-threaded; Send/Sync would be whatever TD's Rust wrapper declares.
reply_channel An output callback: vterm_output_set_callback(vt, fn, user) receives every byte the terminal sends back — DA1 (?1;2c), DA2 (>0;100;0c), DSR/CPR, DECRQM, DECRQSS, XTVERSION (>|libvterm(M.m)), OSC 52 query replies, focus in/out, and key/mouse encodings. Without the callback, bytes collect in a deprecated internal buffer. XTWINOPS window-size reports (CSI t) are not answered and fall to the CSI fallback. One callback per VTerm, so TD's host would install the PTY writer and the window replica a discarding one; Kitty a=q replies would be TD's own.

grid_api Text uses alacritty's API unchanged: Term::grid() -> &Grid<Cell>, Term::renderable_content(), Cell { c, fg, bg, flags, extra: Option<Arc<CellExtra>> } with CellExtra { zerowidth, underline_color, hyperlink }, flags including WIDE_CHAR and WIDE_CHAR_SPACER, and Term::mode(). damage_tracking Yes for text; pictures get only change stamps. alacritty's Term::damage() returns TermDamage::Full or Partial (a line iterator) since the last reset_damage(). libghostty exposes a storage-wide generation stamp, bumped on any transmit, placement or delete, plus per-image stamps, but no per-row picture damage. Placement geometry moves with scrolling, so TD must recompute positions on every dirty frame.
state_snapshot No, not for pictures. TD's gridwire::encode_snapshot re-encodes only alacritty's grid as VT bytes. libghostty-vt's own binary snapshot (C API added upstream on 2026-08-03, after crate 0.2.1's pin) says Kitty image and placement state is not part of it. So a re-attaching window would get text and no pictures unless TD ships image bytes and placements itself. The window's replica also cannot re-parse t=t or t=s transmissions, because the protocol makes the first terminal that reads them, the host's shadow, delete the file or unlink the shared memory.
threading_and_loop The loop is split. alacritty's EventLoop owns the PTY reader thread and parser, and TD's host.rs TeeReader already copies every read on that thread while holding the lease. libghostty-vt owns no loop, thread or PTY: the embedder calls vt_write. Its Rust handles are !Send + !Sync, so the shadow Terminal must live on one thread. It can be created lazily on alacritty's reader thread (e.g. thread-local per pane) and fed inside TeeReader::read before alacritty parses the chunk. The alternative is a dedicated thread fed through a channel, which loses the ordering that both the attach fence and the a=q reply depend on.
reply_channel There are two reply channels, and TD must merge them by hand. alacritty emits Event::PtyWrite(String), which TD bounces to the PTY. libghostty-vt calls its write_pty callback (Rust: Terminal::on_pty_write) for every reply it generates, DA and DSR included. To keep 'exactly once', TD must drop every libghostty reply except Kitty APC responses (ESC _ G ...). Ordering matters as well. kitty's detection recipe is a=q followed by DA1, and a terminal that answers DA1 first is judged to lack pictures. So the shadow must parse each chunk, and write its a=q answer, before alacritty answers a DA1 in the same chunk; viu and kitten icat both send a=q and then CSI c in the captures.
td_migration Text-side change: the smallest of any picture option. Seam work: the largest. The seven files, one by one. pane.rs: its 51 grid reads stay. It gains a picture pass that walks the shadow's placements, copied out as Send-able values (image id, generation, RGBA bytes, viewport row/col, grid size, z), and paints them in gpui above or below the text by z. For U=1 it also scans alacritty's cells for U+10EEEE placeholders. host.rs: TeeReader::read feeds a per-pane libghostty Terminal on the reader thread before alacritty parses (thread-local, because the handle is !Send). To stop the divergence it must also rewrite the stream: find each direct placement without C=1, inject the equivalent cursor motion into alacritty's input at that byte offset, and forward the rewritten bytes to clients so the replica still hashes equal. That means TD frames Kitty APC itself anyway, which is the approach Zellij takes in front of the same vte 0.15. gridwire.rs: encode_snapshot and grid_hash cover text only. The attach protocol needs a picture message (image bytes plus placements), because the replica window cannot re-read temp or shm transmissions the host already consumed. Build: Zig 0.15.2 or 0.16 plus git/network, or a vendored ghostty source, in the AppImage and AUR builds.
biggest_risk A direct placement without C=1 is the default in chafa, viu, kitten icat and timg; only mpv sends C=1. From the very next byte of text the two grids disagree, and every picture after that is painted at a libghostty row that no longer matches alacritty's cells.

state_snapshot No emulator-state snapshot is sent to clients, because clients hold no terminal state: on attach Tab::add_client calls set_force_render, the next render sends every visible line of every pane, and Screen::add_client clears that client's HostKittyState so its pictures are re-transmitted. threading_and_loop Zellij owns the whole loop. A 'pty' thread starts an async TerminalBytes reader per pane (64 KiB reads) that sends ScreenInstruction::PtyBytes to the single 'screen' thread; the screen thread owns every Grid (built on Rc<RefCell<…>>, so not Send) and runs vte there; writes to PTYs go through a 'pty_writer' thread; other threads are wasm (plugins), background_jobs, server_listener and server_router. It includes its own PTY layer (os_input_output).
reply_channel Grid pushes every reply (DA, DSR, DECRQM, kitty-keyboard ?u, Kitty graphics OK and errors) onto pending_messages_to_pty; after each handle_pty_bytes the Tab drains them and writes each to that pane's PTY once, on the server. Queries only a real terminal can answer (CSI 14t/16t pixel sizes, OSC 10/11/4 colours, an OSC 52 read) are forwarded to a client's host terminal, and the pane stops parsing until the reply or a 500 ms cache fallback lands, so the answer arrives in the right stream position.
td_migration Nothing to adopt wholesale — Zellij is not a library TD can link. What TD can take, and what it costs: (1) copy, with the MIT notice, kitty_graphics/interceptor.rs, parser.rs, store.rs and replies.rs (about 1,200 lines). (2) Rewrite grid_state.rs's anchoring (canonical_line over lines_above, viewport and lines_below) onto alacritty's Grid (WRAPLINE flags, display_offset) in term.rs, since alacritty keeps no canonical-line index. (4) pane.rs paints from placements. main.rs and pane/bench.rs change only in wiring. biggest_risk Reading Zellij as the model for TD's host/window split misleads, because its clients are dumb VT sinks with no replica, and the part worth copying — its Kitty code, merged on 2026-07-31 — is anchored to Zellij's own canonical-line grid, so a port onto alacritty's grid inherits eight-week-old edge cases with none of Zellij's tests carried over.

zmx — server-side snapshots with libghostty-vt (host/replica prior art)✅ complete
what_it_is zmx is a small command-line session persister for the terminal, written and maintained by Eric Bower (GitHub neurosnap; sponsored by pico.sh): each session gets its own daemon that owns the PTY, clients attach and detach over a unix socket, and the daemon keeps a libghostty-vt Terminal fed with the same PTY bytes so it can replay the screen and scrollback as VT bytes to a client that re-attaches. It deliberately has no windows, tabs or splits.
license MIT — an MIT product may copy or adapt its code with the notice kept; its libghostty-vt dependency is MIT too.
language Zig (about 91% of bytes), with shell (bats) tests; it embeds libghostty-vt, which is also Zig.
integration_path not a library (reference only) — zmx builds a single executable and exports no module or C API; TD could borrow its design (and, being MIT, its code), or run panes inside zmx sessions as a process substrate, but not link it.
build_requirements Zig 0.16.0 or newer (not cargo); network access at build time to fetch ghostty from GitHub at commit 8af6897c (a hash-pinned 1.3.2-dev tree, built with emit-lib-vt); links libc. Whatever C/C++ ghostty's lib-vt build compiles is built by Zig's own toolchain [inferred, not verified here].
latest_release v0.8.1, published 2026-09-05
first_release v0.0.1, tagged 2025-11-28 (repository created 2025-10-10; the first GitHub Release object is v0.6.0, 2026-05-29)

api_stability Pre-1.0 application (0.8.1) with no library API to be stable; the README says it has not reached a stable state, an IPC change between versions kills running sessions, and the CHANGELOG marks *BREAKING* changes in 0.1.0, 0.5.0 and 0.7.0. It pins libghostty-vt to a dev commit, whose own snapshot format is declared work-in-progress.
maintainers 1 contributor with >= 10% of commits in the 12 months to 2026-09-25: Eric Bower (neurosnap), 369 of 478 commits (77%); the next, chronologos, has 13 (2.7%). A single-maintainer project by its own contract ('programs that a single person can maintain').
adoption 2,169 GitHub stars and 154 forks; packaged by Homebrew tap, mise, nixpkgs, Alpine (testing), Arch AUR (release and -git), openSUSE Tumbleweed and a Gentoo overlay; community tools built on it include emacs-term-sessions, pi-zmx, zmx-session-manager, the zmosh fork (encrypted UDP reconnect) and rootshell (an iOS/macOS terminal that lists zmx sessions). kitty_graphics None restored, passthrough live. While a client is attached, every PTY read is broadcast raw to it, so Kitty APC reaches the client's own terminal and draws there if that terminal supports it (pixel sizes are forwarded in the winsize since 0.7.0). The server-side libghostty-vt Terminal parses the APC with the readonly stream (kitty_graphics on by default, 10 MB lib quota, direct medium only, PNG disabled without a decode_png hook, which zmx does not set), but zmx never renders or replays those images: the TerminalFormatter it uses for the re-attach snapshot emits no Kitty images, so pictures vanish on re-attach (issue #14, open since 2025-12-04). With no client attached, a=q queries go unanswered.

performance_evidence none published — the README asserts speed without a benchmark; the design cost is one extra libghostty-vt parse of every PTY read (read in 4096-byte chunks) in the daemon, plus a full-screen re-serialization only on re-attach.
grid_api zmx never iterates cells itself. It uses libghostty-vt's Zig API: ghostty_vt.Terminal.init(io, gpa, {cols, rows, max_scrollback_lines, max_scrollback_bytes}); term.vtStream() and vt_stream.nextSlice(bytes) to feed PTY output; term.resize(gpa, {cols, rows}); term.modes.get/set; term.screens.active.pages with getTopLeft(.screen/.active) and pin(.{.active = .{x, y}}) to bound scrollback and viewport; ghostty_vt.Selection.init(tl, br, false); ghostty_vt.formatter.TerminalFormatter.init(term, .vt) with .content and .extra; term.getTitle(), term.getPwd(), term.colors (dynamic fg/bg/cursor); term.screens.active.cursor for logging; ghostty_vt.Parser for input classification.
damage_tracking no — zmx neither reads nor reports damage: each PTY read is forwarded raw to every client and the whole screen is re-serialized only when a client re-attaches.
state_snapshot yes — util.serializeTerminalState(alloc, term) re-encodes the server's libghostty-vt Terminal as VT bytes with ghostty's TerminalFormatter(.vt) and sends them as one Output message, on re-attach only (not first attach): phase 1 = scrollback as styled text with no extras, then CSI 2J / CSI H / SGR 0; phase 2 = the active screen with modes, scroll region, Kitty keyboard and modifyOtherKeys, cursor, charsets and protection; then OSC 7 cwd, OSC 2 title and OSC 10/11/12 dynamic colours. Not carried: palette, tabstops (deliberately), DECSET 2026 (deliberately stripped), per-cell OSC 8 links, the primary screen under an alt screen, and every picture. Against TD's gridwire::encode_snapshot: same strategy (re-emit the grid as VT bytes for a stock emulator), but zmx also carries scroll region, charsets, title, cwd and dynamic colours, which TD does not; both lose the primary grid beneath an alt screen; ghostty's formatter emits modes BEFORE content, where TD restores modes last on purpose; and zmx has no replica emulator on the client and no equivalent of TD's grid_hash check. libghostty-vt also has a binary snapshot API (ghostty_snapshot_*) that zmx does not use.
threading_and_loop zmx owns the whole loop: one double-forked daemon process per session, holding the PTY it created with forkpty(); a single-threaded poll(2) loop over the server socket, the PTY master, a signal pipe and each client socket; every PTY read (up to 4096 bytes) is fed to the libghostty-vt stream and broadcast to clients in the same iteration, so there are no threads, no locks and no snapshot/stream seam to fence. Clients are also single-threaded poll(2) loops that pipe stdin to the socket and Output to stdout.
reply_channel Two regimes. With no terminal client attached, zmx itself scans PTY output for DA1/DA2 queries and queues fixed answers (ESC[?62;22c, ESC[>1;10;0c) into the PTY write buffer; nothing else is answered, because the server's libghostty-vt stream is readonly and ignores queries (Kitty a=q, DSR, XTVERSION go unanswered). With clients attached, queries reach every client's own terminal raw, and only the leader client's input — which carries its terminal's replies — is forwarded to the PTY; a non-leader's input is dropped unless it looks like typing (which makes it leader), so each reply is written once.
td_migration Nothing to adopt as code (zmx is an application); five design points TD's host/replica could borrow, mostly in host.rs and gridwire.rs: (1) resize the host grid to the attaching window's size BEFORE snapshotting, then resize the PTY and SIGWINCH the foreground process group even when the size is unchanged, so TUIs repaint after the snapshot (loop.zig L967-1016); (2) strip DECSET 2026 from the snapshot so a replica does not sit deferring renders; (3) replay title (OSC 2), cwd (OSC 7), dynamic colours and the scroll region, which gridwire.rs does not carry today; (4) answer DA only while no window is attached and otherwise let exactly one leader's replies through — TD already writes replies once from the host, so this is a check, not a change; (5) feed and broadcast on one thread so the snapshot/stream seam cannot exist — TD instead fences alacritty's reader thread with a lease in host.rs. Points NOT to copy: zmx's snapshot has the same alt-screen gap as gridwire, emits modes before content (TD's modes-last order is deliberately safer), drops OSC 8 links and all pictures, and has no equivalent of grid_hash / ReplicaGuard. If TD ever moves its host to libghostty-vt, zmx shows that the formatter can replace gridwire::encode_snapshot for text, and ghostty's binary snapshot (ghostty_snapshot_*) is the better candidate for a libghostty-vt replica; pane.rs, term.rs, socketpty.rs, main.rs and pane/bench.rs are untouched by anything zmx teaches.
biggest_risk Taking zmx as the model for TD's re-attach would carry text only: its snapshot drops every Kitty, Sixel and iTerm2 picture (the formatter has no image output and the issue asking for it has been open since December 2025), so a re-attached TD window would still need its own picture replay path.
