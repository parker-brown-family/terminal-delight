⎇ feat/document-model
Proposed

▼ ELI5 — tl;dr
💬 comment
💡 Plain English
The reader is built as a photocopy of the terminal. The terminal has already chopped the text into fixed-width rows, so the reader spends its life guessing which chops were real and which were just the pane being narrow. Every guess is a bug waiting to happen, and content that never reached the screen cannot be shown at all. The fix is to stop photocopying: build the reader on the actual text, and let both the pane and the reader lay that same text out at their own size. Done looks like: shrink the reader's font and the screen fills with more content, in both directions, with no heuristics involved.
▼ Honest status — what today actually bought
💬 comment
📋 Three commits, one axis fixed
  • Width fit — auto-fit scales to width, side padding is 7% of the panel. Landed.
  • Reflow — join_focus_lines heals width-breaks before re-wrapping; the reader's coordinate space became the joined lines, so selection and copy came along for free. Landed.
  • Dedent — the reflow was firing on nothing, because wrap_join vetoes any indented row and an agent indents its whole transcript. Landed.
Horizontal fill now works — long reflowed lines and a full-width Links table are visible in the latest capture. Vertical fill does not work and cannot, and that is the tell this report is about.
▼ The diagnosis: a lossy round-trip
💬 comment
🔎 The reader renders a rendering
Today's pipeline destroys information and then tries to reconstruct it: 
logical content        the agent's markdown / the program's output
      ↓
  PANE RENDER          chops to `cols`, pads cells, forgets which breaks
                       were real          ←── INFORMATION DESTROYED
      ↓
   grid cells          styled_lines() → Vec<(String, Vec<TextRun>)>
      ↓
 READER RECOVERY       trim padding → dedent → join width-breaks
                       → re-wrap        ←── GUESSWORK
      ↓
  reader layout
💬 comment
💣 Every bug this session lives in one box
  • Padding trim — repairing damage the grid itself did. Twice: once in the pane's copy path, once in the reader's.
  • wrap_join's width test — a guess at whether a break was width-induced.
  • is_structural — a guess at whether a row is a code fence or a rule.
  • Dedent — a guess that a shared margin is not structure. It was needed only because the previous guess mis-fired.
  • Vertical emptiness — not a guess at all: the content was never in the pipeline. styled_lines builds exactly grid.rows from display_iter — the visible viewport, no scrollback.
Three of those are heuristics stacked on heuristics. Each new one fixes the last one's misfire. That is the shape of a design problem, not a run of unlucky bugs.
💬 comment
⚖️ The principle being violated
Render from the source, not from another rendering. The reader should not reverse-engineer the pane. The pane and the reader are two views of one document, and neither should be derived from the other. Right now the reader is downstream of the pane's layout decisions, which is why every pane-width quirk becomes a reader bug.
▼ Target architecture
💬 comment
🏗️ Document → Source → Layout → View
Three types with one responsibility each, and a seam between every pair. 
trait DocumentSource {            // WHERE the text comes from
    fn document(&self, want: RowBudget) -> Document;
}

struct Document {                 // WHAT the text is. No cols. No rows.
    blocks: Vec<Block>,           // Paragraph | Code | Table | Rule | List
}
struct Block {
    text: String,                 // logical: real breaks only
    spans: Vec<StyleSpan>,        // styling by byte range
    origin: Origin,               // provenance, for copy + jump-to-source
}

fn layout(doc: &Document, w: Width, m: Metrics) -> Layout;
struct Layout {                   // HOW it sits on this surface
    rows: Vec<VisualRow>,
    map:  Vec<DocPos>,            // visual position → document offset
}
💬 comment
🔌 Two sources, and the second is the prize
  • GridSource (shell panes) — reads the terminal grid including scrollback, and uses alacritty's WRAPLINE flag as ground truth for soft-wrap rather than guessing. We already read that flag in grid_snapshot for links and then throw it away. Heuristics survive here only for output an application hard-wrapped itself — isolated in one module, labelled best-effort, not spread through the reader.
  • TranscriptSource (agent panes) — TD already tails agent .jsonl transcripts (mcp_tail.rs). That file is the actual source document: real paragraphs, real code fences, real tables. For an agent pane there is nothing to guess. No join, no dedent, no width test. The entire class of bug we chased today cannot occur.
💬 comment
🔁 What else falls out of the same seam
The FOCUS reader is the first consumer, not the only one. A Document is also what the alt+click copy affordance wants, what the read-only MCP surface should serve instead of scraped rows, and what an export or a search would consume. Each is a new consumer of an existing seam rather than another scraper.

▼ Migration — five shippable phases
💬 comment
🛤️ No big-bang rewrite; every phase lands on its own
💬 comment
P-0
Introduce the types, port the current path onto them — zero user-visible change
high
Intent: Land Document, DocumentSource, layout() as new modules, and re-express today's reader as GridSource (viewport only) + layout(). Behaviour identical.

Acceptance: 
Given the current reader on a given pane and zoom
When the same pane is rendered through Document + layout
Then the visual rows are identical, character for character
And the existing reader tests pass unmodified
Gotcha: this phase is worthless unless it is provably a no-op. Write the equality harness first; it is the safety net every later phase leans on.
💬 comment
P-1
GridSource reads scrollback — the vertical fill
high
Intent: Read beyond the display region into the grid's history, governed by a RowBudget the reader derives from its own height and zoom. This is the fix for "smaller text leaves the bottom empty".

Acceptance: 
Given a pane with 500 rows of scrollback
When the reader's text is shrunk until 120 rows would fit
Then 120 rows of content are laid out, not 47
And the glass fills top to bottom
Gotcha: the budget is a feedback loop — more rows can change nothing about metrics, so resolve it in one pass: compute rows-that-fit from the metrics, request that many, lay out. Do not iterate to a fixed point.

Gotcha 2: styled_lines also paints the syntax overlay, human-input colouring, selection and cursor, all keyed to display_iter. Those need a line-range-generic form, which is the bulk of the work here.
💬 comment
P-2
TranscriptSource for agent panes — delete the guessing
high
Intent: For a pane running an agent, build the Document from the agent's own .jsonl — which TD already tails — instead of scraping the screen. Real markdown structure, no heuristics.

Acceptance: 
Given an agent pane whose transcript contains a fenced code block and a table
When the reader opens on it
Then the code block and table are laid out as blocks, unwrapped and unmangled
And no join, dedent or width test runs anywhere in that path
Gotcha: the transcript and the screen are not the same thing — the screen also carries tool-call chrome, spinners and the input line. Decide deliberately what the reader shows; "the conversation, not the chrome" is probably right but it is a product call, not a technical one.

Gotcha 2: a long transcript must be virtualised. Do not build a Document for 50k lines to show 60.
💬 comment
P-3
Quarantine the heuristics
medium
Intent: With P-2 in, the join/dedent/width-test machinery is needed only for shell output an application hard-wrapped. Move it into one module behind one entry point, documented as best-effort, and delete its use everywhere else.

Acceptance: 
Given the agent reader path
When the code is searched for wrap_join, is_structural or the dedent
Then none of them appear outside the single hard-wrap-recovery module
Gotcha: the pane's own drag-select copy still uses reflow_wrapped_copy, and so does the alt+click affordance. They should move onto the same entry point rather than keeping private copies.
💬 comment
P-4
Point the other consumers at the same seam
medium
Intent: The alt+click copy affordance and the read-only MCP surface both currently scrape rows. Serve both from Document, so there is exactly one answer to "what text is in this pane".

Acceptance: 
Given a wrapped command in a pane
When it is copied via alt+click, via reader selection, or read over MCP
Then all three return the same logical line, byte for byte
Gotcha: the MCP surface is a public contract. Changing what it returns is a breaking change for anything consuming it; version it or add alongside.
▼ Where this will bite
💬 comment
🔥 Honest risks
  • Selection is the hard part, not layout. Every phase has to keep click → position → copy working. The saving grace found today: focus_selection_text already reads a snapshot inside FocusMap rather than the live grid, so the reader's coordinate space is already private to it. That is the hook the Document slots into.
  • pane.rs is ~8,000 lines and holds the grid read, the styling, the layout and the copy paths together. These modules are as much a decomposition of that file as a new feature.
  • Performance. Scrollback and transcripts are big; layout must be incremental and virtualised or the reader stutters on open.
  • Two sources can disagree. A transcript-backed reader shows something subtly different from the screen. That is correct, and it will still surprise people the first time.
💬 comment
💰 What it costs, honestly
P-0 and P-1 are where the value is and where most of the risk sits — they alone fix the vertical fill and give the reader a real backlog. P-2 is the elegant one and the one that deletes the most code. P-3 and P-4 are cleanup that can wait. This is not a weekend, and it is also not a rewrite: nothing here throws away the warp, the theming, the selection or the mirror plumbing.
▼ Separate bug — Ctrl+Alt+T cascade and mass close
💬 comment
🔎 Prime suspect, not yet reproduced
The cascade: the Hyprland binding is documented as "first press opens the primary window, every later press opens a fresh scratch window", and TD is explicitly not single-instance. Key repeat on the chord therefore spawns a window per repeat — consistent with the tiny 14×11 and 15×3 tiles in the capture.

The mass close: Workspace::reap ends with cx.quit() when its last tab empties. In gpui cx.quit() ends the process, not the window — and one TD process can host several windows. So one scratch window losing its last pane takes down every window in that process, simultaneously. The correct per-window close already exists elsewhere in the file as window.remove_window().

Falsify it first: spawn two windows from one process, exit the shell in one, and watch whether the other dies. If it survives, this suspect is wrong and the 30-second alignment points instead at the checkpoint/instance interaction — save on the 30s timer, or a second process failing claim_in and releasing.
▼ Open questions
💬 comment
Q1
Is the FOCUS reader a mirror of the screen or a view of the conversation? Everything above assumes the second. If it must stay a faithful mirror — spinners, tool chrome, input line and all — then P-2 is off the table and we are stuck recovering structure from the grid forever, with the vertical fill from P-1 as the ceiling.
💬 comment
Q2
How much backlog should the reader hold — a few screens, the pane's whole scrollback, or the entire transcript? This sets whether layout can be eager or has to be virtualised from day one, which is the difference between P-1 being a week and being a fortnight.
💬 comment
Q3
Do we stop shipping reader patches while this lands? The three commits from today work and are deployed, but each one added a heuristic that P-2 is designed to delete. Continuing to patch the old path makes the migration harder; freezing it means living with the vertical emptiness until P-1 lands.
