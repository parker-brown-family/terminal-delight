▼ 2 — What SideCrab actually is
💬 comment

▼ 3 — The hook data plane (the mechanism worth taking)
💬 comment
The panel is pushed to; it does not look
Seven hooks in settings.json. Five are fire-and-forget curl POSTs of the hook payload to a loopback endpoint, each with a 2 s timeout and || exit 0 so a dead daemon can never wedge an agent. Two use the newer "type": "http" hook, where the hook's HTTP response is a return channel back into the agent. 
"Notification":      curl -s -m 2 -X POST --data-binary @- http://127.0.0.1:2722/v1/hook   (timeout 3)
"SessionStart":      … same …
"UserPromptSubmit":  … same …
"SubagentStop":      … same …
"SessionEnd":        … same …

"Stop":              { "type": "http", "url": ".../v1/hook/stop",       "timeout": 5  }
"PermissionRequest": { "type": "http", "url": ".../v1/hook/permission", "timeout": 60 }
💬 comment
⚠️ That 60 is the entire tap-to-answer feature
There is no keystroke injection, no PTY write, no window targeting. The PermissionRequest hook blocks the agent for up to a minute while the daemon parks the request and waits for a finger on the glass. The decision is returned as the hook's HTTP response. If nobody taps, the hook times out and the hold falls through to the in-pane terminal dialog exactly as if the panel did not exist — which is also, deliberately, what an out-of-date widget gets when the server refuses its write.
💬 comment
Waking an idle session — measured, not assumed
docs/spikes/reply-spike-2.md is a properly run spike against Claude Code v2.1.246: a disposable session spawned under a ConPTY in a throwaway directory, driven only through that PTY, killed and verified gone afterwards. Findings: the cross-session message bus delivers to an idle session as a new turn (live-tested); it cannot answer a session that is mid-turn (that half of the old finding stands); the CLI has no send subcommand; Remote Control is cloud-relayed and therefore the wrong shape for a same-desk companion.
💬 comment
The read API that fell out of the spike
claude agents --json prints live sessions and, per its own help, does not require a TTY. Observed shape: {pid, cwd, kind, startedAt, sessionId, name, status} with status tri-valued (idle, waiting, absent while busy) and waitingFor distinguishing permission prompt from dialog open. Their conclusion: it is not a reply channel, but it is what tells you whether a reply would be accepted right now. Only send to status: idle.
▼ 4 — Contract discipline worth stealing
💬 comment
The best artifact in either repository
docs/STATE-CONTRACT.md is roughly 25k tokens of wire contract written as narrative — every field carries the measurement that justified it and the failure that motivated it. It reads like our own commit-message doctrine applied to a JSON schema.
💬 comment
⚠️ schema marks only the last breaking shape
It is pinned at 5 while additive fields are detected by key presence, never by version number. The reason is a deploy-coupling failure they actually hit: a strict version whitelist tied every daemon deploy to a console-bound widget import, so schema N+1 bricked the panel until somebody physically stood at the desk. Unknown keys are always ignored; a version above the reader's ceiling is still treated as a dead feed, because that is what a real break looks like.
💬 comment
⚠️ null is a reading, not an absence
The key is always present; the value carries the knowledge. Consumers must test the value's type, not the key's truthiness. Unknown means no bar drawn — never a zero, never a default, never last week's number. Their sentence for it: "a wrong bar looks exactly like a right one."
💬 comment
Most-specific-first, and the order is load-bearing
For the context-window denominator: (1) the status-line document's own context_window.context_window_size, this session, live; (2) the [1m]/[200k] marker in the session's model string; (3) the models catalog's max_input_tokens for that model. Ranks 2 and 3 are ordered that way because the marker is that session's window while the catalog is the model's ceiling — preferring the ceiling would gauge a [200k] card at a fifth of its true fill. And never the sibling max_tokens, which is the output cap: measured 2026-08-28 as 128000 sitting beside a 1000000 input window. They also deleted the obvious model-name lookup table on the grounds that "opus means 200k" is a number no document said.
💬 comment
🚨 The feature that shipped and never once rendered
The widget derived its context-fill denominator solely from a [1m]/[200k] marker in the model id. The live ids on that host carry none — measured 2026-08-28 as claude-fable-5 and claude-opus-5. The bar had therefore never drawn on a real session. Green build, shipped feature, zero pixels. This is the same failure our own memory records twice over.
💬 comment
A printf channel for a surface no debugger can reach
iCUE renders the widget where devtools cannot attach, so console.log has nowhere to go. Their answer: POST /v1/panel-log, the widget describing what it saw, the server timestamping it, a 500-line in-memory ring that is never persisted. Explicitly optional in both directions — the widget must function fully when the endpoint 404s, no feature may be gated on it, and a failed POST must never surface to the operator. Over-limits are not errors: past 50 lines the first 50 are kept, and a line over 300 characters is trimmed then truncated, because losing the tail of one burst is recoverable and losing the burst is not.
▼ 5 — Interrupt economics (the notifier)
💬 comment
Six toast kinds, one shared rule
Waiting session (a needs_input row aged past 120 s) · long run (a turn over 900 s) · approval undecided past 20 s · daily digest · budget crossed · companion outage. Each carries its own dedupe key. The gate is five conditions deep: state, unacked, aged, not already toasted, not quiet hours.
💬 comment
⚠️ One toast per waiting spell, not per poll
The ledger key is (sessionId, stateSince) and it is permanent for the life of the process. A session waiting an hour toasts once, not thirty times. Only a genuinely new question — which moves stateSince — re-arms it. A session flapping needs_input → working → needs_input at the same stateSince is not a new spell. A not-yet-due spell is deliberately not consumed by an early poll, so it still fires when it matures.
💬 comment
⚠️ Quiet hours mean silent, not deferred
A matured spell inside quiet hours is suppressed and marked resolved. It does not queue. Their reasoning, verbatim in shape: without it every question that matured overnight fires the instant quiet hours end — a burst of stale toasts on a perfectly healthy morning, "exactly the kind of alert that trains you to ignore the one that matters."
💬 comment
The three-absence grace, and why it exists
The ledger prunes a session only after 3 consecutive absences from the feed. The specific failure it defends: the daemon restarting and briefly serving an empty sessions array would otherwise clear the ledger mid-spell and toast the same question a second time. Adjacent, in the daemon: two PermissionRequests in one assistant message (what parallel tool calls produce) are newest-wins, and A's release must not stand the card down while B is still parked, or the card reads working while serving B's live hold.

▼ 10 — Open questions
💬 comment
Q1
What is the acceptable ceiling on a PermissionRequest hold in TD — their 60 s, or something shorter?
Their panel sits under the monitor and is glanced at constantly, so a minute is cheap. A TD fleet may be running many agents where a blocked one costs real throughput, and the ceiling also decides how badly a TD hang hurts. A short window that always falls through cleanly is the conservative start; the number should come from watching a real fleet rather than from copying theirs.
💬 comment
Q2
Does tap-to-answer belong in FleetView, in a popout, on the phone, or in all three — and does the same endpoint serve them?
SideCrab's answer surface is a single panel with a pairing code held as a widget property, which works precisely because there is exactly one of it. TD has several surfaces already and a phone is plausible, so the authentication question that their panelToken answers arrives here in a harder form. Deciding this before T-001 is cheaper than deciding it after.
💬 comment
Q3
Does hook-fed state replace TD's inference, or run beside it as a cross-check?
Hooks require a settings fragment in every environment TD watches, which is a real deployment cost and fails silently when absent — whereas inference works on any session that happens to exist. Keeping both and treating disagreement as a finding is the expensive-but-honest option, and it is the same shape as T-003. The cheap option is to let hooks win where present and fall back to inference, which risks two code paths that are each only half exercised.
