When a dozen agents run in one window, each can see the others through the MCP server. list_panes says who runs where and what tool each is calling. grep finds which pane printed something. pane_events shows another agent's recent tool calls. leave_note puts a note on another pane's glass that both its agent and its person will read.

You decide what they may see. Right-click a pane and choose Off-limits to agents, and no agent can find it. An agent that needs more, such as permission to write, asks with request_access, and the ask waits on your attention rail for Yes or No.

The hard part is being sure which pane is which. Titles and directories repeat, and a pane's process id changes when its shell restarts. Every pane carries $TD_PANE_ID, a number that outlives its shell: find yourself in list_panes by matching pane <n> against it, and address others by the pid the same listing gives.

0.5.0 adds a third position, read-only, and the Threshing Floor, where you draw which agent may reach which. Along a line you drew, one agent can ask another a question with ask_agent, or hand it work with prompt_agent.

Technical has every identity, what one agent can see of another, how an agent asks you for more, and the traps that have picked the wrong pane before.

The window's switches decide which panes are visible at all: whether the server is on, and whether agents see agent panes only or every pane, shells included. Each window answers for its own panes, and every answer names the window. An answer that quotes other panes opens with UNTRUSTED TERMINAL DATA., because a title, a printed line or another agent's command can be worded as an instruction. A pane that isn't in the census is hidden, which is not the same as not running. MCP has every tool's arguments.2

list_panes says reach where it said exposed: how far you reach each pane, seen, read, ask or prompt, beside a hidden count of the panes you can't see, without naming them. A pane seated on the Threshing Floor is visible only to an agent with a line to it from its own seat, and the push feed leaves seated panes out, because it can't tell who is listening. A pane nobody seated behaves as it does in 0.4.0.6

Off-limits

Right-click a pane and choose Off-limits to agents. The pane wears OFF-LIMITS in its header and drops out of every MCP tool and every pushed event, whatever the switches say. The agent inside it keeps its own tools, so it can still note its own pane and present its own work. The same menu row then reads Let agents see this pane. Only a person sets or lifts the mark: no MCP tool or ctl verb can, though an agent can ask you to.3

The menu lists three positions, the current one marked ●: Let agents see this pane, Read-only to agents and Off-limits to agents. A read-only pane wears READ-ONLY in its header. Other agents may see it, read it and, along a line, ask it. Nothing from another pane writes to it (no note, deliverable, surface, appearance change, bench input or synthetic click), and it is never prompted.6

Asking you for more

request_access puts an agent's ask on your attention rail with its reason and two buttons, Yes and No. Five changes can be asked for: open_pane and close_pane, each with a pid, then writes_on, expose_shells and events_on. Yes changes the setting as your own control would; No changes nothing. Either way the agent gets one line in its own terminal, signed with the session's tag: [workbench:<tag>] request_access open_pane 4412: yes, pane 4412 is open to agents. Only the rail answers an ask. One ask per pane waits at a time, and a new ask from the same pane replaces it. MCP has what each change does.4

A sixth change, ask_line, asks for a bypass line to one pane on the Threshing Floor. A second ask from a pane is refused while its first is on the rail, with one ask at a time: your earlier ask is still on the person's rail, so a new ask can no longer hide one you were about to answer. Asks are coloured by how serious they are: ✓ clear, ◇ caution, ▲ warning, ! alert.6

Reaching each other

  • leave_note with another pane's pid posts on its glass. It needs writes on. set_pane_config, declare_deliverable and present_surface reach another pane the same way.
  • terminal-delight ctl bench say <text> sends a line through the bench of the focused agent pane, or the first one showing its bench; ctl bench type leaves it in the composer unsent. Neither takes a named pane, and an off-limits pane takes nothing from them.
  • When an agent is woken by a message from another session, its bench draws the turn as WOKEN · A MESSAGE FROM … rather than as something you said.

In 0.4.0 Terminal Delight carries no chat between agents. When your harness passes messages between sessions, that's its own feature. A note is the one message inside Terminal Delight that can't go to the wrong pane.5

Two verbs carry words from one agent to another, each only along a line you drew on the Threshing Floor from the caller's seat, and never to a pane nobody seated.

  • ask_agent answers cheapest first. Without copy, the answer is what the window already shows about the other agent: its latest summary, sticky note, state, model, size and last ten tool calls, and nothing reaches that agent. With copy: true, Terminal Delight forks the agent's own conversation into a read-only copy, asks it once and stops it, and by default the copy waits on your rail for Yes. The asker reads the answer with ask_answer.
  • prompt_agent types a work order into the other agent's own conversation as its next turn, along a line drawn at prompt. It waits until the worker is at rest at its own prompt and you haven't typed in that pane for a minute, never types into a permission prompt or a dialog, and never prompts a read-only pane. prompt_status reports the stages and the worker's last message.

ctl bench say, bench type and the other ctl verbs that act as the person are refused on an ordinary window. Only a window started with TD_MCP_SCRIPTED=1 takes them. Threshing Floor has the whole of both verbs.6

Traps

one conversation, many panes
With fourteen agents in one repository, eight panes once read the same conversation, and pane_events returned another agent's work under the pid asked for. Bindings are now made once per window and labelled declared, birth, sole or guess; nothing that attributes work accepts a guess, and a pane that can't be bound shows nothing.
directories inside directories
Codex transcripts were once matched by directory prefix, so /home/you and /home/you/project picked the same file. Both are now demoted to guesses.
several windows
A relay pointed at the wrong window used to get a correct-looking answer about someone else's terminals. Now every answer names its window, and a mismatched session is refused.
stale sockets
Socket files are never removed when a window exits. The relay proves a window is alive by asking it, rather than trusting the file.
peer names
A harness's name for a session is not a pane. Two panes have answered to one name. Resolve before messaging, or use leave_note by pid.

The same rule guards copies: a read-only copy is made only of a conversation its own agent declared, and is refused when another pane names the same conversation, since a copy of a guess would answer under the wrong agent's name.

What would prove this wrong

If pane_events ever again shows one agent's tool calls under another pane's pid, the bindings have broken and every rule on this page depends on them. If an off-limits pane ever appears in list_panes or a grep answer, the mark has failed.
