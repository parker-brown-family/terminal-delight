Open CONFIG ▾ at the right end of the bottom bar and choose ⚙ ADMIN. A panel opens in the middle of the window with three jobs: export your settings, remove old builds, and uninstall Terminal Delight. Nothing is removed on a first click.

To uninstall, pick what happens to your records: Keep records, the default, Export, then remove records, or Remove records. Click Review the plan and read the page it opens, which lists every step in order and everything it will leave for you. Then click Uninstall Terminal Delight twice. Terminal Delight closes, a background worker removes only the files it can prove Terminal Delight installed, and it writes a receipt saying what it removed and what it left.

The same plan is available without a window: terminal-delight uninstall preview prints it and changes nothing. A machine you have protected with terminal-delight admin protect refuses to uninstall.

Technical has the panel row by row, the worker's steps, the protection marker, the commands, and the manual removal for 0.4.0.

Opening ADMIN

⚙ ADMIN is in the CONFIG menu, beside Report a bug and Plugins. CONFIG ▾ appears at the right end of the bottom bar whenever any of the controls there is hidden, which is true of Clean, the UI set a new window starts in, and of Standard. When nothing is hidden, as in the all set, those controls fold into … only in a window narrower than 720 pixels (1,000 under a skin that draws controls as words), and … opens the same menu. A wide window with every control showing has neither, so narrow it or hide one control in UI CONFIG. The commands further down do the same jobs without a window.1

The panel is 500 pixels wide, centred over a dimmed window, and headed ⚙ ADMIN: Export your settings, clear out old builds, or remove Terminal Delight. Nothing is removed on a first click. Esc or a click outside closes it, and closing it disarms any row waiting for its second click.

EXPORT

RowDoes
📦 Export settingsCopies ~/.config/terminal-delight (your settings, layouts and sessions) into a new folder, ~/terminal-delight-export-<YYYYMMDD-HHMMSS>, stamped in UTC.
🗃 Export settings and recordsAlso copies ~/.local/state/terminal-delight: notes, conversations, the lines that resume sleeping agents, and the rest of the records. The row shows how much that is.

One click starts either. The copy is made in a hidden folder beside the destination, every file is read back and compared by size, SHA-256 and mode, a manifest.json listing each file is written last, and only then is the folder renamed into place. If anything fails, including one unreadable file, the half-made folder is deleted and the row says Failed: with the reason. Success reads Exported to and the path.3

Left out, each with its reason in the manifest: a credential, older copies of session files, copies of other programs' settings that installers kept as backups, files bound to this machine (the GNOME shortcut's undo files, the protection marker and the default-terminal journal), lock files, temporary files, and anything that is not a regular file. Links are recorded, never followed.

OLD BUILDS

Each install from source leaves a build in ~/.local/lib/terminal-delight, named td-<commit>-<label>. 🧹 Remove old builds counts them and says what it would free: <n> builds, <size>; <used> in use. Removes the <free> that nothing runs (<free size>) and keeps the launcher's build, running builds and the newest three. The first click asks Click again to remove <free> builds (<free size>). The second removes them and says Removed <n> builds and freed <size>.4

  • It keeps the build ~/.local/bin/terminal-delight points at, every build a process is running, and the newest three.
  • It only ever touches td-* programs in that folder. An AppImage, a link or any other file there stays.
  • It checks each build again just before removing it, and keeps one that changed, started running or became the launcher's.
  • It removes nothing while a process that might be Terminal Delight cannot be read, or when the folder or the launcher cannot be read in full.

The panel shows totals. terminal-delight admin builds lists every build with its size and why it is kept.

UNINSTALL

  1. Pick a chip: Keep records (the default), Export, then remove records or Remove records.
  2. 📄 Review the plan writes ~/.cache/terminal-delight/admin/uninstall-plan-<stamp>-<choice>.md and a .json beside it, and opens the Markdown in the window. Until you have reviewed a plan for the chip that is selected, the next row says Review the plan first.
  3. 🗑 Uninstall Terminal Delight: the first click asks Click again: Terminal Delight closes and is removed as the plan says. The second starts the worker on the exact plan file you reviewed. If that file changed since, it refuses: the plan file changed after it was reviewed; review it again.
  4. The row then reads Removal started. Its receipt will be and the receipt's path, and Terminal Delight closes.

🤖 Agent handoff, always last, writes uninstall-handoff-<stamp>.md beside the plan: a brief an agent of your choice can use to walk you through the removal. It is optional.2

What the worker does

The worker is a copy of the program placed in the removal folder and started apart from Terminal Delight, so closing every window, or an AppImage unmounting, cannot stop it halfway. Before it changes anything it makes the plan again and compares: if any of Terminal Delight's files changed since you reviewed it, it stops with Refused: TD's files changed since the plan was made. Review a fresh plan. Then, in order:2

  1. If default-terminal on made Terminal Delight your default terminal, it restores the previous list from its journal.
  2. From Claude Code's settings.json it removes only Terminal Delight's own hooks (the exact commands its installers recorded, and the briefing hook) and the mcp__terminal-delight permission entries. Other hooks stay. A file whose formatting it cannot write back byte for byte is left alone and reported.
  3. It removes the terminal-delight MCP registration from Claude Code, Codex and Gemini, using each one's own mcp remove, but only an entry whose command resolves to a Terminal Delight program on this machine. It reads the entry again just before, and leaves one that changed. An entry that only looks like Terminal Delight's is reported with the command to remove it yourself.
  4. It takes out the key-sheet block from Hyprland's bindings.lua, only if the block is exactly as installed.
  5. It asks each session host to save and close, stops Terminal Delight's windows and MCP relays (matched by the program they run, never by name), and wakes any frozen panes.
  6. With Export, then remove records, it makes the same checked export as the panel, to ~/terminal-delight-export-<stamp>.
  7. It removes the helper scripts, the key sheet, the desktop entry and icons, the cache, the runtime folders, Terminal Delight's own files in ~/.local/share/terminal-delight, the builds, and the launcher. Each file goes only if its content matches what an installer recorded or a version Terminal Delight shipped. One that doesn't is left and reported.
  8. With records kept, it deletes the install receipts of the parts it removed. With records exported or removed, it removes ~/.config/terminal-delight and ~/.local/state/terminal-delight last, and only if every step before finished. If the export failed, the records stay and the receipt says so.

A step that fails holds back only the steps that depend on it. One case to know: if Terminal Delight is still your default terminal when the worker checks, it leaves the program in place, because your desktop would otherwise have no terminal, and the receipt says the removal was partial.

What it leaves for you

  • The AppImage. The plan names it, and the worker never deletes it, because nothing on disk proves which file was mounted.
  • A GNOME Ctrl+Alt+T shortcut. It is reported with the command that removes it, scripts/install-hotkey.sh --uninstall from a source checkout. Run that first if you plan to export or remove records, because the files it needs to restore your old shortcut live in the settings folder.
  • Companion tools and their services, Omarchy themes and hooks, the agent-usage cache, Context Delight packages, MCP entries in a project's own .mcp.json, and anything it found but could not prove was Terminal Delight's. Each is listed under ## What it will leave for you in the plan and ## Left for you in the receipt.

The receipt

Everything the worker writes goes in ~/.local/state/terminal-delight-removal/<stamp>/, beside Terminal Delight's state and outside every folder it removes: receipt.md and receipt.json, the reviewed plan, journal.jsonl with one line per step, worker.log, and in before/ a copy of each shared file it edited, such as Claude Code's settings. The receipt opens with Terminal Delight was removed, …was removed in part or …was not removed.2

Protecting a machine

A machine you never want removed, such as the one you develop on, can carry a marker:5

terminal-delight admin protect --reason "my development machine"

That writes ~/.config/terminal-delight/protected and prints This machine is now protected. To lift it, delete and the path. The file names this machine by its /etc/machine-id, so a settings folder copied to another computer doesn't carry the protection with it:

# Terminal Delight will not uninstall itself on this machine.
# The marker names /etc/machine-id, so a copied config does not carry it.
# To lift the protection, delete this file by hand.
machine-id = "…"
hostname = "…"
since = "20261101"
reason = "my development machine"

On a protected machine the UNINSTALL section shows This machine (<host>) is protected, so removal refuses here. To lift it, delete <path> by hand. with Preview the removal beneath it, and the worker refuses. A marker that can't be read, or that names no machine, counts as protected. A marker naming a different machine is reported and ignored. Export and Remove old builds still work. terminal-delight admin guard says which of these applies.

When it refuses

The worker refuses before writing anything, and says Nothing was changed., when:

  • the machine is protected, or its marker can't be read;
  • the plan was made on another machine, or for another home folder;
  • Terminal Delight's files changed since the plan was made;
  • two of Terminal Delight's folders overlap, so removing one would take the other;
  • the removal folder would sit inside something the removal deletes;
  • it is running under a home folder that isn't the account's own, and a path leads outside it.

Later, a single step is left undone, with its reason in the receipt, when its file changed since the plan, is now a link, or is no longer what the plan said: changed since the plan; left, is a link; left, no longer a build; left. Another running Terminal Delight that the plan didn't cover is left alone and named.

Ownership records from the installers

The source installers record what they put on disk, in ~/.local/state/terminal-delight/receipts/<component>.receipt: each file's path and SHA-256, each hook's settings file and exact command, and each block's file and marker. The worker trusts a receipt only if you own it and no one else can write to it. Each installer also takes --uninstall, which uses the same records: install-agent-hooks.sh, install-recovery-hook.sh, install-desktop.sh, install-plugins.sh and install-keys-hotkey.sh. When an installer edits a shared file it keeps the original in ~/.local/state/terminal-delight/backups/ and prints the path.6

The GNOME installer, install-hotkey.sh, records the three shortcut values it set. Its --uninstall compares all three with what GNOME holds now and refuses if any changed; it puts back your old Ctrl+Alt+T choice only if nothing else has taken that key since. An install from before these records existed needs the review it prints.

What is not covered yet

The worker reports a GNOME shortcut and does not remove it. Each check runs just before its change, but the check and the change are separate steps, so a program swapping a path at that exact moment could get past it (issue 1222). An MCP entry registered by a bare command name, with no path, is resolved on the remover's own PATH. The plan says when either applies.

On 0.4.0

0.4.0 has no ADMIN panel and no uninstall verb. Remove it by hand, in this order, from another terminal.

  1. While the program still exists, undo what it changed outside its own folders: 
    terminal-delight default-terminal off
terminal-delight briefing hook off
  2. Remove any MCP registrations you added: 
    claude mcp remove --scope user terminal-delight
codex mcp remove terminal-delight
gemini mcp remove --scope user terminal-delight
  3. If you ran any installer from a source checkout, run its uninstaller from the same checkout. On 0.4.0 these remove every hook group that mentions the helper, including unrelated hooks in the same group, and leave a copy of the settings file as settings.json.td-backup.<seconds>: 
    scripts/install-agent-hooks.sh --uninstall
scripts/install-recovery-hook.sh --uninstall
scripts/install-keys-hotkey.sh --uninstall
scripts/install-hotkey.sh --uninstall
    install-desktop.sh and install-plugins.sh have no --uninstall on 0.4.0; remove what they installed in the next step.
  4. Delete the AppImage you downloaded, or ~/.local/bin/terminal-delight if you moved it there, and the files the installers left: ~/.local/share/applications/terminal-delight.desktop, terminal-delight.svg and terminal-delight.png under ~/.local/share/icons/hicolor/, and leanctx-mcp and td-send-mcp in ~/.local/bin.
  5. Delete Terminal Delight's own folders, keeping the first two if you want your settings and records: ~/.config/terminal-delight, ~/.local/state/terminal-delight, ~/.cache/terminal-delight and ~/.local/share/terminal-delight. The runtime folder in $XDG_RUNTIME_DIR goes when you log out.

What would prove this wrong

A file the worker removed that the plan you reviewed did not list, or one it removed without proof that Terminal Delight put it there. Either would break the rule the whole feature is built on: a second click runs exactly the plan you read.
