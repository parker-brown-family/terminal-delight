With a dozen agents in one window, one of them often needs another: to find out what it has done, or to hand it a job. The Threshing Floor is where you decide which agent may do that to which. Click the agent counter at the top right and it opens over the panes as an org chart.

You put agent panes into orgs, and each one you add gets a seat. Then you draw lines between seats. A line points one way and carries a rung: see (the other agent shows up in its list of panes), read (its screen and tool calls), ask (a question, answered without disturbing it) or prompt (a turn typed into its own conversation). Agents never draw lines. Only you do.

A seat with no line into it is hidden from every other agent, so seating an agent closes it off until you draw. A pane you never seat stays readable, as it was before, and nobody can ask it or prompt it.

Story follows one coordinator across the Floor. Technical has every control, what each rung allows, how asks and prompts are answered, and what is saved.

Picture the window as a small office with an agent at every desk. One of them is planning a site rebuild and wants two others to do the work: one to write the pages, one to run the tests. The Threshing Floor is the office's org chart, and Terminal Delight is the front desk that holds everyone to it.

You open the Floor from the agent counter, press + New org, name it Site rebuild, and drag the three agents in from the pane pool on the right. Each gets a seat, drawn as a card with its name, model and latest message. Seating them changes one thing straight away: they can no longer see each other. A seat is a desk behind a door, and the doors start shut, so nothing reaches a seated agent until you say so.

So you draw. In the builder above the chart you put the planner under Actor, pick a verb under CAN, and add the pages agent under Targets. The verb is the rung, and each rung allows what the ones below it allow. see puts the pages agent's name on the planner's staff list. read lets the planner look through the glass at its screen and the things it has run. ask lets the planner put a question to it. prompt lets the planner put a job in its in-tray. You choose prompt and press Submit, and a line appears on the chart labelled may prompt →.

The tests agent you mark read-only first, from its right-click menu, because you want it watched and never steered. Then you draw the planner a line to it at ask. A read-only desk takes questions and never takes jobs, whatever line you draw.

Now the planner works. It calls floor_position and learns where it stands: two lines out, none in. It asks the tests agent what failed overnight. The front desk answers from what is already pinned on that desk's noticeboard (its latest summary, its sticky note, its state and the last ten things it ran) and the tests agent never hears the question. When the noticeboard isn't enough, the planner can ask for a copy: a photocopy of the tests agent's notebook, handed to a temp who can only read, asked the question once, then sent home. Reading a whole notebook costs tokens, so the copy waits at your desk, as a card on your attention rail, until you press Yes.

The job goes the other way. The planner writes a work order and calls prompt_agent. The front desk holds the order until the pages agent is sitting back at its prompt, settled for five seconds, with nobody having typed at it for a minute. Then it pastes the order in under a header naming the sender, presses Enter once, and watches the work start. When the pages agent finishes, the planner reads the result with prompt_status.

Every question leaves a line in a logbook: who asked whom, along what kind of line, at which stage. The logbook keeps each question's length and a fingerprint of it, and never the words. One of its counts is questions answered with no line on the chart. It should always read zero, and the settings cog grows a red dot when it doesn't.

An agent you never seat is a visitor in the lobby. Any agent can see it and read it, as before, and nobody can ask it anything or hand it work. Those are the real terms on the Floor: orgs, seats, lines and rungs, drawn by you and checked by the window on every ask and every prompt.

Orgs, seats and lines

An org is a named group of agent panes. Adding an agent pane to an org gives it a seat, a random id saved with the pane, so a session host restart that renumbers panes keeps the chart. Only agent panes take seats, sleeping ones included. A plain shell can't be seated. Membership alone grants nothing: every permission comes from a line, which runs one way from one seat to another, or to or from a whole org, and carries a rung.1

Rungs

Each rung allows what the ones below it allow.15

RungThe actor mayThrough

Whatever the line says, the pane's own position caps it. You set the position from the pane's right-click menu, which in 0.5.0 lists three rows with the current one marked ●: Let agents see this pane, Read-only to agents and Off-limits to agents.3

  • An open pane can be reached as far as the line goes.
  • A read-only pane wears READ-ONLY in its header. It can be seen, read and asked, and never prompted, and nothing from another pane writes to it: no note, deliverable, surface, appearance change, bench input or synthetic click.
  • An off-limits pane is hidden from every agent along every line.
  • A pane nobody seated is read by any agent the window's switches let see it, and is never asked or prompted, because neither travels without a line.
  • A seated pane is hidden from every agent except along a line from that agent's own seat. An agent whose own pane is unseated sees no seated pane at all.
  • The strongest line wins when a seat-to-seat line and a whole-org line both apply. A whole-org line reaches whoever is in that org now, so a pane joining or leaving changes what the line reaches with no edit to the line.
  • A rung word this build can't read is kept in the file and grants nothing.

An agent can ask you for a bypass: request_access with change: "ask_line" and the other pane's pid, both panes seated. Its card on the rail reads Let it ask {pane} directly, past the chart, with a 1 / 3 / 10 picker for how many copies it allows, 3 unless you change it. A bypass is always an ask line, never a prompt line. Each copy asked along it spends one; at zero it disappears. It never shortens a drawn line that already reaches as far as ask.10

Drawing a relationship

The builder sits above the chart, titled Relationship, and reads left to right: Actor → CAN → Targets. Fill it any of these ways:2

  • Click + Actor, then a card on the chart. Further cards you click, or pool cards you drag in, become targets.
  • Drop one card onto another. The card you dropped onto becomes the actor, and the one you carried becomes the target, the way you file a thing under where it belongs.
  • Alt+drag from one card to another, or drag a card's ○ connector at its bottom right. The card you started from is the actor. Clicking ○ starts a relationship with that card as the actor.
  • Click a line's label on the chart to edit that line: change its rung, or erase it.

Choose verb under CAN opens a menu of see, read, ask and prompt. Each press of + beside the targets adds an empty Choose target slot and scrolls it into view; choose a card or drop one onto it, and an empty slot can be selected or removed. The line under the slots reads {n} targets · {added} join org · {changed} existing lines change, or Choose cards on the Floor or drag pool cards here. when nothing is chosen yet.

Submit stays dim until there is an actor, a verb and no empty slot. It saves every target together, adds any pool cards you staged to the org, and reports {n} relationships saved. A missing or moved pane rejects the whole batch with Choose actor, targets and verb. Check missing or moved panes. CANCEL leaves membership as it was. A new line between the same two seats replaces the old one, and any copy ask still waiting along the old one is withdrawn.

In an org's view the actor and every target must sit in that org. Lines across orgs, and lines to or from a whole org, are drawn in the System Map's builder, or by dropping a seated card onto another org's tab: that opens Drop {pane} onto {org} with Move into {org}, Relate to all of {org}, Relate to a member (once that org has members) and CANCEL. The relate routes ask for a rung, show the sentence {from} may {rung} {to}, and draw it with Draw relationship.

The org chart

The open org is drawn as a bordered region wearing its name, ▣ SITE REBUILD, with its seats laid out as a tree. A seat sits one row under the seat whose line into it is oldest, and each parent is centred over its own reports; seats with no parent on the chart form the top row, sorted by project and then title. A loop of lines is cut where it is first met. Each card names its role, read from drawn lines only: orchestrator (lines out, none in), manager (in and out), worker (in only) or seated (no line).12

A line's label reads as a sentence fragment, may ask →. A prompt label is drawn in the theme's yellow, ask and read in its accent, and see fainter. A bypass is drawn dashed in yellow and adds · bypass · {n} left. A line into an off-limits seat is drawn faint and dashed, because it grants nothing.

Seats and orgs related to this org from outside stand in a lane to the right of the border, headed OUTSIDE, one card each however many lines they have. A whole org appears as ◇ {org} marked whole org. Click an outside card to open its org.

Moving a seat that has lines into another org first warns Moving {pane} removes {n} connections. and waits for Move and remove connections. To take a seat out, drag it to the pool or to the Remove from org bin that appears at the foot of the Floor during a drag, choose Remove from org from its right-click menu, or select it and press Delete. Removing does what the bin's second line says, Access turns off: every line to and from the seat is erased, the seat is taken away, and the pane is marked off-limits. Open it again from its right-click menu. A seat whose pane is closed, or open in another window, stays on the chart as Unavailable pane with a Take off the chart button.

The chart zooms from 20% to 250%. − and + beside the org's title step it, and the third button shows the zoom and resets the view, as in 100% · Reset. Cards, lines and labels scale together; the builder and the pool keep their size.2

The pane pool

The column on the right is headed PANE POOL · {shown} of {total} panes. With nothing typed it lists every pane in no org, agents and shells alike. With a search typed it lists every pane off the open chart that matches, members of other orgs included, so you can find an agent wherever it sits.2

The search box, ⌕ find a pane, takes fuzzy words matched across project, left-bar group, tab and pane title in any order. Colons address fields: project:tab:pane, where an empty field matches anything. It narrows the pool only, and never hides a seat or a line on the chart. × clears it, and so does Esc.

A pool card shows where the pane sits on the left bar, its header title, its program, and for an agent the counter's state glyph and word in the state's colour, then AGE and TOKENS. It says OFF-LIMITS when it is, and the name of the org it belongs to. Its buttons are Open org for a member of another org, Add to org for a loose agent while an org is open (it reads Targets while you are building a relationship), and Go to pane, which closes the Floor and focuses that pane, sleeping agents and shells included. Agent cards can be dragged onto the chart or an org's tab; a shell card can't.

The System Map

◇ System Map shows every org at once, each as a bordered region holding its seats in the same tree, on the same 20% to 250% zoom. Each card shows a state dot, the tab's name, the harness and model line with age and tokens, and the newest artifact's title with a line saying No artifact, No comments, Human comments or Comments unknown. Below 60% zoom a card keeps its name, its model and that last line. Click a card or an org's name to open that org.2

Lines inside an org are drawn as they are on its chart. Between orgs, every directed pair of orgs gets one wire, border to border, labelled with the strongest rung among all the lines it stands for and a count when there is more than one: may ask → ×3. Wires follow their orgs when you move them.

Drag an org by its frame or title to place it; it snaps to a 20-unit grid, is pushed clear of the orgs around it, and is saved when you let go. Arrange forgets every placement and packs the orgs again. Dragging a card on the map moves that agent: drop it on another org to move or relate it, as on a tab. The map's builder takes a whole org or a single agent at either end: drag an org from its frame or its header tab, or an agent card, into a slot. Beneath it, Cross-org & whole-org relationships lists every line a single org's chart can't show, each with Remove, or None yet — draw one above.

How an ask is answered

ask_agent answers cheapest first, and only along a line from the asker's seat that reaches ask, or a bypass. Questions are up to 4,000 characters.56

  • From what the window already shows. Without copy, the answer comes at once: the agent's latest workbench summary (only when its conversation is proven its own), its sticky note, its state, model and size in tokens, and its last ten tool calls. Nothing reaches the asked agent, and its conversation does not change.
  • From a read-only copy. With copy: true, Terminal Delight forks the agent's own conversation into a copy that can only read, asks it once, and stops it. Only Claude and Codex agents can be copied, and only when the agent named its own conversation and no other pane names the same one. Claude's copy runs with the Read tool alone and no tool server, saves no transcript, and is stopped if anything wider turns up. Codex's runs read-only with no network, no user configuration, no apps and no web search, on codex-cli 0.162.1 only. Nothing of Terminal Delight's environment reaches a copy, and its process group is killed when it answers, fails, or passes five minutes.

A copy is priced by what it would read, the agent's current context, and by default every copy waits as a card on the asker's row of the attention rail until you press Yes or No: Start a read-only copy of {pane} to answer another agent — it reads {tokens} tokens. The card is coloured ◇ caution up to 600,000 tokens, ▲ warning up to 1,000,000, and ! alert above that; a copy of unknown size is never less than a warning. A press limit, ask_press_tokens in the layout file, lets copies at or under it start without asking; it is 0 unless you set it, and the window has no control for it yet. One copy at a time per asking pane. The asker reads the outcome with ask_answer, which answers only the pane that asked. Refusals come by name (no_line, busy, conversation_unnamed, tools_wider and more) so an agent can tell you why. MCP has the fields.1

Prompting along a line

prompt_agent types up to 32,000 characters into another agent's own conversation as its next turn, so a coordinating agent can treat the others as its sub-agents, Claude Code and Codex alike. It goes only along a line you drew at prompt, seat to seat or through a whole org. An ask line, a bypass, a read-only pane, an off-limits pane and an unseated pane are all refused by name.57

  • The words go in only at a recognised rest: the worker's own idle prompt on screen, settled for five seconds with no turn starting, a prompt that asked for bracketed paste, and no key pressed in that pane by a person in the last minute. A permission prompt, a question, a dialog, an error or a screen nobody can read is never typed into.
  • A working worker is waited for, up to ten minutes. A resting or asleep one is woken. One restarted from sleep reads, under the header: [You were asleep, and Terminal Delight restarted you from your saved conversation for this prompt. Anything that lived only in your old process is gone: background shells, permissions granted for that session only, and running loops.]
  • The first line names the sender: [Threshing Floor prompt {n}, from {sender} (pid {pid}): a person drew a prompt line from that agent to you. Your last message this turn is returned to the sender.] When the worker's conversation can't be proven its own, the last sentence reads The sender is told when you finish.
  • Every control character but newline and tab is removed. Enter is pressed once, a second after the paste shows on the worker's screen. If the paste doesn't show within four seconds there is no Enter, and the prompt fails saying the words may be sitting at the worker's prompt; the next prompt to that pane is pasted after them, and its Enter sends both.
  • The line and the pane's position are checked again on every look until Enter, so erasing the line or marking the pane read-only stops a prompt that hasn't gone in.
  • One prompt at a time from a sender to a pane, and prompts to one worker go in the order they were sent.

prompt_status reads the stages waiting, typing, delivered, working, finished (with the worker's last message when it can be read), failed and expired, and can hold its answer up to six seconds. An optional key of up to 64 characters names one assignment: sending the same key again reports the first attempt and never types a second turn. MCP has the fields.

The record of asks

Every ask and every prompt stage appends one JSON line to $XDG_STATE_HOME/terminal-delight/threshing-floor/<session>/asks.jsonl: an id, the time, the two seats, via (line, bypass, prompt, or none when there was no line), the stage, a refusal's name, the program and model, what a copy would read and did read, and its cost when the program reported one. Ask stages are cheap, priced, pressed, declined, copy_started, answered, refused and failed; a prompt records its own stage words. The record keeps each question's or prompt's length and SHA-256 and never its words, and never an answer. Prompt keys are kept beside it in prompt-keys.jsonl, as the prompt's id, the sender, the key's SHA-256, the worker's pid and the time.87

The counts in the settings tray are read back from this record when the Floor opens and after every ask. A record written by a build from before the rename, under warroom/<session>/, is still read and counted, and never moved.

What agents are told

Every agent Terminal Delight launches gets a paragraph about the Floor in its briefing: Claude in its system prompt, Codex in its first prompt. It says that agents work with each other only along lines a person draws, names the four rungs, and tells the agent to call floor_position to learn its seat, the panes it reaches and how far, and the panes that reach it, and to read it again before relying on it. It tells a worker to treat a turn opening with [Threshing Floor prompt <n>, from ...] as carefully as one its person typed, and to end with one final message, because that message goes back to the sender. It tells a coordinator to hand over a work order with how the work will be judged done, to check each reply and prompt again when it falls short, to stop and tell its person after two or three tries on the same piece, and to ask an agent from a different provider for an adversarial review.9

Seen from outside

  • list_panes gives each pane a reach, how far the caller reaches it (seen, read, ask or prompt), and a hidden count of panes the caller can't see, without naming them.5
  • The pushed events (agent_appeared, tool_call, agent_vanished) carry only panes nobody seated, because the feed can't tell who is listening.
  • No MCP tool and no ctl verb draws, changes or erases a line. Only the Floor and a Yes on the rail do.

What would prove this wrong

If an agent ever gets an answer from ask_agent, or a turn typed by prompt_agent, with no line from its seat on the chart, the Floor has failed. The record's count of asks answered with no line exists to show exactly that, and it should read zero in every session.
