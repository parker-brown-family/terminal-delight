Terminal Delight is an MCP server. An agent running in one of its panes can ask about the rest of the window: which panes exist and what each is running, what they printed, what tool another agent is calling right now.

It starts locked down. Nothing is readable until you turn the server on, in the Threshing Floor: click the agent counter at the top right. Even then only agent panes are visible unless you choose all panes. Writing is a second switch, and a write only ever restyles a pane, leaves a note, declares a deliverable, opens a document or puts work on a workbench. No tool can type into a terminal.

To connect an agent, register the relay as a stdio MCP server:

claude mcp add --scope user terminal-delight -- terminal-delight mcp

The relay finds the window it is running in by itself. Every answer ends with the window it came from, because several Terminal Delight windows can run on one machine.

Who may reach whom is yours to draw. In the Threshing Floor you seat agent panes and draw lines between them; an agent asks another only along a line you drew, and a question that needs the other agent's own memory goes to a read-only copy of it, which you pay for with a Yes when it is expensive.

Technical lists all fifteen tools with their arguments, the switches, the Threshing Floor's rules, and the errors.

The server speaks newline-delimited JSON-RPC 2.0, advertises MCP protocol 2025-06-18, names itself terminal-delight, and offers tools and logging. It answers for the panes of one window.1

Connecting

There are three ways in:

the relay
terminal-delight mcp, registered as a stdio server. It forwards each request to a running window over that window's control socket. It finds its own window by walking up its parent processes to the pane it was started in, so it needs no environment variable; --pid <N> picks a window explicitly. If the window is replaced mid-session, the relay reconnects to the same session once and says so on stderr. Each call waits up to ten seconds.
in-process
An MCP client that launches terminal-delight itself with TD_MCP set gets the server on the window's own stdio. This is the only way that receives pushed notifications.
one call from a script
terminal-delight ctl mcp rpc '<json>' hands one JSON-RPC line to a window.

The registration this machine uses, in ~/.claude.json:

"terminal-delight": { "type": "stdio", "command": "terminal-delight", "args": ["mcp"] }

A relay that located itself names its session and pane with every call. If that session isn't the window's, the call is refused with -32001, wrong window: this is terminal-delight session "1" (window 31337), and you asked for session "2". Nothing was read or written., so a relay pointed at the wrong window gets an error instead of someone else's panes.

The window's switches live in the Threshing Floor: the agent counter at the top right, or THRESHING FLOOR in the footer's … menu. In 0.5 development, all six ctl mcp policy changes are refused unless the operator launched that window with TD_MCP_SCRIPTED=1. This includes disabling access used by other workloads. An agent can propose wider access with request_access; it cannot grant the proposal to itself. Standard processes still have account access. The optional offline Restricted command profile enforces a smaller scope before workload code starts; online agents and automatic delegation are unavailable in that profile. Each change is saved with the session. TD_MCP starts the in-process transport but does not turn the server on, and TD_MCP_WRITE turns writes on only alongside TD_MCP.

Where a tool takes a pid, leaving it out means your own pane, which only works through the relay because only the relay says who is calling. Without it you get no `pid`, and this connection did not say who is calling — pass a pid from list_panes. A write to a pane the policy hides is refused.

Appearance

get_pane_config and set_pane_config use 0 to 100 percent for brightness, contrast, colour, text, background, gamma, menu_bar, text_size, bench_size, warp, crawl_angle and crawl_depth, plus crawl as true or false, and logo as an image path for a pane. An update names only what changes; a misspelled channel is an error. The values are absolute, so "20 % lower" is yours to compute from a read. On a pane, only the channels you set become its own; outer changes every pane that follows the window.

The Threshing Floor

The switches above hold for the whole window and a pane's position for every agent. The Threshing Floor says which agent may reach which pane, as an org chart you draw. Give an agent pane a seat, then click one seat and another to draw a line from the first to the second. A line's rung is how far its sender reaches: see it in list_panes, read it with grep, pane_events and get_pane_config, ask it, or prompt it: give it work. Asking reads an agent and leaves its conversation as it was; prompting is its next turn. Click a line's label to change its rung or erase it.

  • A pane nobody seated keeps the window's switches. Agents read it as before, and nobody asks or prompts it: neither travels without a line.
  • A seated pane is hidden from every agent except along a line from that agent's own seat.
  • Read-only caps a line at ask: a read-only pane is asked, never prompted. Off-limits beats every line.
  • A line drawn at ask before prompt existed stays an ask line. Prompting takes a line you set to prompt.
  • Only you draw, change or erase a line. An agent can ask you for a bypass line to one pane with request_access ask_line; it lasts the number of uses you pick on the card, three unless you change it, and it is always an ask line, never a prompt line.

Each seat shows its agent's state, model, size, latest summary and note. The Threshing Floor's last line counts this session's asks: answered from what was visible, answered by a copy, and answered with no line, which must stay at zero.

Asking another agent

ask_agent answers cheapest first. Without copy, the answer is what the window can already show about the agent, and nothing reaches it. With copy, Terminal Delight forks the agent's own conversation into a copy that can only read, asks it the question once, and stops it. A copy reads that agent's whole context again, so it is priced when it is asked for. By default every copy waits on the asker's row in the attention rail, saying what it would read and how the question begins, until you press Yes or No. If you set a press limit (ask_press_tokens in the layout, 0 unless set), a copy at or under it starts at once, and one over it, or of unknown size, still waits. The asker reads the answer with ask_answer.

A copy is refused by name unless the agent named its own conversation and no other pane names it. Claude's copy runs with the Read tool alone and no tool server, checked before and as it starts; Codex's runs in a read-only sandbox with no network, on a version whose switches were measured. Nothing of Terminal Delight's own reaches a copy's environment, and a copy leaves no transcript. One copy at a time per agent. Every ask is recorded with its question's length and fingerprint, never its words, and never the answer.

Giving another agent work

prompt_agent is how a coordinating agent treats the other agents in the window as its sub-agents, whatever program each runs. Along a line you drew at prompt, its words are typed into the worker's own conversation as its next turn, and the worker answers with everything it already knows. Nothing is typed at once: the window waits until the worker is at rest at its own prompt.

  • The worker must show its idle prompt for five seconds with no turn starting, since a streaming agent's screen can look idle between chunks. A working worker is waited for, up to ten minutes. A resting or asleep one is woken first, without moving your focus. One woken from sleep is a fresh process on its old conversation, and the prompt tells it so: its background shells and the permissions you gave that session are gone.
  • A worker showing a permission prompt, a question, a dialog or an error, or one you typed in during the last minute, is never typed into. The waits are long on purpose: this runs while you are away, and slow beats wrong.
  • The words go in as one bracketed paste with every control character but newline and tab taken out. Enter is pressed once, a second after the paste, and only once the paste shows on the worker's screen. Without that, the prompt fails and says the words may be sitting at the worker's prompt; the next prompt is pasted after them, and its Enter sends both.
  • The first line names the sending pane and says you drew the line, so the worker knows the turn came from another agent.
  • One prompt at a time from a sender to a worker, and a worker's prompts from several senders go in turn. A key makes a retry safe: the same key returns the first prompt instead of typing another.

prompt_status reads the stages, waiting, typing, delivered, working, finished and failed, and on finished the worker's last message, read from its own Claude Code or Codex transcript. It is given only when the prompt's number is in that transcript ahead of it, so the message is known to answer this prompt; otherwise it says why the message is not known. Erasing the line, or marking the pane read-only or off-limits, stops a prompt that has not been sent, even in the second between the paste and Enter. The ask record keeps a line per stage with the words' length and fingerprint, never the words.

An agent asks, a person answers

A refusal about access no longer has to be the end of it. request_access puts the agent's ask in the attention rail's first lane, ACCESS, coloured by how serious it is (✓ clear, ◇ caution, ▲ warning, ! alert): what it wants in plain words, its reason in quotation marks, and two buttons, Yes and No. With the queue open, y and n answer the row under the cursor. Yes changes the setting the way your own control would and saves it; No changes nothing. Either way the agent gets one line in its own terminal, signed with the session's tag: [workbench:<tag>] request_access open_pane 4412: yes, pane 4412 is open to agents. It is typed when that pane is on screen. The setting does not wait for the line.

One ask per pane at a time; a second is refused while the first waits, and an ask goes when its pane closes. An ask for what is already so is refused before it reaches you. Asking does not need writes, since writes are one of the things an agent may ask for. Appearance needs no ask at all.

Only the rail's buttons and keys answer an ask. No MCP tool and no ctl verb can. An agent that has a shell still runs as you and could edit the state file directly; this is the door Terminal Delight offers, not a wall around the machine.

Every answer says where it came from

Each tool result, errors included, ends with a line like — terminal-delight · session 1 · window 31337 · td-81ec545-rows-where-drawn and carries the same in structuredContent.instance. To find your own pane in list_panes, match its pane <n> against $TD_PANE_ID; titles and directories are not unique.

What another pane says is data

An answer that quotes other panes opens with UNTRUSTED TERMINAL DATA. before anything else, and names each quoted field under structuredContent.untrusted_terminal_data. Those answers are list_panes, grep, pane_events, ask_agent, ask_answer, prompt_status and engineering_state, and the same goes for data.untrusted_terminal_data on a pushed event. A line a program printed, a title it set or a command another agent ran can be worded as an instruction, and the label is how the agent reading it knows it is not one. Terminal Delight's own answers carry no label, and neither do a person's document_notes.

Pushed notifications

Over the in-process transport, after initialize and with events on, the server pushes notifications/message with data.event set to agent_appeared, agent_vanished or tool_call, about once a second. A pane seated in the Threshing Floor is never pushed, because the feed cannot tell who is listening. logging/setLevel to warning or above silences it. The relay carries no pushes.

What would prove this wrong

Any tool call that puts bytes into a pane's terminal breaks the server's first rule. So does any answer that describes another window's panes without saying which window it came from, and any answer that quotes another pane without opening with the label. In the Threshing Floor: any ask answered with no line, and any copy that writes, reaches a tool server or the network.
