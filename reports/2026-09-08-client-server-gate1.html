The doc being approved

Problem — one cause, two faces

When the window dies, every running agent dies with it: losing a window should cost a window, not a day of running work. And automation keeps creating windows — a CLI call that should be invisible boots the full terminal instead (the phantom-window morning). Both happen because the window process is the terminal.

Success metric

During a live agent run, kill and relaunch the GUI N times; after every relaunch, every PTY, pane, tab, and sticky note is still there and still running. The count of losses across the run is the metric, and it ships at zero. Watched but not the metric: unexpected windows spawned by a week of automation, expected to fall to zero as a consequence.

Announcement

Terminal Delight now keeps your sessions alive even when the window isn't. The terminal itself — every shell, every running agent, every pane and sticky note — lives in a small always-on server on your machine; the window you see is just a view attached to it. Close the window, crash it, or swap in a new build mid-flight, and your work keeps running; open a new window and you're exactly where you left off. Command-line and MCP tools now talk straight to the server, so automation never pops a window again. Your terminal is finally the place your work lives, not the process your work dies with.

Screens

No new UI. The product is that the existing screens survive: relaunch the app and the same windows, tabs, panes, and notes come back live. Any small affordances (an attached/detached hint, say) are Gate 2+ details, not product surface.

Out of scope for v1

Remote attach — this machine only; another machine is a later feature. Multi-attach — several windows on one live session is not a v1 goal; if the architecture makes it cheap, fine, but nothing in v1 may get harder to keep it possible.

measuredThe seam already exists

Every GUI window already serves a per-pid unix socket (ping, tab ops, adopt, paint, mcp rpc), and the ctl and mcp subcommands are already pure clients that never touch the UI toolkit. The protocol core is a pure function shared by two transports; a third transport plugs into one entry point. A split reuses far more than it invents.

Up to 10,000 lines per pane, never persisted anywhere, gone with the process — along with the PTYs, every child process, and the live control connections. 2 · Does "nothing lost" include scrollback?

Non-resumable foreground programs are classified unrecoverable by today's restore story — reasonable, since restore means respawn. Under a server they are just children of a PTY that no longer dies; they survive by construction.

Recommendation: yes — count them in the metric. It costs nothing and it is the honest reading of "every PTY still running".

Coupling hot-spots, hardest first

  • Frame-rate shared-memory grid reads — the UI locks the Term mutex in dozens of places to paint, hit-test, and search; the read path assumes zero-cost shared memory.
  • UI writes into the emulator — selection lives inside alacritty's Term and is set from mouse handlers; scroll position likewise. No seam at all today.
  • Pid-keyed, machine-local identity everywhere — sockets, write targets, event keys, /proc parent walks (which already fail under tmux). None of it survives a process hop; session cross-wiring has bitten four times.
  • /proc introspection woven through the UI thread — foreground-mode polling, capture-on-save; must run wherever the PTYs run.
  • Everything funnels through the main thread — nested budgets (10 s ≥ 8 s ≥ 5 s, 150/40 ms tickers); a richer server API inherits this latency model; headroom unmeasured.
  • One fragile dispatch ladder — unknown verb boots the GUI; the stale-fork binary lacking headless verbs regressed every caller at once. Client and server currently share a dispatch whose failure mode mutates on-disk state.

Reusable assets

  • The emulation core is already server-shaped and toolkit-free: term/session/instance/recover and the layout tree are std+libc only, unit-tested without the UI.
  • A truthful write round-trip exists (per-target apply outcomes) — the model the ctl path should adopt.
  • Fail-closed ownership arbitration is solved (flock claim; persistence disarmed before release). Scratch windows already model a zero-persistence client.
  • The durable unit is a rebuild recipe (cwd, resume line, appearance) — a thin client's pane-rebuild story already exists.
  • The substrate is verified: KillUserProcesses=no, Linger=yes — a user daemon survives logout and starts at boot.
  • Field survey on record: wezterm-mux, VS Code ptyHost, zellij, shpool, zmx.

Gate 2's question list

consolidated from six subsystem maps · none blocks Gate 1

Deduped across the six maps. Questions 2 and 3 of the decision round on the main page settle the first of these at the product level; the rest are architecture.

  • What does "nothing lost" mean — scrollback continuity, and non-resumable foreground programs (vim, htop)?
  • Pane identity — what durable, client-addressable id replaces the shell pid, and is outside-addressability wanted at all?
  • Session ground truth — keep forensic inference, adopt hook-pushed ids, or both? (Plus one stale-comment discrepancy to settle by reading.)
  • Session ownership — who holds the flock when sessions outlive windows; can two explicit launches contend?
  • Write gating — unify MCP's gated, truthful-outcome model with ctl's ungated queue-ack, deliberately.
  • Trust and auth — same-user 0700 unix trust is the entire model, and adopt runs arbitrary commands. Anything beyond it needs an auth story (recorded unsolved).
  • The grid — server-side Term behind a diff protocol vs client-side replica on the raw byte stream. The central cut.
  • Push feed — the relay every in-pane agent uses gets no notifications; deliberate contract or a gap the split closes?
  • Binary shape — one binary or two; what unknown-verb semantics replace the GUI fall-through (the pinning test gets rewritten either way).
  • Discovery and addressing — what replaces the pid-keyed socket scan and /proc walks; stale sockets and recycled pids are addressing hazards.
  • Formally record the trigger — say in a doc whether the staged "build the daemon when it measurably hurts" condition has fired.

What the method misses

  • One recorded conflict between maps (whether the Hyprland workspace is part of the session key or only a ranking hint) was kept, flagged, and left for Gate 2 to settle by reading the resolver fresh.
  • Runtime headroom (latency budgets under load) is unmeasured everywhere it is mentioned.
  • "The triggers look fired" is inference from issue traffic and one incident, and is labelled so.

One corrected claim

The recon's synthesis flagged a live writer still updating the legacy state file every 30 seconds and told us to kill it before trusting persistence measurements. Checked the same day: the file's last write is 10:13:46 — the moment the phantom-window revert landed — and every running terminal-delight process is on the live-line build (verified via /proc/<pid>/exe). The writer was the stale-fork binary, already dead; what remains is residue, and the 30-second impression came from the backup cadence it left behind. The correction is in research-inventory.md next to the original claim.
