Restricted commands

A build from an unfamiliar repository can run beside a production shell. Both belong to you, but the build should not gain control of that shell. Restricted starts the build with one chosen project and no network. This review fixes the reported gaps and records what the tests cover.

Shared workspace

That leaves two boundaries to verify: which files the command receives, and which TD actions it can request.

Directory identity

The review found that validation pinned one directory but scanned its pathname. Renaming that path could make the scan inspect a replacement. Validation now walks open directory handles and checks each entry’s device and mount identity.

The command’s access to TD needs its own check.

Caller identity

An agent could previously name another pane and be treated as its occupant. The OS now reports which process connected to TD. TD checks that process runs under the pane it claims, then checks the current policy before making a change. A Restricted command uses a supervisor outside its sandbox to relay its permitted note.

Access proposals

The optional own-note grant still follows the existing MCP switches. Revocation blocks future TD effects after an in-flight accepted note finishes; it does not undo files or stop ongoing file work. Network, TUIs, GUI services and automatic delegation remain unavailable.

Regression controls

Removing each protection independently checks whether its regression test can detect the failure. The first injection fixtures could not: their invalid payloads were refused before reaching the intended guard. Correcting those fixtures made both removed guards fail their intended tests.

Both strict production lint runs, formatting, the optimized build and remote CI pass. The native exercise also checks the older host binary used by the existing daily window. Authorized output and shared files can still mislead an unrestricted reader; that reader’s broader actions are outside the boundary.
