The Comments Shelf

A fourth tab on the pane's rail, holding notes you write and the agent never reads — and the DRY audit of the spine it has to live inside.

parker-brown-family/terminal-delight · branch chrome/phosphor-legibility · one approval, then four slices

The rail on your workbench has three tabs. At the width a three-column tiled pane actually hands it, it cannot draw all three — the frame is overflow_hidden and decisions runs off the end of it. So a fourth tab means two pieces of work: the comment board, and the arithmetic on a tab row nobody has measured.

The board itself turns out to be cheap. Everything a comment needs — a place on disk, a restore when the window opens, a row on the rail, a card when you click it, an unseen dot when one arrives while you were elsewhere — already exists for the eight kinds the bench holds today. Make a comment a ninth kind and it inherits all of it, and the only genuinely new machinery is a text box that does not type into the pseudoterminal.

    The tab row already overflows inferred

    Three chips need 200 px; the rail gives the row 118–191 px depending on pane width. The fourth tab makes it 264 px against the same budget. Fix the row before adding to it — one flex_wrap, and it repairs a tab that is unclickable today.

  2. 2

    A comment is a surface, so it needs no new store measured

    surfacefeed::drop_surface already writes a .json into the pane's own directory, and the bench re-reads that directory when a window opens. Persistence, restore and history capping come for free, and the window has the write path in bench_dir().

  3. 3

    The bench composer is a mirror, not a buffer measured

    Every keystroke in it has already gone down the pseudoterminal; the local Line exists only so the caret can be drawn. A comment composer that reuses it would type your private notes into the agent's prompt. This is the one piece that has to be built rather than borrowed.

  4. 4

    A corner guard is promised and does not exist contradicted

    benchdraw.rs line 25 says a guard test in crate::skin catches literal corners. There is no such test, and benchdraw.rs itself has two — one of them draws the LIVE → AGENT chip in the photo you sent.

  5. 5

    Anyone can write into a pane's directory measured

    Any process running as you can drop a file that says kind: "comment". Origin already exists to record who did. Label the writer on the card rather than trying to lock the door — an unattributed note that looks like yours is the failure worth preventing.

The DRY audit

You asked whether restyling the whole workbench spine would break anyone's will to live. It mostly would not, and the reason is that the spine already has the Rust analogue of a component library: Skin owns every shape, benchdraw owns every element, and three tests read the source file and fail the build when a renderer hand-rolls something.

What I need from you

Does a comment ever reach the agent on its own?

Recommendation: no, with one door. The board is silent by default and the card carries an ask agent verb you press. That honours “external to the agentic workflow” and still lets a note become a prompt when you want it to, without a second mechanism.

The alternative is a hard wall with no verb at all, which is simpler to test and means copying text out by hand the first time you want to act on a note.

Per pane, or per project?

Recommendation: per pane, the way surfaces already work. A pane is the conversation, and the note you leave belongs to the thing you were watching. A project-wide board is a different feature with a different home — it would want to live beside the left bar, not on one pane's rail.

The cost is real: close the pane and the board is reachable only through its directory on disk. Surfaces already have that property, so this adds no new sharp edge, but a note feels more personal than an artifact and may want to outlive its pane.

Does comment go in the agent-facing catalogue?

Recommendation: no. Keep it out of td-surface-protocol.md and out of surface_catalogue. An agent that reads the spec and emits one is putting words on your board; leaving it undocumented means the only documented writer is you. The parser still accepts it, because refusing it silently would be worse — it arrives labelled with whoever dropped it.

Fix the tab row inside this work, or separately?

Recommendation: inside, as slice one. It is one flex_wrap plus a test, it repairs a tab that is unreachable today, and adding a fourth chip to a row that cannot hold three would ship the feature broken on every narrow pane.

Argument for separating it: it is a fix to shipped behaviour and deserves its own commit and its own falsifiable issue rather than riding a feature branch.

Method and limits

Nothing here was built or rendered. Every figure is drawn by hand from the source on chrome/phosphor-legibility as it stood on 18 September: the rail geometry from workbench.rs constants, the row anatomy from benchdraw::rail_row, the guard table from the three include_str! tests in benchdraw.rs, and the missing corner guard from a grep over skin.rs that found no source-scanning test. The one number I estimated is glyph advance — 6.0 px per character at 10 pt monospace — and figure 1 carries the check that would kill it. The strings on every mockup are invented. No claim here has been confirmed against a running window.
