Program Pixels

This morning Alt+click started opening pictures inside Terminal Delight. Click a PNG path in a pane and it opens in a floating square beside the line that printed it; close the square and the GPU gets its memory back, which a hundred-cycle soak on the real card proved. The next step is pictures that programs draw themselves — chafa, timg, a ratatui image widget, and one day the video an agent plays in its pane — so the first question is how much of the square they can use. The back half carries over whole: drawing under the glass and giving the texture back. The front half does not exist yet, and tonight’s runs made its hard part concrete: two of the three programs you named put their picture wherever the cursor happens to be, and nothing in TD that sees the picture knows where that is. This brief shows what each program actually does in a TD pane, why the cursor is the whole problem, and two ways through it: teach TD’s own read loop to turn every picture into text, or swap TD’s emulator core for one that already draws pictures, the move TD’s foundation review set aside for exactly this moment. It ends on five questions to settle before any code.

revised · 2026-09-25, after your links to wterm and asciinema

The first version of this brief weighed three ways for TD to hear a picture and recommended owning the read loop. It missed a fourth that TD’s own foundation review (2026-08-29) had already written down: swap alacritty_terminal for an emulator core that handles pictures, “when image support becomes a committed TD feature”. wterm is a working example of that swap — Ghostty’s emulator, embedded as a library, drawing Kitty pictures. A new section weighs it, the second question now asks loop or swap, and the first build step is a head-to-head test of the two cores rather than a spike of the loop. asciinema comes in at the video question.

The square already draws a picture

What Alt+click does now is a short pipeline, and each stage was a decision. The path under the pointer is decoded by gpui’s own image loader on a background thread. The square then takes the decoded picture out of gpui’s cache so that it holds the only copy, draws it inside the pane where the CRT glass bends it like everything else, and when it closes hands the texture back to every window’s GPU atlas (the image backend, docview/image.rs). What made that trustworthy is a soak script that opens and closes a 4096-pixel PNG a hundred times in a hidden window and reads the GPU’s memory after each close: it grew 2 MiB across 99 cycles, while a control build with the give-back removed grew 64 MiB every cycle. measured

A picture drawn by a program needs the same pipeline with a different front end. Figure 01 lays the two side by side.

So the question is the front end: what happens today when a program in a pane tries to draw.

Five programs, run against TD tonight

Four image programs ran in a hidden TD window built from tonight’s main, each in its own tab, the way you would run them by hand. mpv ran against a small stand-in terminal that answers questions exactly as TD does, since mpv has to be told to draw and cannot be asked. The stand-in also answered a second time as a TD that says yes to pictures, which is where the last two columns come from. measured

The icat hang deserves a sentence of its own, because it is a defect today whatever happens to pictures. Programs ask a terminal to describe itself with a device-attributes question, and TD answers with the shortest legal reply, ESC [ ? 6 c, inherited unchanged from alacritty_terminal, the emulator library TD is built on. icat ignores any reply that short (the check is in kitty’s detect.go), so it waits out its ten-second timeout. A longer, equally legal reply ends the wait. measured

Most programs put the picture at the cursor

Of everything in that table, the last column is what decides the work. Kitty’s protocol gives a program two ways to place a picture (figure 03). The common one sends the pixels and lets the picture land wherever the cursor is when its last byte arrives. The other, which Kitty added for tmux and friends, sends the picture once under an id and then prints ordinary characters, one per cell: a character from a private part of Unicode, coloured with the picture’s id, carrying accent marks that say which row and column of the picture belongs in that cell.

This morning’s research found the text route cheap in TD: the grid already keeps those marks on each cell, and the snapshot a window receives when it attaches already carries them. It also found that only ratatui-image uses it. Tonight’s runs confirm that and sharpen it: of the three programs the note named, ratatui-image is the only one on the text route. chafa and timg place at the cursor, and so do icat, viu and mpv. A plan built on the text route alone draws one of the three.

A picture at the cursor can become text

That seems to call for two picture systems, a cheap one for ratatui-image and an expensive one for everything else. There is a way to need only the cheap one.

When a picture arrives at the cursor, TD can write the text route’s cells into the grid itself: the private character in every cell the picture covers, the picture’s id in the colour, the row and column in the marks — exactly what ratatui-image would have printed. From that moment the picture is text, and whatever TD already does to text it does to the picture (figure 04). None of the four emulators studied this morning works this way. Ghostty pins each picture to a tracked position, kitty keeps row numbers and shifts them on every scroll, WezTerm stores a slice of the picture in every cell, and Rio keeps pictures in a side table keyed by an absolute row count, which needed a fork of the parser. inferred

The price is the one thing text cannot do, which is sit on top of other text. A program that prints words across its own picture punches a hole in it, and Kitty’s layering of pictures above or below text has no equivalent. The programs in figure 02 clear the area before they draw, so this is a hunch about rare cases rather than a measured loss. hunch

The moment it needs is inside the read loop

Writing those cells needs the cursor at the byte the picture ended, and TD cannot see that today. Every pane’s output is read by a loop that belongs to alacritty_terminal: it reads a chunk from the pseudoterminal and hands the whole chunk to the parser while holding the terminal. TD’s only seat on that loop is the tee inside the read, which copies each chunk to the window, and this morning’s cell-size fix put a small scanner there (figure 05).

This morning’s research named three ways to get that moment, and TD’s own records hold a fourth, which has a section of its own after the next. A scanner in the tee is the cheap one, and figure 05 is why it cannot place a picture. Patching the parser (the vte crate) and alacritty_terminal gives the moment by construction, at the price of carrying two forks against their releases. The third is for TD to run its own read loop in place of alacritty’s, stopping at the end of each picture. Reading the code tonight added one fact that makes the third safer than it sounds: TD’s loop would still hand every byte to the same parser, only in more pieces, and a streaming parser builds the same grid however its input is cut. A mistake in finding where a picture ends can put a picture in the wrong place; it cannot change a character of text. inferred

What owning the loop costs

alacritty’s loop runs in three places in TD: in the session host for every hosted pane, in the window for its copy of each hosted pane, and in the window again for panes the window owns outright — scratch and demo windows, and any window started with sessions turned off. All three would change together, because the host and the window have to turn the same bytes into the same cells or the grid check fires. The loop being replaced is about five hundred lines under a licence that lets TD adapt it, and seven things the current code relies on have to survive the swap: the lock held across read and parse, the tee inside that lock, one wake-up per parse, replies written exactly once, the exit flag set before the stream closes, the socket reader’s contract, and the instant the grid check samples. They are listed with their code in a modal below. measured

Owning the loop pays for more than pictures. The cell-size answer shipped today has a documented flaw: its reply can overtake the answer to an earlier question in the same read. Window-owned panes cannot hear the cell-size question at all. And the terminal-version question, which timg and yazi use to recognise a terminal, has no answer anywhere in TD. In a loop that sees the stream in order, all three become ordinary cases. measured for the flaws, inferred for the fix.

Patching the parser is the alternative, and TD already lives with patches: it carries six against gpui, applied by a script at a pinned revision, with a ledger of why each exists. This one is heavier because a parser callback alone does not reach the cells. alacritty_terminal would need a second patch to write them mid-parse, and both would be rebased against every release. Comments in three files also record a standing choice to keep the emulator stock. Figure 06 shows where the loop sits, and what it would carry once pictures arrive.

Or swap the emulator core

Owning the loop and patching the parser both keep alacritty_terminal and make TD the author of Kitty’s protocol. The other way to have the cursor at the right moment is to use an emulator core that already handles pictures, so the moment belongs to someone else’s code.

TD wrote this option down a month ago. The foundation review of 2026-08-29 scored an alternative to each of TD’s dependencies, and for the emulator it listed swapping alacritty_terminal for rio-vt or libghostty-vt, with the verdict “zero product win today” and a trigger: “when image support becomes a committed TD feature”. Pictures that programs draw are that feature. measured

Both candidates have moved since. rio-vt, the core extracted from the Rio terminal (itself descended from Alacritty), has had 26 releases on crates.io in two months, the latest on 2026-09-17; it is MIT and carries Kitty, Sixel and iTerm2 pictures. libghostty-vt is Ghostty’s emulator as a library, MIT or Apache, with Rust bindings at 0.2.1 whose own documentation says the API is not yet stable, and it builds from source with a Zig toolchain this machine does not have. wterm, the browser terminal you linked, is the working example: Vercel Labs compiled libghostty 1.3.1 to WebAssembly and draws Kitty pictures with it, pinned to their text through scrollback and resize. It stops short of the text route and caps pictures at 32 MiB a screen. measured from the projects’ own pages.

What a swap costs can be counted. Seven of TD’s files import alacritty_terminal: the read path (host.rs, term.rs, socketpty.rs), the attach snapshot and grid check (gridwire.rs, written against alacritty’s cells and flags), and the renderer, where pane.rs reads the grid in 51 places. The foundation review called the emulator TD’s contained seam, and by file count it is; by depth it reaches the snapshot, which is what lets a window re-attach to its host. measured

The two roads also meet. On the GUI-in-the-TUI brief you asked that the part of the HTML engine most likely to be the wrong call sit behind an interface you can unplug, and wterm’s cores are that pattern applied to the emulator: one terminal component, two interchangeable engines behind it. TD’s own read loop is where such a seam would go, since the loop is what hands bytes to whichever core parses them, so owning the loop is the first step of a swap as well as the alternative to one. inferred

Which road is cheaper is a question tonight’s recordings can answer before anyone rewrites anything. The stand-in terminal already captured what icat, viu, chafa, ratatui-image and mpv send. Recorded again with the raw bytes kept, those streams can be fed to rio-vt and to libghostty-vt in a small program that reports what each stored and where it put it, and set beside the count above. That turns the second question below from a judgement into a measurement. hunch that it takes about a day.

What pictures cost once they arrive

Whichever road gets TD the cursor, the remaining costs are the ones every emulator with pictures pays, plus one that TD’s split into a host and a window adds.

Video is where the bytes get large. mpv at a 1200×675 pane sends each frame as 3.24 MB of text-encoded pixels, about 97 MB a second at 30 frames. Tonight’s probe fed a hidden TD window the same frames — which TD still throws away — and timed how fast the pane took them in (figure 08).

mpv can also send each frame through shared memory, which shrinks a frame in the stream to a 32-byte name. Only the process reading the pseudoterminal can open that memory, and in TD that is the host, so the host would forward the pixels to the window over the socket anyway. The same holds for pictures sent as file paths, which is how icat sends a PNG it finds on disk: the host reads the file, and for a temporary file deletes it, before the window could. measured for the bytes, inferred for the forwarding.

Kitty caps stored pictures at 320 MB per screen and evicts the ones nobody can see first. Applied per pane in a window of twenty panes, that ceiling is 12.8 GB, so TD needs one budget for the whole window. wterm, living inside a browser tab, settled on a tenth of kitty’s number: 32 MiB a screen. A cell whose picture has been evicted should draw as a hatch that says so, since an empty cell reads as a picture that happens to be blank.

Two things come from the renderer. Pictures bend with the CRT glass for free, because they draw in the same part of the pane the text does, which is what you chose for documents this morning; a warped tube is drawn 35% brighter so it does not look dim beside flat panes, and a photograph may look washed out under it. inferred And each row is drawn as one run of shaped text, so the private character has to print as a space: a font that drew it as a box of another width would slide every column to its right. The picture then lies over the cells as its own element, clipped to its rectangle. measured

The first build

Everything so far describes what has to exist. The order to build it in comes from asking which choice would cost the most to reverse, and the answer is the road: loop or core, every byte of every pane goes through it.

So the road is chosen first, by the head-to-head test, and nothing draws until it is. One small change comes even before that, because it ends icat’s ten-second hang today and needs none of the rest: telling programs what TD is. After the road, the first picture is ratatui-image’s, since it needs the store and the painter but not the cursor, and then everything that places at the cursor.

Five questions before any code

Five of the choices in that plan are yours rather than the code’s. Each carries my recommendation; a concur is enough where you agree.

1 · Which program draws first?

ratatui-image uses the text route, so it needs the store, the painter and the query answer but not the cursor. chafa and timg need all of that and the cursor too. The first slice should cross every risky part once.

Recommendation: ratatui-image, built on whichever road question 2 picks rather than on the tee scanner, so the cursor programs are one step away instead of a second design.

2 · Own the read loop, or swap the emulator core?

Owning the loop keeps alacritty_terminal, makes TD the author of Kitty’s protocol and turns pictures into text. Swapping to rio-vt or libghostty-vt gets a maintained implementation, and with libghostty-vt pictures that can share cells with text, and moves the seven files that read alacritty’s grid onto a two-month-old crate or an unstable API. TD’s foundation review named the swap as the move for exactly this moment. Patching the parser stays the least attractive of the three.

Recommendation: decide it by the head-to-head test, not by argument: tonight’s recorded programs fed to both cores, and TD’s alacritty surface counted beside the result. If neither core places all five programs correctly, own the loop.

3 · Tell programs what TD is?

Three changes, none of them about pictures: a device-attributes reply icat recognises, an answer to the version question, and TERM_PROGRAM=terminal-delight. Then ask chafa and yazi to add TD to the tables they recognise terminals by. Pretending to be kitty would make chafa place pictures before TD can draw them.

Recommendation: yes, and ship it first, on its own. Until pictures exist icat then says at once that TD cannot draw, instead of hanging for ten seconds.

4 · One picture budget for the whole window?

kitty’s 320 MB is per screen, and every pane in a TD window shares one GPU.

Recommendation: one budget per window, starting at kitty’s 320 MB my number, evicting what is off-screen first, with an evicted picture drawn as a labelled hatch.

5 · Video now, or later?

Your note on the morning brief put video from agents in the future. The pipe already carries mpv-style video; decoding thirty frames a second and forwarding shared memory from host to window are the new parts. A terminal agent has a cheaper kind of video, though: a recording of its terminal. asciinema’s format stores what a program printed and when, as text rather than pixels. TD’s host already sees every byte a pane prints, so it could write one, and TD could replay one in the floating square with its own emulator — pictures included once TD draws them, which asciinema’s web player, going by its documentation, does not.

Recommendation: mpv-style video later, but the store replaces a picture in place from the first build, because mpv sends every frame without an id and never deletes one. asciinema recordings are a separate, smaller track — a new kind of document for the floating square — and not part of this one.

Four ways to hear a picture

and one that was rejected

A scanner in the tee

Where the cell-size answer lives today. It can do everything that does not need the cursor: store a picture, answer a query, delete by id, and serve the text route. It draws ratatui-image and nothing else in figure 02. No fork.

TD’s own read loop

Replace alacritty_terminal’s event loop (event_loop.rs, Apache-2.0, about 500 lines) with one that stops at the end of each picture, parses up to there, and acts with the terminal locked. Inside a synchronized update the parser holds text back; the loop flushes it first (Processor::stop_sync is public) so the picture lands after the text it follows. No fork; three call sites and seven invariants.

Patch vte and alacritty_terminal

Rio’s road: a picture callback in the parser, and a terminal that writes the cells when it fires. vte’s maintainer declined such a callback upstream (“I’m very hesitant to accept this sort of ‘second rate escape sequence’”, alacritty/vte#115), and alacritty’s own graphics pull request has been open since 2021. Two forks, rebased against every release.

Swap the emulator core

Replace alacritty_terminal with a core that implements pictures: rio-vt (crates.io 0.5.28, 2026-09-17, MIT; “Embeddable terminal core extracted from Rio: VT state machine, grid, PTY driver, selection, search”; 26 releases since 2026-07-26; Kitty, Sixel and iTerm2) or libghostty-vt (Rust bindings 0.2.1, 2026-07-18, MIT or Apache-2.0; “the API is not yet stable”; libghostty-vt-sys “fetches and builds libghostty-vt.a from ghostty sources via Zig by default”). TD’s foundation review (docs/2026-08-29-foundation-interrogation-zed-gpui-quickshell.md, option F) sets the trigger: “If alacritty_terminal stalls, or when image support becomes a committed TD feature”.

wterm (Vercel Labs, Apache-2.0) is the evidence that libghostty embeds with pictures working: its @wterm/ghostty core compiles libghostty 1.3.1 to WebAssembly (about 580 KB) with patches for the browser’s allocator, and renders “direct Kitty Graphics Protocol PNG, RGB, and RGBA data” as “bounded, transient canvas overlays for pinned placements”. It leaves out Sixel, iTerm2, animation and “virtual Unicode placements”, and caps storage at 32 MiB a screen with at most 4,096 images and 4,096 placements. Its default core is a 26 KB Zig one that swallows Kitty sequences without drawing them — one component, two engines behind it.

TD’s side of a swap, counted with grep at 81ec545: seven files import alacritty_terminal (gridwire.rs 19 references, term.rs 18, socketpty.rs 12, host.rs 8, main.rs 3, pane.rs 3, pane/bench.rs 1), and pane.rs reads the grid, its cells or their flags in 51 places.

Rejected: rewrite the stream in the tee

Swap a cursor picture for the bytes that would print its cells. The tee knows neither the column, so it cannot stop at the right margin, nor the program’s current colours, so it cannot restore them afterwards; saving them with the terminal’s save-cursor sequence would overwrite the one slot the program itself may be using.

Seven things the loop must keep

what TD’s code relies on alacritty’s loop for

  • The lease across read and parse. Attaching a window and the grid check both wait on it, and take the lock unfairly because the fair lock would deadlock against a held lease (host.rs:18-23, :876-895; socketpty.rs:101-104).
  • The tee inside the lease. “Tee somewhere else and the ordering guarantee evaporates” (host.rs:129-133).
  • One wake-up per parse. The window’s redraw counts generations (term.rs:90-94, :330-333).
  • Replies written exactly once, by the host, through the input queue; the replica swallows its own (host.rs:739-754; term.rs:58-72, :98-105).
  • The exit flag before the stream closes (host.rs:755-771).
  • The socket reader’s contract: tokens copied from alacritty and a manufactured hang-up (socketpty.rs:16-21, :40-50, :236-241).
  • One instant for the grid check: its byte offset and hash describe the same moment (host.rs:930-943).

Also inherited from alacritty’s loop, and to be kept or replaced on purpose: the synchronized-update timeout, the cap on how long one lock is held, and the 1 MiB read buffer (event_loop.rs:24, :27, :229-247).

Two comments in the code are out of date and worth fixing whenever this is touched: host.rs:59-61 says the reader thread is shared by every pane (each loop has its own), and socketpty.rs:23-29 says nothing constructs a socket reader yet (term.rs:307 does).

A program can name a file

and the terminal opens it

Kitty’s protocol lets a program send a picture as a path instead of pixels, and icat does exactly that for every local PNG. The terminal opens the path with your permissions. Kitty’s own rules: refuse anything that is not a regular file, and delete a “temporary” file only if it sits in a known temporary directory and its name contains tty-graphics-protocol. measured from the protocol document.

Over ssh the program runs on another machine but the path is read on this one, and a query about a path answers whether it exists and holds a picture. That leaks little, but it is not nothing. hunch

Proposed: follow Kitty’s rules, refuse /proc, /sys and /dev, and decide at Gate 2 whether a pane whose foreground program is ssh accepts file and shared-memory pictures at all.

Method and limits

what was run, and what was not

How it was done

A read-only agent mapped TD’s code at 81ec545 against eight questions, with a line reference for every claim; the load-bearing ones (alacritty’s ?6c, the scanner, the soak) were checked by hand. Programs came from their own releases, none installed system-wide: kitty’s static kitten binary, chafa unpacked from the Arch package, viu built with cargo, and ratatui-image in a 25-line program that draws one picture full-screen. mpv is the system’s.

What was run

  • Each program under the stand-in terminal three ways: as TD answers today, as a TD that says yes to pictures, and as kitty.
  • icat, ratatui-image, viu and chafa in a hidden TD window of the installed build (spikes/tdrun.sh), launched with the soak script’s recipe: its own session, a special workspace, never focused.
  • The throughput probe (spikes/apcprobe.sh): 40 or 200 frames of 1200×675 raw pixels in mpv’s own framing, and the same number of bytes as plain text, in a hosted pane and in a window-owned one. A re-attach opens a new socket, and TD logs nothing when it drops a slow window, so the probe compares the window’s sockets before and after each run. The first hosted run did not yet do this; in the two that did, no socket changed.

Limits

  • Throughput runs are single runs on a machine with about twenty agent panes open; the two window-owned runs differ by more than a factor of two.
  • No picture was decoded, stored or drawn by TD. The cost of decoding and uploading frames is unknown.
