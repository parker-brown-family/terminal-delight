Two instances, one identity

terminal-delight · 2026-09-16 · measured on the live desk, workspace 1 and workspace 6

The two Terminal Delights are not sharing a backend. They are two hosts, two windows and four different binaries, all writing into one flat runtime directory where nothing carries an instance name. Every agent reaches its window through a single environment variable, and every answer that comes back is identical in shape whether it came from the right instance or the wrong one.

measuredNothing is shared between the instances except a directory

Workspace 1 is serve --session 1 (pid 876777) behind window 545381. Workspace 6 is serve --session tdclip (pid 714673) behind window 1549490. Separate sockets, separate session files, separate panes. What they do share is the runtime directory they both write into, where every lookup is by a bare pid or a bare session name — which is enough on its own to produce the symptoms a shared backend would.

measuredThe mechanism that finds an agent's window no longer works, and one environment variable is carrying the whole feature

owning_td() walks the process tree for an ancestor that owns a control socket. Under the host split the window is a sibling of every pane, never an ancestor, so that walk now ends at systemd every time. What remains is $TD_SESSION → a best-effort file → a socket path.

measuredA wrong-instance answer is byte-identical to a right one

Run from a workspace-6 pane with TD_SESSION=1, the relay returned workspace 1's twenty-two panes, exit 0, nothing on stderr. Neither initialize nor list_panes carries a session, a window pid or a build. There is no field to check, so there is no way for an agent — or for you reading its output — to notice.

measuredThe rail's blindness to hosted agents is probably an install, not a design fault

Neither running instance carries reconcile_modes. The fix whose issue title is “12 running agents are invisible to the attention rail” merged this morning and is in none of the three installed binaries. That is cheap to test and cheap to fix, and it should be ruled out before any of the work below is approved.

Slices

do this first

A · The answer says who answered

initialize and every tool result that names a pane carry the instance: session id, window pid, and the build the window is running. list_panes gains pane_id beside pid.

No behaviour change, no resolution change, and it makes every other claim in this brief checkable from inside an agent turn. Its cost: a few bytes on every response, and a field that is cheap to add and expensive to withdraw — which is the reason to settle its shape before writing it, not after.

B · The caller names itself

The relay forwards its own TD_SESSION and TD_PANE_ID on the ctl line. A whoami answer; pid becomes optional on declare_deliverable and leave_note, defaulting to the calling pane.

This is the attention-spine fix proper: a turn's deliverable lands on the pane that declared it by construction. Better at: removing a whole class of wrong-pane writes. Worse at: nothing, except that it needs A's field to be worth reporting.

C · Resolution asks an authority

Walk the ancestry to the host, ask it which window is attached. HostProbe::Live gains the window pid. discover() filters on liveness and the two false sentences in its refusal are corrected. $TD_SESSION becomes a hint that is cross-checked, not the road.

The only slice that fixes the two dead Codex relays, and the one that makes the feature independent of the environment. Better at: working when there is no environment to read. Worse at: it is the largest, and it touches the host protocol, so it needs a version bump to land safely.

D · The wire admits it has versions

One integer on the ctl hello, with the host protocol's existing refusal shape: a window from a build this relay does not speak to is named as skew, not treated as broken.

Smallest of the four and the easiest to defer. Better at: turning today's three-build call path into something that reports itself. Worse at: it buys nothing until builds actually diverge in the ctl protocol, which they have not yet.

Decisions that are yours

1 · Does session 1's host get restarted to pick up the rail fix?

The mode-reconciliation fix touches host.rs, so a window cutover will not carry it. Getting it into workspace 1 means restarting serve --session 1, which ends every terminal in that session — twenty-two panes and roughly twenty agents.

Recommendation: cut over workspace 6 first, where three panes are at risk, and see whether the rail's behaviour changes there. If it does, you have an answer about the cost without paying it, and the session-1 restart becomes a scheduling question rather than an experiment.

2 · Is a cross-instance call labelled, or refused?

An agent in workspace 6 can read workspace 1 today, and that is genuinely useful — it is how you look at the other half of the desk without a screenshot. It can also write there, with the same silence.

Recommendation: reads stay allowed and become labelled; writes to a pane in another instance require naming that instance explicitly. A note landing on a stranger's glass should take a deliberate act, not an inherited variable.

3 · Does an absent pid mean “me”, or stay an error?

Making it default is the whole of slice B's value. Keeping it required is more explicit and keeps every call auditable from its arguments alone.

Recommendation: default to the caller. The current requirement does not buy explicitness — it buys a guess, because the agent has no reliable way to compute the right number.

4 · How much of this is worth doing before the spine is used in anger again?

A alone makes the problem visible. A + B makes the spine correct for the common case. A + B + C makes it correct without an environment. D is insurance against a skew that has not bitten yet.

Recommendation: A and B now as one change, C next as its own with a host protocol bump, D parked behind a falsifiable issue. That is one approval, not four.

Method and limits

what was tested, and what was not

Everything here is observation, not repair

Nothing was built, no file in the repository was changed, and no window was restarted. The three probes in figure 07 each sent one list_panes line through a relay started by hand and then exited. No write verb was called against either instance.

One deliberate gap

The cross-instance write is inferred, not measured. declare_deliverable and leave_note take a pid and route through the same apply pipeline as the read that was measured, so a write to a pid the resolved window knows will land there — but demonstrating it means putting a note on somebody's pane in the other workspace, and that is not a thing to do to prove a point. Treat “a write lands on a stranger’s pane” as inferred and the read behaviour as measured.

What the build skew does not explain

All three installed binaries carry declare_deliverable, so the spine verb is present everywhere and the skew is not why it is hard to use. The skew explains one separate thing — hosted agents' modes not reaching the rail — and that is the reason read-first item one exists.

Not established

Whether the symptom you noticed is the identity defect, the missing install, or both. They produce overlapping surfaces: an agent whose relay answered for the wrong window and an agent the rail cannot classify both read, from the rail, as a pane that is not doing what it should.

How to prove this wrong

run these first, before changing anything

The identity defect

Confirms it: from a pane in one instance, start a relay with the other instance's TD_SESSION and send one list_panes. If it answers with the other window's panes and exit 0, the defect is real.

Invalidates it: if the relay refuses a session whose window is not the one hosting the caller, or if any field in the response names the instance, this is already solved and the brief is stale — close it.

The dead Codex relays

Confirms it: tr '\0' '\n' < /proc/<relay>/environ | grep TD_SESSION on relays 883316 and 883790 returns nothing, while their parent Codex has it.

Invalidates it: if those relays answer a list_panes correctly, the fallback is finding the window some other way and the third tier is not load-bearing — close it.

The install skew

Confirms it: strings -a <binary> | grep reconcile_modes returns nothing for all three installed builds.

Invalidates it: if the rail behaves identically after a rebuild and cutover, the missing fix was not the symptom, and read-first item one drops to a footnote.

The ancestry claim the repair rests on

Confirms it: walk /proc/<relay>/stat upward in any hosted pane and find the serve --session process on the chain.

Invalidates it: find one hosted pane whose relay does not have its host as an ancestor — a pane adopted from another process, or anything under tmux. If that case is common, slice C is the wrong shape and the environment variable has to be repaired instead of replaced.
