The verdict

measuredThe bench keeps every key it cannot use, and the rename box is below it

TerminalView::on_key (app/src/pane.rs:4481) is the pane's only key handler. It calls bench_key at line 4662; every path out of that function ends in cx.stop_propagation(), so on the workbench face nothing below line 4662 ever runs. The inline rename box is handled at line 4729.

Invalidate: press Esc on the open box with the bench showing. It should cancel the rename. If it does not, the key never reaches on_key at all and this whole reading is wrong — the problem would then be focus, and none of the three options apply.

measuredThe keystrokes go somewhere, and it is the agent

A printable key on a reading bench resolves to Reading::Talk: the composer opens carrying that character and the byte is written to the pseudoterminal. So typing a pane name on an agent pane starts a message to the agent. On a pane with no agent the same key is swallowed and nothing happens.

Invalidate: if typing into the box leaves the bench's composer empty on an agent pane, bench_key is not being reached and the trace is wrong.

measuredThis is the unfinished half of an issue that is still open

Issue 524 — the workbench face swallows every one of the window's alt chords — was answered with workbench::window_chord, a table the bench consults before it can swallow, plus a structural guard. That fixed the window's chords. The pane's own chords and its two text fields never got the same treatment, and they are what is dead now.

Invalidate: press ctrl+shift+b on a bench pane. If the left bar toggles, the pane's chords are reaching the workspace some other way and only the rename box is broken.

Read first

  1. Escape is the discriminator — press it before anything else

    Escape already cancels the rename on the bench face, because keylayer::escape_target ranks the rename box above the bench. Everything in this brief follows from escape working and the letters not. One keystroke, ten seconds, and it decides whether the rest is worth reading.

  2. Twenty-one of twenty-seven chords are swallowed there, not one

    ctrl+w, ctrl+f, ctrl+c, every ctrl+shift+… panel, the scrollback keys, alt+s for a sticky note. The rename box is the one you happened to reach for. Fixing only it leaves nineteen.

  3. The precedence already exists, as a value, tested over all 128 combinations

    app/src/keylayer.rs says the rename box outranks the bench and proves it. Only escape consults it. Every other key is ordered by which if was written first, which is the failure mode that module was written to end.

  4. The recommended fix adds no new rule, it reuses the one that is there

    The bench already declines the window's chords before it can swallow one. The change teaches it to decline the pane's chords and its text fields the same way. Nothing is reordered, so nothing that works today can break.

  5. Issue 524's "done when" is already satisfied — it can be closed as this lands

    Its five acceptance bullets are all met by the shipped window_chord work. Leaving it open makes the remaining half invisible: the rollup shows one ticket that looks half-fixed rather than one fixed and one filed.

What you see

Why it happens

The pane stacks surfaces — paint across every pane, a context tray, the header's menu and rename box, the FOCUS reader, a sticky note, and under all of it either a terminal or a workbench. One handler decides which of them gets a key. For escape, that decision is a table in keylayer.rs. For every other key it is the order the if statements happen to be written in.

How far it goes

ctrl+c, on the bench

ctrl+c does not reach an agent from its own workbench. In reading mode it resolves to Reading::Ignore and is dropped. workbench.rs's own doc comment says the opposite — "ctrl+c must reach a running agent. A bench that refused it would take away the only way to interrupt a turn" — and it is describing why the chord is kept off the decline list, which is true and not sufficient. Invalidate: start a long turn, flip to the bench, press ctrl+c. If the turn stops, this reading is wrong.

Three ways to cut it

narrow

A · One more table, text fields only

Add typing_owner beside escape_target in keylayer.rs: the topmost surface that owns characters, which is a shorter ladder than escape's because menus want escape and no letters. bench_key declines when the answer is not the bench.

Fixes exactly what you hit, plus the sticky note's composer. The precedence stays one value, and the new ladder can be asserted to agree with the escape ladder wherever both name a surface.

Leaves nineteen chords dead, including ctrl+c. You would be back here.

~55 lines · keylayer.rs, bench.rs, pane.rs

recommended

B · A, plus the pane's own chord list

Everything in A, and a pane_chord table sitting beside the existing window_chord one: the chords the pane owns, declined before the bench can swallow them, exactly as the window's already are.

It adds no new mechanism — the bench has declined a class of chords since issue 524, and this is a second class through the same door. Nothing is reordered, so no key that works today can change. Twenty-one of the twenty-seven come back.

Two lists that can drift: a chord added to on_key later and not to the table stays dead. Needs a scan test, and alt+backspace has to stay off the list because the composer uses it for kill-word.

~110 lines · three files, all additive

structural

C · Cut on_key into chrome and content

Sort the handler into the half that is true on both faces — the pane's chords, its text fields, the reader — and the half that belongs to whichever face is showing. The bench rung moves to the seam, and the terminal's own guards move with it.

The only version where a chord added later is right by construction rather than by remembering to add it to a list. It is where B ends up if this keeps happening.

It reorders a 480-line handler on the hottest path in the app. The exited-pane guard at 4757 currently sits above those chords, so a dead pane's bench is one of the cases whose behaviour changes and nobody has decided what it should be.

~300 lines moved · behaviour change across ~30 keys

B, because it buys nineteen chords back for fifty lines more than A and cannot break anything that works, and because C is the same change with the risk front-loaded — it is worth doing when the list has drifted once and not before. If you only want your rename box, A is the small version; say so and it ships today.

The three functions that decide a key's fate on a reading bench — window_chord, types_a_character and reading_key — were cut out of app/src/workbench.rs by line range, compiled standalone, and driven over the chord list. The bodies are the repository's, byte for byte, not retyped.

Issue 524

the workbench face swallows every one of the window's alt chords

What it asked for

Five acceptance bullets: one pure, table-tested answer to "is this chord the window's?"; both bench_key exits consulting it; printable never true for a modified keystroke; a test that fails when a new stop_propagation skips the table; and alt+w, alt+r, alt+v, alt+h and the arrows behaving the same on both faces.

What shipped

workbench::window_chord, consulted at the top of bench_key above the gallery; types_a_character refusing alt, control and platform; the_bench_declines_a_window_chord_before_it_can_swallow_one asserting the decline sits above the first stop_propagation, comments stripped first, mutation-tested both ways. All five are met. The issue's own invalidation criterion — "bench_key already consults a list of window-owned chords and returns false for them, then this is fixed and the issue is stale" — has fired.

What it did not cover, and could not have

It was written about the window's chords, and the fix is scoped to them: window_chord answers true only for alt and ctrl+alt forms. The pane's own chords are ctrl and ctrl+shift, so they fall straight past it, and the pane's two text fields are not chords at all. 524 is one class narrower than the problem, and nothing in it is wrong.

The focus-handle fix

option D

What it would be

The workspace's own editors — the tab rename, the group rename, the left bar's branch rename, the find box — do not fight for order inside another handler. They take the keyboard: the workspace root focuses itself, and overlay_owns_keyboard() lists every surface that legitimately holds it. The pane's rename box is the odd one out. It sets renaming = Some(..), focuses the pane, and relies on being reached by a branch a hundred lines further down.

Giving it its own focus handle and the shared EditBuffer would end the ordering question outright, and would also close issue 376 — the pane header being the only rename box with no caret, no selection and no word navigation.

Why it is not the recommendation

Focus on this window is watched. Every workspace render calls plan_focus (main.rs:21823) and, unless an overlay owns the keyboard, defers a restore back to the active pane. overlay_owns_keyboard enumerates workspace state; a pane's own rename buffer is not in it and cannot be without the workspace reaching into the focused pane every frame.

The race is documented rather than theoretical. open_find carries this line: "Deferred focus dodges the focus-back race the rename editors hit (the pane's own focus would otherwise grab it back)." Somebody has already been bitten moving focus off a pane, and the workaround was a deferred focus call.

So D is a real improvement that lands on the focus system, fixes a second issue, and wants its own brief. It is not the cheapest route to typing a name.

The guard

what has to fail before the fix is believable

Three tests, and what each one is for

The table, in keylayer.rs. That module imports nothing and compiles standalone, so its tests run in about a second and mutating the table is cheap enough to actually do. typing_owner gets the same treatment escape_target already has: every flag alone, the exhaustive sweep over every combination, and the pairwise probe that catches two adjacent rows being swapped.

The two ladders agree. A test asserting that the typing ladder is a subsequence of the escape ladder — wherever both name a surface, they name it in the same order. This is the one that prevents the next drift, because the two are allowed to differ in membership and never in order.

The decline sits above the swallow. The structural scan that already guards window_chord, extended to the new call. Comments stripped before the scan — the first draft of the existing one failed on its own doc comment, which described the call it was looking for.

The mutations it has to fail

  • Move the new decline below the gallery block. The scan must go red.
  • Delete the decline outright. The scan must go red.
  • Swap Rename and Bench in the typing ladder. The pairwise probe must go red — not just the exhaustive one, which passes a swap of adjacent rows when only one flag is raised at a time.
  • Return Bench unconditionally from typing_owner. Everything must go red.

A guard nobody has watched fail is a guard nobody should trust. Each of these gets run and the result named in the commit.

And the behavioural check

The tables are pure and the wiring is not. Before the commit closes: right-click a pane title on the workbench face, type a name, press enter, and read it back off the header. Then ctrl+shift+b from the same face.
