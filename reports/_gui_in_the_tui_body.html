GUI in the TUI

An agent in a Terminal Delight pane finishes a brief and prints its path. You Ctrl+click it, Hyprland tiles a Chromium window beside the terminal, and the document is now in a different window from the agent that wrote it. The idea on the table is to keep it where the work is: open the file in a new split in the same tab, or as a square floating over the pane that you can drag out of the way — Markdown, HTML briefs, images. Most of that is already on disk. TD draws images today, and a Markdown renderer built on the same GPU framework sits in markdown-delight. What is missing is the other half of the pictures you sent — programs inside the terminal drawing their own pixels, the way the Pokémon dashboard draws its Game Boy screen — because the part of TD that reads program output throws those bytes away. This brief lays out both halves and what each costs, and closes on five decisions. The recommendation is a floating square for images and Markdown first.

A Ctrl+click on a path leaves the terminal

Every way of opening something from TD ends in the same place. Ctrl+click or Shift+click on a path in terminal output, the right-click “Open link” item, an artifact on the workbench and a deliverable on the attention rail all call one function, which hands the path to xdg-open — through uwsm-app on Omarchy, so the new window belongs to the desktop rather than to the pane (the function is open_with_system in pane.rs). measured What opens next is decided by the desktop’s file-type table.

It was a choice, and three of TD’s own documents record it: the surface protocol (“The window never hard-wires a viewer”), the attention-spine plan (“The desktop opens it, not the terminal”), and a comment in the file that defines what a person can do to a work object, surface.rs:

Open it with the desktop’s own handler. Never our own viewer: the person already told their machine where Markdown goes.

So the first thing this feature does is reverse a written rule, and it should do that on purpose. The reason to reverse it is in the two pictures that started this, and they turn out to be asking for two different things.

The picture you pointed at is two different machines

The first picture is artwork: a retro monitor showing a text-mode dashboard with a Windows 95 settings dialog sitting inside it. The second is Boyd’s dashboard from the week Jev beat Pokémon Blue — a terminal layout of panels for the trainer, the goal, the battle and Jev’s running cost, with the live Game Boy screen drawn in real pixels on the left. They look like one idea. Underneath there are two unrelated mechanisms, and TD has to build them separately.

In the first mechanism, TD draws the thing itself. TD is a terminal emulator — a window drawn with gpui, the GPU framework Zed is built on — and anything gpui can draw, a pane can hold: an image, rendered Markdown, a panel with a title bar. Your Ctrl+click idea lives entirely on this side. TD opens the file and paints it, and no escape sequence is involved.

In the second, a program running inside the pane draws it, by writing escape sequences into its output that mean “put these pixels here”. Three such protocols are in use — Kitty’s, Sixel and iTerm2’s — and a terminal shows the pixels only if it implements them. That is how a Game Boy screen gets into a terminal layout, how the file manager yazi previews images, and how mpv plays video in a terminal.

the pasted framing, in one paragraph

The summary pasted into this research described TD as a text UI running inside Foot or Ghostty, probing them for Kitty or Sixel support, built on types called SurfaceHost and TubeTarget over Ratatui. None of those types exist in the repository, TD does not use Ratatui, and TD is the terminal — so the protocol question is which ones TD implements for the programs running inside it. contradicted Its instinct to start with a still image was sound, and survives below. Programs cannot draw pixels in TD today, because the parser drops them

The second lane is dark for a reason that sits in TD’s shape. TD runs as two processes. A session host owns the pseudo-terminals, so shells and agents survive the window closing; it copies every byte it reads to the window, which parses the same bytes again into its own replica of the grid and draws it. Both sides parse with alacritty_terminal, the terminal library from the Alacritty project, taken unmodified from crates.io.

Inside alacritty_terminal sits a parser called vte, and vte is where graphics end. A Kitty image arrives as an APC sequence, and vte has no callback for APC at all: it reads the bytes and discards them one at a time. A Sixel image arrives as a DCS sequence, which does reach a handler, and the handler logs it at debug level and drops it. When a program asks for the cell size in pixels, nothing answers; when it asks what the terminal supports, TD’s reply leaves Sixel out. measured

Upstream will not change this. vte’s maintainers closed every pull request that added APC, one of them with “I’m very hesitant to accept this sort of ‘second rate escape sequence’”, and Alacritty’s own graphics pull request has been open since 2021 with its maintainer writing that it “has little chance of ever getting upstreamed”. Zed, built on the same library, closed its request for terminal graphics as not planned, and on the day this research ran Alacritty’s maintainer declined again, writing that GUIs in a terminal are “actively working to make terminals and terminal applications worse”. measured TD’s June review of competitors had already filed image protocols under “defer, but flag as a future moat”, sized extra-large.

So the meme’s half is expensive and was deferred on purpose. The half you asked for costs far less.

Images need nothing beyond a view to hold them. measured Markdown needs markdown-delight’s renderer, lifted into TD rather than shared, because the two apps build against two separate copies of Zed on disk and a shared crate would have to reconcile them. The lift needs three changes: a palette parameter (its colours are hard-coded to its green theme), link targets (it keeps a link’s text and throws the address away), and drawn images. measured Zed’s own Markdown crates are not an option — they are GPL and pull in 53 to 94 other Zed crates. An earlier TD plan chose a different Markdown parser and new elements written from scratch; the lift reuses elements already written and debugged in markdown-delight.

The renderer would have a second customer the day it lands. The workbench’s markdown surface kind draws its body as plain lines today, so an agent’s ## Heading shows up with its hash marks. measured

With the drawing solved, the design question is where the document appears, and what a split is allowed to hold decides it.

A floating square is cheaper than a split, because a split can only hold a terminal

TD’s tiling is a binary tree per tab whose leaves are terminal views. Every leaf owns a live terminal session, the saved layout stores each leaf as a recipe for starting a shell, and new splits stop at four panes. A pane that holds a document and no terminal would change what a leaf is, and with it every place the window walks the tree — sixty-three of them in the window’s main file alone. measured

There is a cheaper route to a split. Every pane already has two faces, the terminal and the workbench, chosen by one branch in the pane’s render. A third face — the document — gives a split that shows a file, at the price of a shell idling behind it and one of the tab’s four pane slots. inferred

The floating square is cheaper still. It is a child of the pane’s screen, drawn after the grid and before the glass — the layer the sticky note uses — so it needs no layout change at all. The sticky note looks like the model to copy for dragging, but it cannot be dragged; its position is computed from the pane’s size. The drag to copy is the window’s pane-drag state, which records a start point and engages only past a threshold. measured

Both shapes have to settle one thing about the glass. TD’s CRT curvature is a post-pass over each pane’s screen rectangle, and the first rectangle that contains a pixel wins, so anything painted inside a pane bends with it — a document included. The sticky note looks flat because its paths and glyphs are pre-warped; an image cannot be, because gpui’s image sprite carries no transform. measured A document therefore either bends with the tube and routes its clicks through the inverse map, the way the workbench already does, or it needs a flat rectangle registered in front of the pane’s. That second option is exactly what the open issue “Exempt only an overlay’s own rectangle from the CRT warp” asks for.

Images and Markdown are native and cheap. The HTML brief, the format agents here hand back for anything that needs a decision, is neither.

HTML is where it stops being cheap

A brief like this one is a web page: CSS grid, inline SVG, and a notes system written in JavaScript that tags every figure, opens a dialog and saves your notes into the file. gpui has no web engine, and on Linux it cannot show a texture it did not upload itself, so any foreign renderer reaches a pane as pixels copied through the CPU. measured Four routes were tried or read.

The question Servo leaves open is whether a current Servo lays out and runs your briefs well enough to embed at all, and it is cheap to settle before any TD code exists: rebuild Servo at upstream main, screenshot the 118 HTML reports under ~/Work/reports and TD’s reports/ in both Servo and Chromium at the same size, and compare. Ninety-one of them carry the notes system. If a large share break, the live rung becomes headless Chromium streamed over its DevTools protocol, or nothing. A working demo of Servo inside a gpui window already exists, in a project called wgpu-graft; the way it polls every frame and never frees old ones are the parts a TD version would replace. The measurements are in the modal Servo in a pane, measured.

That settles the half you asked for. The meme’s half — programs drawing into TD — looked extra-large in June, and one part of it is not.

Programs can draw into TD without a fork, through one trick of Kitty’s

Kitty’s protocol has a mode built for multiplexers like tmux, and it fits TD’s host-and-window shape closely. The program sends the image once, tagged with an id. Then it prints text: a private-use character, U+10EEEE, in every cell the image should cover. The character’s colour carries the image id, its underline colour carries the placement, and two combining marks after it give the row and column of the slice. The terminal draws that slice in place of the character.

That is the part that fits TD. The grid already stores these cells without loss, and the attach snapshot the host sends the window already re-emits the combining marks and underline colours. measured Sending an image, placing it by id, deleting it and answering the support query do not depend on where the cursor is, so a scanner reading the byte stream can handle all four without touching alacritty. TD already has two seats for one: the host’s tee, which copies every read, and the window’s byte counter. inferred

Two fixes ride along, and both are needed whatever else happens. TD tells programs its cells are 6 by 14 pixels, which is the logical size with the fraction cut off; this monitor runs at 1.6×, so a program sizing an image from that draws it at about sixty percent of the screen’s real resolution. And TD should answer the terminal-identity query, XTVERSION, so yazi can recognise it and choose placeholders. measured

Placeholders reach fewer programs than the trick deserves, though, and the rest need something harder.

Most programs place images at the cursor, and that part needs surgery

ratatui-image, the Rust library behind many TUI image widgets, always uses placeholders, and kitty’s own image viewer, kitten icat, does when asked. Everything else on the list places images at the cursor, and so does every Sixel and iTerm2 image.

A scanner cannot place an image at the cursor, because at the moment it sees the bytes, alacritty may not have parsed the text in front of them. alacritty reads several chunks before parsing any of them, holds the grid locked while it does, and when a program asks it to hold the screen until a whole frame is ready — a synchronised update — it buffers for up to 150 ms before applying anything. measured That leaves three routes, and the third was named in TD’s own August review of its foundations:

  • Own the read loop: replace alacritty’s 486-line loop that reads the terminal and feeds the parser with TD’s own, parse up to each graphics sequence, then act with the cursor in hand. No fork; the code that keeps a re-attaching window in step with the host, and the window’s socket reader, have to be re-expressed against the new loop.
  • Fork vte and alacritty_terminal, the way Rio did. Rio is a Rust terminal on wgpu whose core descends from alacritty; it forked the parser, added APC callbacks, and supports all three protocols under the MIT licence. Two forks to rebase for ever after — though Rio’s graphics modules, now published inside its rio-vt crate, can be lifted whichever route is chosen.
  • Swap the VT layer — the library that turns program output into a grid — for one that already speaks graphics. The August review: “Swap the VT seam (rio-vt / libghostty-vt)” becomes right “when image support becomes a committed TD feature.” herdr, the agent workspace Omarchy installs, already runs Ghostty’s VT library per pane; a pull request swapping rio-vt into Zed’s terminal was closed unmerged, and its diff maps the differences.

Video has one more cost, from TD’s split into host and window. mpv at 720p sends about 3.7 MB of base64 per frame — roughly 110 MB/s at 30 frames a second — and the host drops a window that falls 512 chunks behind. inferred That wants a real mpv run through the split before anyone designs around it.

None of this is new territory. The last question is what other terminals learned building it.

Someone already ships the click, and no one surveyed ships the whole thing

The survey ran through research-delight, the research harness that declares what “done” means before it starts and refuses any value without a source. It covered 52 projects — 32 seeded, 20 found along the way — and 51 met the bar; the one that never closed is the retro artwork, which three rounds could not tie to any software. Three projects sit closest to what you described, each on a different axis.

Four of them converged on one shape, and it is worth taking whole. kitty’s open-actions, herdr’s link handlers, Wave’s wsh view and Arcan’s open each route a target by file type to a viewer, and each ended up with the same short list of placements: split, tab, float, and “in place”. For TD that is one router — something like td open <path> --float|--split — that Ctrl+click, a command line and an agent all call. It carries one flag for who asked: a person’s click may fall back to the desktop, a program’s request may not, and a program’s request never takes focus from the pane you are typing in. inferred

The two posts resolved as well. Boyd’s dashboard is npx jev-plays-pokemon, an MIT Node client from Standard Agents — the company behind dmux, the other example you named. The Game Boy screen is Kitty graphics placed at the cursor, up to 15 frames a second, each frame scaled up four times with nearest-neighbour sampling first because, in the source’s words, “Terminals scale Kitty images with smoothing, which blurs pixel art.” It turns Kitty on only when the terminal’s name says Ghostty, WezTerm or kitty, so inside TD it would draw half-blocks until it learns TD’s name and TD can place at the cursor. measured The HYPERION artwork is, as far as three rounds of search could tell, concept art with no software behind it. hunch dmux itself draws no pixels; its dialogs are separate processes in tmux popups, and its issue tracker is a record of what goes wrong when panes are coordinated from outside the program that owns them. TD owns its panes in-process, which is the advantage to keep.

The pieces exist and the shape has converged. What is left is the order.

Five things only you can settle

Everything above arranges into two tracks that share one drawing primitive and nothing else. They can run in either order, and the first rung of each is small.

1 · Reverse “never our own viewer”, and give the two clicks different jobs?

Today Ctrl+click and Shift+click do the same thing. The proposal gives Ctrl+click to TD for the types it can draw and leaves Shift+click on the desktop handler, so nothing you use now disappears. It reverses a rule written in three places, and those places should change in the same commit.

Recommendation: yes. The rule was about not second-guessing your desktop, and Shift+click keeps that path one modifier away.

2 · Floating square first, split second?

The square lives inside one pane and changes nothing about tabs or layout. The split, as a third face, spawns a shell behind the document and spends one of four pane slots. The two mockups above show both.

Recommendation: the square first; the split right after, as its “⤢ split” action, once the square has shown what reading in TD feels like.

3 · Should a document bend with the glass?

Bending costs nothing and matches everything else in the pane; clicks go through the inverse map the way the workbench’s already do. Dense text on a strongly curved tall pane may read badly, and hit-testing already drifts low at maximum warp. Flat needs the warp-exemption change the open issue asks for.

Recommendation: let it bend in the first build, look at a real brief at your usual warp, and land the exemption only if it reads badly.

4 · HTML as a rendered page now, and Servo only after the fidelity test?

A rendered page is faithful and cheap and cannot be annotated. Servo can be annotated, costs about 230 MB and a ten-minute build, and already broke one layout.

Recommendation: yes. Run the 118-report comparison on upstream Servo before a line of TD code depends on it.

5 · Start the program-pixel track now, or park it after the size answers?

What TD tells programs about its size is wrong today whatever else happens: the cell size is never answered and the pixel sizes are logical and truncated. Placeholders are three medium pieces and light up ratatui-image apps. Boyd’s dashboard, mpv and the rest place at the cursor and need the loop-or-swap decision.

Recommendation: fix the size answers with the first build; start placeholders when you want a pixel dashboard inside TD; take the loop-or-swap decision only when video, or yazi previews everywhere, becomes a goal.

Method and limits

four research agents, then checks by hand

How it was done

Four research agents read in parallel, each writing one file under docs/research/gui-in-the-tui/: TD’s internals (read-only, at origin/main), the graphics protocols from an emulator’s side (against local checkouts of Ghostty, kitty, WezTerm and Alacritty and the vte and alacritty_terminal sources TD builds), document renderers inside gpui (markdown-delight, Zed’s gpui, the Servo fork, the web), and a prior-art survey run through research-delight with servo-reader for pages a plain fetch could not read. I then checked the load-bearing claims against the code myself: the no-viewer comment, the img() call sites, the Ctrl+click path, vte’s anywhere() and the ?6c reply.

What was run, and what was not

  • Run on this machine: the Servo notes probe on a copy of a brief, headless Chromium and Servo screenshots, a CPU benchmark of the readback copy, pdftoppm on one page, mpv --vo=help and --list-options, a read-only TIOCGWINSZ on three panes.
  • Not run: TD itself with any of this in it. No image was drawn in a pane, no document square exists, no escape sequence was fed to TD. Every statement about TD’s future behaviour is inferred from its code.
  • Not established: that the host answers CSI 14 t with the size a pane was spawned at (read in the code, not reproduced); how much memory a placeholder cell costs; mpv throughput through the host and window; whether dense text reads well under the warp.

What the method misses

Reading code finds what exists and where it attaches; it cannot say how a feature feels. The estimates in figure 13 are from reading, not from building. The Servo fidelity finding rests on one brief.

Frames into gpui

gpui on Linux cannot display a texture it did not upload (surface() is macOS-only; the wgpu renderer drops surface batches). So Servo’s frames come back through the CPU. A benchmark of the copies per 1000×1400 frame — Servo’s vertical flip, the RGBA-to-BGRA swap and gpui’s atlas staging copy — measured 6.98–7.11 ms, before the GPU transfers, which were not measured. Reading back only when Servo reports a new frame costs nothing while a brief sits still. Zero-copy needs a GL-to-Vulkan hand-off and a new gpui_wgpu patch.
