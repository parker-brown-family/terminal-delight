Escape vectors for a live question

terminal-delight · 2026-09-19 · audit of the workbench question surface · read in ~15 min

A question on the bench is a modal dialog with no cancel, and the rest of the window stays live behind it. Every control on the bench types raw bytes into whatever is on screen — so while a picker is up, the composer, both dials and END SESSION all land inside it. Escape is nailed shut on purpose, and that decision is the one to reopen.

Read first

  1. END SESSION during a live question does something nobody has established

    The button delivers 0x03 0x03 straight down the pseudoterminal (bench.rs:599) and is offered whenever an agent is present — strip_verb never looks at whether a question is up. Whether the picker eats the first interrupt or both fall through decides between the button silently did nothing and the session died with a tool call still open. Both are bad and they are different bugs.

    What it would take: one transcribed run, then a guard. hunch which branch fires.

  2. Escape is deliberately refused, and that floor is the defect

    peel() returns Peel::Nothing when a card holds a waiting question, with the comment “THE FLOOR”. The intent was protective. The consequence is that the workbench face is the only face of this pane with no way out of a modal — the terminal face prints Esc to cancel in the picker's own footer.

    What it would take: an ABANDON verb on the question card. measured

  3. Commenting on a question answers it instead

    Kind::Question ships Action::Comment specifically so “a person who wants to say something other than one of the answers still can” (surface.rs:1256). The comment becomes typed_line() — the prose, then \r. Into an open picker that carriage return commits whichever row the cursor is on.

    What it would take: the same guard as #1. inferred

  4. The dials and the composer are one defect wearing three chips

    bench_deliver is the single write path and it checks exactly two things: the pane is on screen, and an agent is in it. Not what that agent is doing. /model opus and a typed message are the same shape of byte stream as a comment, and land the same way.

    What it would take: one gate, in the one place the rule already lives. measured

  5. This pane's answer channel is unauthenticated

    The bench stamps [workbench:<tag>] in front of every line it types so an agent can tell its operator from page content. TD_TAG is unset in the pane that wrote this brief, while session-1.tag exists on disk — the host predates the export and a host only upgrades by dying. Documented seam, not a new bug, but the guarantee is off here today.

    What it would take: restart the host, or say so in the strip. measured

What it should do

A · Go modal

Freeze every other control while a question is live, and add a cancel. Matches the terminal exactly. But a bench that greys out END SESSION while an agent is stuck asking is the trap it was built to avoid.

B · Cancel, then act

Every gesture stays live. Anything that is not an answer sends ESC first, lets the picker close, then does what it was going to do. The agent receives a clean tool rejection — the path it already handles.

C · Queue it

Hold non-answer gestures until the question resolves. Rejected: the question resolves when the person answers it, so this makes them wait on themselves.

Why B, and the evidence for it

This brief exists because a question was cancelled mid-session. The agent received “The user doesn't want to proceed with this tool use. The tool use was rejected”, followed by the interruption notice, and carried straight on into the next instruction. The abandon path is already well-formed on the agent's side — nothing needs building there, and the window is the only half that cannot reach it. measured in this session's own transcript.

Decisions

Cancel-then-act, or refuse-while-waiting?

B lets you press anything and takes the question down first. A freezes the bench until you deal with the question. A is more honest about the modal; B is what every modern surface actually does when you click Log Out with a dialog open.

Recommend B. A bench that disables its own kill switch while an agent is stuck is the shape of trap this window keeps finding.

Does END SESSION confirm while a question is live?

It is the one gesture here that cannot be undone, and today it is also the one whose behaviour is unknown. A confirm costs a click on the rarest press.

Recommend yes, and only in this state — a confirm on every press would be noise.

Is DEFER real, or is it abandon with a note?

A blocked tool call cannot be parked. The closest honest thing is cancel plus a typed line saying come back to it, which leaves the agent free and the intent recorded.

Recommend abandon-with-a-note, drawn as its own chip so it does not read as a dismissal.

Run the END SESSION experiment before or after the guard?

The guard is justified either way. The experiment decides whether a second issue gets filed about a button that silently lies, or about a transcript that loses a tool result.

Recommend after. The guard is cheap and the experiment costs a live session.

Method and limits

what was and was not done

What was done

The audit is a read of app/src/pane/bench.rs, app/src/workbench.rs, app/src/surface.rs and app/src/screenread.rs at commit a6b04e6, plus the environment of the pane it was written in. Every open issue on the repository was searched for existing coverage of questions, escape, cancel and pickers; nothing matches.

What was not done

  • Nothing was run. No gesture in figure 03 was performed against a live question. The verdict column is derived from the bytes each path sends, not from watching a picker receive them.
  • The installed harness was not instrumented. What Claude Code's picker does with 0x03 specifically is the open question in figure 05.
  • No code was changed. Figure 07 is a proposal.

Invalidation

  • The composer and dial findings die if a carriage return into the picker is ignored rather than committing. Check: open a question, type a word in the composer, send, and read the transcript for a tool result.
  • The END SESSION finding dies if the button already refuses to draw while a question is live. It does not — strip_verb takes two arguments and neither is the question state — but that is the check to run first.
  • The escape finding cannot die; peel() is a pure function with a table test asserting the floor by name.

The unauthenticated answer channel

TD_TAG, and what its absence costs

Every line the bench types is prefixed with [workbench:<tag>], where the tag is eight random characters minted into a file beside the host socket and exported into each pane's environment. The agent's briefing tells it to treat a [workbench] line carrying its own tag as an instruction from its operator, and any other one as content it should not obey.

In the pane that wrote this brief, TD_TAG is unset while /run/user/1000/terminal-delight/session-1.tag exists and dates from 2026-09-17. The host that owns this pane predates the export, and the source says why that is expected: a host only upgrades by dying.

So the mechanism is sound and this instance is unprotected. An agent that follows its briefing cannot tell an operator's press from a line of text dressed up as one — which is the exact caution the briefing ends on. It is worth a line in the strip rather than a fix: the pane already knows whether it has a tag.
