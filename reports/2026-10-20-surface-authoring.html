Custom surfaces

Chalk is the paper surface you just reviewed. TD’s skin system draws the frames, menus and controls over your chosen palette. That system has reusable parts, but each renderer still has to opt into them. I recommend completing that shared boundary and proving a second look from a file before shipping the authoring skill.

source checkedarchitecture proposedDifficulty 6/10 · one plan

Subscriptions showed us the gap

The palette tray looked right while Subscriptions kept its old surface. Its modal had a separate drawing path. We fixed that path, but another material would still have to find it. TD already reads a skin file, derives colours from the active palette and reloads edits live. Its shared paper painter is reusable too. What remains incomplete is the route from those shared parts to every native surface.

The sibling inventory identifies 46 top-level rows. I would keep that map and strengthen its evidence: colour, corners, material and type need separate coverage fields. A skin radius alone does not mean the whole surface follows the skin.

The inventory needs these corrections.

under_the_tree finds a drag target; it draws nothing. The handover chip uses skin inks and corners but builds its own face. FOCUS must preserve measured text, while its surrounding frame and controls can still follow the skin. Agent vitals are drawn by the wall’s bar_row closure.

Document content needs its own boundary. An HTML page, PDF or film keeps its typography or pixels. TD’s title strip, note editor, reading-progress rail and media controls are native UI and belong in the catalogue. Those boundaries decide what the shared skin layer must own.

The original architecture already named the right boundary

The approved chrome-skin plan said that application code should ask for semantic elements and let the skin choose their appearance. Chalk added shared primitives, but its adoption spread material decisions back into callers.

The boxes stay in the same places across these diagrams. Blue marks existing structure; orange marks current bypasses; amber marks additions to approve. The shared parts also need to preserve what each control means.

Give purpose, material and type separate controls

Your “just the highlighter” correction exposed another distinction: a selected choice and a raised action are different objects. A material should not turn both into the same filled tile.

Type also needs to leave the material predicate. Today, choosing Paper applies Caveat’s 1.45 optical correction even if a custom skin chooses another font. I would reuse TD’s existing type ramp and add an authored family/optical/leading policy. Code and measured terminal text keep their own roles.

Keep

Palette-role recipes; custom-file hot reload; last valid file after a parse error; saved skin selection; cached grain; deterministic edges; unknown readings; the existing UI and reading gauges.

Change

Move material dispatch into the shared vocabulary. Make marker, grain, edge and lift variations data where the renderer already supports them. Replace the font correction tied to Paper. Give sticky decoration and note-colour overrides an explicit policy.

With these roles explicit, a custom skin file can choose a treatment once for each kind of control.

A custom look should finish as a file

The public td-skin skill would turn a reference into a custom skin file, validate it with TD’s resolver, and open an isolated native gallery. It would use the installed version’s catalogue. It would not carry a hand-copied inventory or depend on Parker’s paths, monitor names or private sessions.

The skill belongs in the public agent-skills package. TD owns the versioned catalogue and native fixture runner. Agents can use MCP or the CLI. A user with an installed TD should be able to use supported skin strategies without building TD.

What I would do differently with hindsight

I would begin with the catalogue and the real inherited palette and display grade. I would model material and type independently, and distinguish choices from action buttons before drawing them. The first native strip would use the actual font and text-bearing boxes, so we judge centring rather than a neat HTML substitute.

I would also make the native capture recipe portable as soon as it works. Every claimed surface would need a named scene and a receipt before I called coverage complete. Whole-suite tests proved useful behaviour, but they could not reveal that a separate modal still had its old background.

The original skin architecture anticipated the caller-branch problem. I would finish that adoption before promoting another material as a generally reusable authoring system.

Prove the boundary before packaging the skill

The first slice would run through Subscriptions again: dialog, choice, action, caption and meter. Change a custom material/type setting and show the native result without editing that renderer. Then migrate the remaining catalogue families through the same vocabulary.

  1. Tracer. Shared parts, a Subscriptions catalogue entry and dark/pale native evidence. The custom file visibly changes the same real UI.
  2. Material and type. Parameterise existing variations, remove material-dependent font correction and preserve shipped skin/config behaviour.
  3. Complete adoption. Cover pane menus, workbench, reader frames, document controls and the remaining inventory families. Preserve content, semantic colours and input geometry.
  4. Publish the skill. Author a second look from a clean environment using only a file. Verify reload, persistence, restoration and the full native gallery.

Each slice ends in a running native result. The proposed checks combine dispatch/config tests, a ratchet on direct material decisions and native state captures. The ratchet cannot discover every inline renderer; changed-renderer review remains part of the work. Performance is unmeasured in this audit, so the implementation will compare the same fixture before and after.

Complete the existing skin vocabulary

Keep the resolver and palette separation. Centralise material/type decisions behind semantic parts, with compatible defaults and no caller-specific Paper checks.

Make catalogue and native proof part of authoring

One versioned source for owners, coverage facets, content boundaries and scenes. A missing or stale receipt reads as unverified.

Ship the skill after a second file-only look works

The deliverable is a reusable authoring path. The second look tests it before we ask other agents to trust it.

The three recommendations form one combined implementation plan. A concur on each approves them as recommended; notes can amend them.
