Jev is a plugin you install

Terminal Delight can now reach TypeSafe's System One, and its own source knows nothing about it but the plugin's name. A checkout without the server installed has no Jev surface at all — not a greyed one waiting for a key, and above all not a zero. Three tests hold that promise, and each one has been broken on purpose to check it fails.

Yours to settle

Does a dev escape hatch belong here?

Right now the only way to get the plugin is to put jev-mcp on PATH or in ~/.local/bin. The other two plugins auto-resolve from the checkout, so on your box they just work and this one will not. My recommendation: leave it. The friction is one ln -s and it buys a rule with no exceptions, which is the only kind a public repository keeps.

What happens to jev-integrations?

The plugin imports it and will not work without it. Published to PyPI, vendored into this repo the way the Omarchy collectors were, or left private and the plugin stays yours-only — those are the three, and they are genuinely different answers. My recommendation: leave it private for now and revisit when the questions stop changing weekly. Vendoring a client that is still moving means keeping two copies correct.

Should a provisional confidence floor ship?

Nothing is gated today; every answer arrives with its probability and the caller decides. A floor would need labelled cases and the skill's own sweep refuses to recommend one under ten. My recommendation: no floor until there are cases. A shipped default is a number nothing measured, and it would be inherited by every surface that ever calls this.

Is the five-state pane taxonomy the right one?

working, needs_person, stalled, done, unclear, plus not_an_agent read off the mode. It is my guess at what you actually scan the wall for. If you look for something else — “has this one gone in circles”, “are these two doing the same job” — say so, because that is a different question and it belongs in the plugin, not in whatever draws it.
