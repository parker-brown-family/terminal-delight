Ten Slices

Documents opening inside Terminal Delight’s panes now has an approved product and an approved architecture, and the next step is the one most plans skip: deciding every file, every type, every call and every test before a line of code exists. Two agents did that in parallel, one working from the click inward and one from the document outward, and they met at a small set of calls both sides agreed on. Their two design documents run to fifteen hundred lines of types, signatures and call stacks, which is the wrong thing to ask you to read. This page draws what those lines decide, and the order the work would be built in — ten slices, each one running and shown to you before the next begins — and asks you to approve both, or change them.

New modules carry the work; the session protocol is left alone

Almost all of it is new code in two places, a small file of decisions and a new document module, and the existing files change at their edges. The window process carries everything; the session host changes in one spot, the stale size answer.

Two agents writing two halves of one feature is how a feature breaks at the seam. This one has a rule that stops it.

One rule holds the two halves together

TD bends each pane’s picture with the CRT glass after everything is drawn, but gpui, the framework underneath, decides what a click hit using the flat, unbent layout. So a button drawn near a pane’s curved edge is clicked somewhere beside where it appears. The terminal grid and the workbench already live with this: the pane catches every click, un-bends the point, and hands it on. The document view must do the same, and nothing inside it may listen for the mouse on its own.

The other seam is between TD and the browser that draws a brief.

TD talks to Chromium through a pipe, not a port

The page engine needs sixteen of Chromium’s remote-control commands — open a tab, load a file, run a script, take a picture. The usual Rust libraries for that each bring an async runtime TD does not use and open a debugging port on your machine that any local program could connect to. Chromium can also be driven over a private pipe, which is what the spike measured through.

The last seam runs between TD and the brief skill, which both write the same notes.

The notes are held to the skill’s own bytes

TD’s notes layer writes the same blocks your briefs’ own script writes, and that script changed today. So the design puts a set of test briefs in the skill’s repository — thirteen cases, one per release of the notes script plus the hostile and broken shapes the spike found — with the exact bytes a save must produce. The skill’s tests and TD’s tests both run them.

That is what the design decides. The order it gets built in matters as much.

Ten slices, each one you can see working

Every slice ends with something running that you can try, and each is one pull request to main. The first does almost nothing, on purpose: it proves the whole path from a click to pixels and back, and it measures the one thing that could leak memory unseen before anything is built on top of it.

Five calls to argue with, then approve

The design carries fourteen decisions its authors were least sure of; these five matter most, each with the recommendation it was built on. The rest are in the modal below.

1 · Does a saved note ever move the page?

The page cache and the no-re-render-after-save both assume a changed notes block moves no element on the page. It should not — a noted element gains only a shadow — but nobody has measured it.

Recommendation: keep the assumption, and make slice 8 measure it across the report archive; every save also re-reads the file in the engine and says so if anything is off.

2 · The note box inside the bent glass, or as a flat window-level box?

Inside the pane keeps the note beside its passage, as the mockup drew it, but it needs a multi-line edit box TD does not have yet. Every other glowing box in TD is flat and window-level.

Recommendation: inside the pane, as drawn; the multi-line editing is slice 8’s largest piece of new code, and it can flatten if typing into bent glass feels wrong.

3 · Notes you have not saved live only in memory?

That matches the brief’s own save button and your “SAVE doc”. A crash loses unsaved notes; a draft journal would keep them and create a third place notes live.

Recommendation: explicit save, with the bar showing “N unsaved” so nothing is lost by surprise.

4 · A brief cannot reach the network from inside TD?

A brief runs its own script in TD’s engine; blocking the network means it cannot send anything anywhere. Your briefs are self-contained, so they lose nothing; a page that loads a web font renders with a fallback.

Recommendation: blocked by default, with one setting to allow it.

5 · One pull request per slice, merged to main as each goes green?

Main is merge-on-green, so each slice lands on its own and the feature grows in your terminal as the deploys at slices 2, 4, 6 and 8 go out. The alternative is one long branch merged at the end.

Recommendation: one per slice. Small diffs stay reviewable, and slice 1 already changes what Alt+click does on an image path.

6 · Approve Gate 3 and Gate 4, or what should change?

Approving starts slice 1, the tracer bullet. Nothing is built before this.

Recommendation: approve, with a note on anything above.

All fourteen least-confident calls

merged and ranked in 03-program-design.md

  1. The face in two places. A third workbench face plus a document on the pane can disagree; the API makes it unreachable, the type does not. The alternative lets the pane’s document outrank the face.
  2. Notes are data, not layout — the cache and the no-re-render-after-save rest on it. Measured in slice 8.
  3. Textures given back at close rely on gpui’s release order; up to 61 MiB per closed brief if wrong. Counted in slice 1.
  4. Owning the DevTools client: no crates, no port, sixteen commands to maintain.
  5. The note box inside the bent glass, with new multi-line editing.
  6. Explicit save; unsaved notes live in memory.
  7. The cell-size answer can overtake an earlier answer in the same read; right for the usual probe order.
  8. A document pane swallows typing rather than typing into the hidden shell.
  9. Browser storage still wins in the browser until the skill fixes issue 24.
  10. No network for a brief by default.
  11. Vendored fixtures and a weekly watch: TD can lag a format change by up to a week.
  12. One Chromium per TD process, shut down after five idle minutes (265–570 MiB while alive).
  13. Serverless panes answer 14 t but not 16 t; hosted mode is the default.
  14. Promotion moves the view from the square to the split rather than reopening the file.
