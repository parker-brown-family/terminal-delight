The plugin built to stop a confident wrong number was producing three of its own

Pull request 706 puts TypeSafe's Jev behind a plugin boundary so a public checkout of terminal-delight carries no hosted-model dependency. The boundary works. What did not work was the rule the plugin exists to enforce — that an absence is never answered as a fact — which was broken in three places, each one inside a function whose own comment forbids it. Eight findings are fixed and pushed; one is deferred with an issue. The plugin's own model was then asked to judge all nine, and it separated them the same way I did. Then I shipped a crash in the fix commit and the author caught it, which is the last section and the most useful one.

  2. workspace_weather reported judgement available on a machine with no client. Availability was resolved inside if judged:, so a pane list that happened to be all-measured never looked, and answered available: true beside a reason reading no jev client in the same object.   3. The plugin's timeout equalled the host's, so its own abstention could never arrive. TD_JEV_TIMEOUT_S defaulted to 10, and RPC_TIMEOUT in app/src/plugins.rs is 10. The client abstains at the deadline and only then writes; the host had already given up. Fixed: eight seconds, with the gap documented as the point of the number.
  4. One malformed question destroyed every answer in its batch. The encoder raises on a bad question and the call sat outside any handler, so the whole request returned a JSON-RPC error. This one caught me while I was composing the questions for this very review. Fixed: questions are validated through the port's own encoder and a bad one abstains alone.
  5. You can now see which key the window is spending, and never the key. Your ask. jev_status answers the variable name, where the value came from, and a truncated domain-separated digest — safe on a screen, in a screenshot, and on a stream. The carve-out is the honest part. Knowing which key, without the key

You asked for the plugins card to be aware of the key people are using without it ever being on screen. The awareness belongs in the plugin, because the plugin is the only thing that ever holds the value — terminal-delight's own source still contains no key, no endpoint and no model id, and a test walks every .rs file to keep it that way.

What the fingerprint is not. Thirty-two bits collide, so it is a label and never a credential: it must not be accepted as proof of possession anywhere. Recovering the key from it means guessing the key, which is the only security claim being made and the only one needed. The domain prefix matters more than it looks — without it the digest would be the plain SHA-256 of the secret, which is a value some other system might publish for the same secret, and a number that is safe alone stops being safe when it can be lined up against somebody else's.

Then I shipped the same bug I had just written up twice

7a6ee60 — the commit carrying all eight fixes — raised NameError: name 'before' is not defined out of every verb in the plugin, on any machine where the client imports and a key is set. The pull request's author hit it within minutes of rebasing onto my work, reproduced it, traced it to my commit with git log -S, and did not touch it because it was mine to fix. measured

The cause is dull: a restructure deleted the set the line compared against and left the line. What is worth your time is why nothing caught it.

The repair is the guard, not the line. Reaching that branch never needed a real client — only something importable. fake_jev_home writes a jev package of two empty classes into a temp directory, and live_jev_mcp_tracks_where_the_key_came_from spawns against it twice: once with the key in the environment, once with a stand-in dotenv.load that sets the key only after the import, so both origins are asserted and told apart. No checkout, no network, runs everywhere. Put the deleted line back and it fails with the exact NameError — while all six sibling live tests stay green, which is the measurement that matters: they were not weak guards, they were guards pointed somewhere else.

This is the third variant of the same fault in one evening, and the first two are findings in this document. A fourth arrived within the hour, below. The timeout made an abstention unreachable; one malformed question made twenty-seven answers unreachable; and now a guard made its own subject unreachable. Between us we produced three different ways for a thing to be green and not run — the author's probe rig supplied a variable that hid a mismatch, my rig skipped the branch entirely. A reviewer who has just written that up twice is evidently not immune to it.

What is actually yours to decide

Does the fingerprint go on the card, and is eight characters the right length?

I built the plugin half and drew the surface as a proposal, but I did not touch main.rs — the rail agent owns that surface and is mid-change in it. Eight hex characters is a judgement, not a measurement: long enough to compare by eye, short enough that nobody mistakes it for a credential. My recommendation: ship it at eight, on the card, next to the version.

Is inverting the mode list the right call, or should an unknown pane simply not appear?

I chose to ask the model about a pane nobody could describe, with unclear as its escape. The alternative is a row that says unknown outright and costs nothing. Asking spends a fraction of a cent and sometimes gets a real answer from the title and last line alone. My recommendation: keep asking — the pane that cannot be described is exactly the one most likely to be stuck. The author agrees, independently.

Should the timeout be eight seconds, or should the host's deadline grow?

I made the plugin finish first because that is the side I could change without touching the host's contract with three other plugins. If Jev is routinely slower than eight seconds under load, the right answer is a longer host deadline instead, and that is a measurement nobody has taken. My recommendation: eight now, and sweep the real latency distribution before touching RPC_TIMEOUT. Tonight's one reading was 236 ms for 27 questions. hunch that the tail is nowhere near eight seconds.
