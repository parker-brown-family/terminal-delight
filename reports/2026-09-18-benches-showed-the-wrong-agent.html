The benches were showing the wrong agent

Why a workbench in one pane displayed another pane's deliverable — 2026-09-18, terminal-delight

You saw a pane whose bench carried File drop — difficulty brief and The drop — as built, neither of which that agent had made. Both belonged to the pane two tabs over. The guess in your message — probably others? — was right: at the moment you asked, seven agent panes in this repository were reading one single conversation, and it was not theirs.

What a bench reads, and where it goes wrong

Half of what lands on a bench needs nothing from the agent: Terminal Delight reads the agent's own transcript and derives the surfaces itself — the questions it is waiting on, and the Deliverable: line in its last reply. To do that it has to answer one question first: which conversation is this pane in?

The resolver had four rungs and was falling off the bottom

agent_resume tries, in order: a ledger entry pushed by the agent, the transcript the process holds open, a --resume id on its command line, a transcript born within 120 seconds of the process starting, the newest line in history.jsonl, and finally the newest file in the directory. Every rung above the last was returning nothing.

The fix was already in the repository, switched off

Rung one — scripts/td-agent-ledger, a SessionStart hook that writes each agent's current session id to ~/.local/state/terminal-delight/agent-ledger/<pid>.json — is the exact, rotation-proof answer, and it beats every forensic rung. It has code, tests and an installer. It had never been run on this machine: no hook in settings.json, no binary in ~/.local/bin, no state directory. The capability was advertised in the resolver's own comments and carried nothing.

Installing it fixes every session started from now on. It does nothing for the forty already running, so those were bound by hand: each live agent's own session id read out of the file descriptor it holds on /tmp/claude-<uid>/<project>/<session-id>/, and where no such descriptor existed, by matching process start times to transcript birth times one-to-one.

The one decision left

Rung six is still there, and it is the rule that turned a missing answer into a confident wrong one. Unknown is not zero: when Terminal Delight cannot tell which conversation a pane holds, the honest answer is to derive nothing, not to hand it whichever one moved last.

  • Refuse the shared fallback. Newest-by-mtime only when this is the only live agent in that directory. Several agents, no exact binding → no derived surfaces, and the bench says so.
  • Replace the 120-second window with greedy one-to-one matching: each transcript goes to the latest-started process that predates its birth, and no transcript is ever handed to two panes. Run by hand tonight on eight panes, all eight correct, one confirmed against the pane's own screen.
  • Read the scratchpad descriptor as a new exact rung — it bound 13 of the 40 live agents outright, including both panes in your screenshots.

Difficulty 5 / 10 — one resolver, forty lines, but pane identity feeds the bench, the MCP census and the desktop recaps, and a wrong answer there is invisible until somebody notices a strange card. Invalidation: if a fresh window comes up with every pane already bound by rung one, the code change is optional hardening rather than a fix, and should be judged on that lower bar.

What this also explains

The duplicate session ids in list_panes — two panes reporting the same --resume line — were never a display bug. They were this. The same resolver feeds pane_events, which is why tailing one pane's tool calls could return another agent's work, and it feeds the notification recaps.

Nothing on this page is drawn from memory: every number came from /proc, the transcripts on disk, or terminal-delight probe run against the live panes.
