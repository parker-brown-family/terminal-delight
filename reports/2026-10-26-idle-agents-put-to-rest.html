Idle agents, put to rest

Six of your Claude agents had not been touched for four to seven days and still held 1.6 GB between them. Terminal Delight can hand that memory back without losing any of them. Rest freezes an agent and pushes its memory out; nothing is lost and it wakes in a fifth of a second. Sleep ends the process, keeps the conversation, and brings it back in about a second and a half. Seven decisions at the end are yours.

measured on this machine, 2026-10-26 difficulty 8/10 · four gates one probe reached a live conversation — below

Where it stands

An idle agent is a family of processes. On this machine the families of 27 agents hold about 8.5 GB of real memory, and the largest single block belongs to no pane: the helper servers Codex's shared service starts for each Codex window, which were still running three minutes after a test window closed. For Claude agents, Terminal Delight can do two things it cannot do today — rest an idle agent and sleep one — and both were tried end to end on a disposable copy of a 20 MB conversation. I recommend building both, rest first, with Codex's helpers handled outside Terminal Delight by the Codex sibling.

One probe reached a live conversation

My second probe needed the file of its own copy and fell back to the newest conversation in the folder. That was pane 111's live session, which you had opened ten minutes earlier. For two minutes a second process held pane 111's conversation, then the probe stopped it. It sent nothing and made no model calls; it left two zero-cost bookkeeping lines in pane 111's transcript, and pane 111's own process was never touched. I left the lines alone because pane 111 was writing the file.

07 Codex is a different problem

Codex's shared service keeps a closed window's helpers measured to 3 minutes

A Codex pane runs a 15–41 MB window; the window asks Codex's shared service to start its helpers (garrison, gmail, lean-ctx, a browser runner, a REPL). One bare test window made the service start twelve of them, and all twelve were alive three minutes after the window closed, past the one minute in Codex's configuration schema (its documentation says thirty minutes for an inactive thread, which was not tested). Nineteen sets are alive now, holding about 2.9 GB of real memory. How many of them outlive their window is not established: one window can start two sets, and up to eleven open Codex windows could own them. Nothing Terminal Delight does to a pane reaches them.

Would prove it wrong: close a Codex window and watch its helpers (filtered by working directory, since other windows start sets in the same seconds) for forty-five minutes; if they end, this is a slow unload rather than a leak, and the Codex half shrinks to a setting. The reproduction and the questions for the Codex half are in docs/plans/idle-agents/evidence/codex-daemon-keeps-every-windows-helpers.md, and the Codex sibling in your tab has a note pointing at it.

08 What others already do

09Yours

1 · Build rest and sleep, rest first?

Rest loses nothing and wakes in 0.2 s, and it is safe in the two cases Terminal Delight cannot see today (session grants, messages from other agents). Sleep saves everything while asleep, and costs the things listed under "What sleep cannot bring back".

Recommendation: both, rest first. Sleep follows once rest's refusals have run on your panes for a while and the refusal counts look right.

2 · Rest after ten minutes untouched and quiet?

Quiet means no output, nothing else running in the pane, and the agent reporting it is waiting. Waking costs 0.2 s, so a short threshold is cheap.

Recommendation: ten minutes, adjustable in the settings panel.

3 · When does an agent sleep?

By hand ("sleep now"), after a fixed time untouched, or only when memory runs short. You leave agents for up to a week; this machine is short on memory most of the time.

Recommendation: by hand from the first build, and on its own after a day untouched, when none of the reasons to refuse applies, with a keep-awake switch per pane.

4 · What wakes a sleeping pane?

Waking one costs about 1.4 s and brings back its full 300–450 MB.

Recommendation: a key or a click on its card, not focus, so tabbing past a sleeper leaves it asleep. A resting pane wakes on focus, because that costs a fifth of a second.

5 · Codex's helpers: outside Terminal Delight?

They live in Codex's shared service and hold about 2.9 GB; a closed test window's helpers were still running three minutes later.

Recommendation: a separate piece of work owned by the Codex sibling (configuration, a restart policy, or an upstream report). Terminal Delight only shows them as "not counted".

6 · Which release?

The 0.5.0 plan says it adds no process termination or resume. Sleep is both; rest is neither, but it is new authority over agent processes.

Recommendation: its own branch, landing after 0.5.0 is cut on 16 November, unless you make an exception.

7 · Ship the per-pane memory figure first?

It is the instrument the success metric is read from, it needs the per-pane memory group that rest also needs, and it is useful even if nothing else ships.

Recommendation: yes, as the first slice, with "not counted" and "unmeasured" drawn where they apply.

Every number, and how it was taken

2026-10-26, 15:20–16:00, this machine (31 GB RAM, kernel 7.2.5, Claude Code 2.1.296, Codex 0.162/0.164)

Memory per process

PSS and SwapPss from /proc/<pid>/smaps_rollup, summed over each agent's process tree (the agent and every descendant). PSS splits shared pages fairly, so the sums do not double-count the binary. "Real memory" adds SwapPss ÷ 2.6, from zramctl: 29.7 GB of data held in 11.3 GB. This overstates the oldest pages, because 6.8 GB had already spilled to /swap/swapfile, which costs no RAM. estimate

Idle age

Last write to each agent's conversation file, found through Terminal Delight's agent ledger or the --resume id on its command line. Five agents last wrote 159.5 hours earlier, one 96.5 hours earlier; together their trees held 1,578 MB. measured

Idle wakeups

Ten idle Claude agents and three idle Codex windows, /proc/<pid>/stat deltas over 90 s: Claude 0.49–1.08 s CPU, 3–1,286 minor and 0–92 major faults; Codex 0.00–0.01 s. A second, independent measurement over 60 s found 0.6–2.7% of a core and 1,200–2,000 major faults a minute, with the allocator's scavenger thread waking 1,072 times in 30 s. measured

Rest and sleep

A --fork-session copy of a 20 MB conversation in a detached tmux, with TD_PANE_ID, TD_SESSION and TD_TAG removed. tmux placed it in its own systemd scope, so its memory group's memory.current, memory.swap.current and cpu.stat were read directly. Freeze through cgroup.freeze; push out through memory.reclaim (it answers "try again" when it cannot reach the amount asked, as expected); wake timed from the thaw write to the typed character appearing at the end of the prompt line in tmux capture-pane, polled every 5 ms. Two runs each. measured

Resume cost

1,398 ms from launching the copy to its prompt being drawn. A resumed session settles at 435 MB in RAM (this copy); an outside measurement on the same Claude Code version found a fresh session at 212 MB and a resumed one at 422 MB. measured

Moving a running process into its own group

A sleep process was moved into a new transient scope over D-Bus (StartTransientUnit with PIDs), frozen and thawed, with no privilege; the scope cleaned itself up when the process ended. Only the processes named move: children already running stay where they were, and one started during the move can escape, so an existing pane's whole tree has to be named and checked afterwards, while a new pane gets its group before its shell starts. This is what would let your existing panes be brought under per-pane groups without a restart. It is a Gate 2 matter, recorded here because it was tested. measured

The probes, and what each one touched

scripts and logs in the session scratchpad; nothing here ran inside a Terminal Delight pane

What went wrong, in order

  • Probe 1 looked for its copy in the memory group it had created and could not find it, because tmux had moved the copy into a group of its own. It measured nothing and was stopped. This is how tmux's per-pane groups were found.
  • Probe 2 measured idle, freeze, push-out and stop correctly, then needed its copy's conversation file. Claude Code does not keep that file open, so it fell back to the newest file in ~/.claude/projects/-home-parker/. That was pane 111's live session, opened by you at 15:37. The probe resumed it in a second process at 15:41:46 and stopped it with SIGTERM at 15:43:47. The second process wrote two cost-state lines into pane 111's transcript ($0, no model calls, 121 s), and Terminal Delight's agent ledger and the session recovery log each gained a line for the dead process. No messages were sent and pane 111's own process was not touched. The lines were left in place because pane 111 was writing the file.
  • Probe 3 had the same empty-name problem in its process lookup: with no name, a pattern match would have picked up every Claude on the machine and its last step stops the process it found. It was stopped by hand on the session picker, before the lookup. All fourteen agents were checked alive afterwards.
  • Probe 3's wake time of 28 s was the screen matcher missing the non-breaking space after ❯; the never-frozen control in probe 4 exposed it.

What changed because of it

Probe 4 took its process from its own tmux pane and refused to run if that process was not the copy it started. The lesson is saved for future sessions: a probe picks its process by its own handle, never by a pattern or "newest file". The same rule goes into this design: Terminal Delight acts only on processes inside the pane's own group, and a pane whose conversation it cannot name with certainty is never put to sleep.

Codex

Two bare Codex windows were opened in /tmp and closed; the eighteen helpers they left in Codex's service were ended by process id after checking each one's working directory and parent. A third set started in cinema-delight during the test belongs to another agent and was left alone.

What Terminal Delight has today

origin/main and dev/0.5.0, read 2026-10-26

  • The session host starts every pane; the agent runs as a job of the pane's shell. No memory groups, memory accounting, freezing or idle state exist anywhere in the app.
  • Idle and working are read from the screen in the window, and from Claude's hooks where they are installed. The host knows only whether a pane is an agent and whether it has ended. Codex has no hook adapter.
  • Each pane's resume line is recorded and replayed on restore. For Codex it falls back to codex resume --last, which picks whichever thread in that folder was touched last, so with several Codex panes in one folder it can bring back the wrong one.
  • The pane-to-conversation binding labels each pane Declared, Birth, Sole or Guess. Sleep would act only on the first three.
  • When an agent exits to its shell, the pane stays as a shell and the bench offers LAUNCH. There is no resume-in-place verb today.
  • The host already ends every agent after 12 hours with no window attached, and they resume on the next launch.
  • Open issue: the session host shares the window's systemd scope, so stopping that scope takes the session with it. Per-pane groups are the same family of fix.
