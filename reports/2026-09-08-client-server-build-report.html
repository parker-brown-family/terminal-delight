The two design errors

found by building the seam, not by reading it

The hangup that could never be noticed

The approved design said a client learns its host has gone from a zero-length read, and that the reader would then poke a descriptor registered under the child key to turn that into the event upstream understands. The first implementation did exactly that, and the test hung for its full five seconds.

The reason is in alacritty's loop: a descriptor that has hung up arrives with the interrupt flag set, and the loop skips it deliberately — "don't try to do I/O on a dead PTY" (event_loop.rs:275). So the zero-length read never happens. A closed socket stays readable forever and the reader thread spins on an end it is not allowed to look at.

The fix registers the same stream a second time under the child key and establishes the hangup by peeking — asking whether the far end has closed without consuming a byte the terminal still needs to draw. Four lines of syscall, and the test now finishes in hundredths of a second. Worth noting the shape of this: it was found by a test hanging, and no amount of re-reading the design would have produced it.

Constants the compiler cannot check

The event loop dispatches poller events by matching integer keys that alacritty keeps crate-private, and exports neither them nor a helper that sets them. An out-of-crate pseudoterminal has to agree by value, so our file hardcodes 0 and 1 with the upstream file and line beside them.

Get it wrong and nothing errors: output arrives on the child arm, or a hangup on the read arm, and a pane simply stops printing. Filed as #325 with the reproduction (change the constant, watch the test hang) and its invalidation criteria — chiefly, if a later alacritty exports them, our copies get deleted and the issue closes.

What both have in common

Neither was a mistake in reasoning; both were places where the design described upstream behaviour it had read rather than run. That is the argument for building the risky seam early rather than at the end, which is what the slice order already said.

The build loop

The worktree's 19 GB build cache was reflink-cloned from the live tree in 4.7 seconds at zero disk cost — btrfs copy-on-write — so every dependency stayed warm and no lock is shared with the other agent. Incremental builds run about twenty seconds; the whole suite runs in well under a second.

The verification standard used

  • Baseline first. 570 tests green before anything changed, so any later failure has a known origin.
  • Every new test proven able to fail. The dispatch tests were run against the parent commit and two failed, printing the open window panic that proves the bug was real. The encoder tests were run against seven deliberately broken encoders.
  • Real processes where the claim is about processes. The dispatch integration tests spawn the actual binary with a sacrificial HOME and strip the display variables, so a regression cannot paint a window on your desktop — and if it tried, the test would time out and kill it.
  • No sleeps. The socket tests poll for a condition with a deadline rather than sleeping a fixed time, because a fixed sleep is how a suite becomes flaky.
