Bench tenancy

A workbench is currently a property of the square it is drawn in. End the agent and its diagrams, replies and answered questions stay on the glass for whoever comes next; resume that conversation tomorrow in a different pane and none of it follows. This is what it would take to make a bench belong to the conversation instead, what already exists for it, and the four things it would get wrong if built from the obvious design.

02 · Where a surface lives

Three writers put a work object on a bench and they all end at the same place on disk. An agent calls present_surface over MCP, or writes a .json file into the directory its own environment names, or prints a fenced block the window reads off the transcript. A sweep every second walks surfaces/<td-session>/, maps each subdirectory name to a pane id, and hands what it found to the pane with that number.

The derived half already works differently, and the difference is recent. On 2026-09-18 fourteen agents were working in one repository, eight of them could not be bound to a conversation, and eight benches showed a neighbour's deliverables as their own. The repair was a resolver that answers with evidence attached and declines to answer at all when the evidence is weak.

03 · Where the change lands

The inbox stays exactly where it is. Every agent on this machine, the terminal-delight surface command, the launch briefing and the published house file all name $TD_SESSION/$TD_PANE_ID, and the variables are stamped into the pane's environment at spawn — before any agent exists to be named. What changes is what happens to a file after the window picks it up: instead of being remembered as something that landed in pane seven, it is filed under the conversation the pane was bound to at that moment.

05 · What decides the key

The obvious key is the agent's session id, and it is close to right. paneident already produces one per pane, with the evidence that produced it, and the rungs are ordered so a reader can refuse the weakest.

What could break that key is underneath it. The ledger hook's own comment says Claude Code mints a new id on /clear, on an in-pane /resume and on compaction, and the hook overwrites its entry every time one fires. So the last write time against the process start time says how often something happened mid-life to a person who never left the pane — and the transcript named by the id says whether that something replaced it.

The instrument was where the field was being thrown away. The hook read session_id out of the SessionStart payload and wrote it; the payload also carries a source, and recording that alongside the id it displaced turns a sequence of overwrites into a chain. A compaction and an in-pane resume continue the conversation the bench is showing, a /clear and a fresh launch begin a new one, and a mint whose source cannot be read continues the chain and says in join that nothing evidenced it — because a bench that keeps too much can be cleared by hand and one that empties itself during a compaction cannot be got back.

Built, 08:30

scripts/td-agent-ledger now records source, a root naming the conversation, a seq saying how deep the chain runs, the prev id each mint displaced, and a join of declared or unknown. Beside it sits an append-only lineage.jsonl that outlives the process, because the per-pid entry is deleted at SessionEnd and recognising that conversation tomorrow is the whole point. Eighteen tests in scripts/td-agent-ledger.test.mjs, and the script was mutated three ways to check they bite: a false declared join, a /clear that fails to break the chain, and an unvalidated source word reaching a reader. Each mutation failed the suite; the unmutated script passes it.

The question this still cannot answer

Whether a /clear mints a new id is unmeasured, not inferred. Across the 600 most recently written transcripts on this machine there is not one genuine /clear invocation — the feature is unexercised here, so nothing in the corpus can settle it. The hook now records the answer the first time anyone types it, anywhere on this box. unknown

09 · Yours to decide

1 · Does a /clear wipe the bench?

It mints a new session id, so under a literal reading it is a new conversation and the bench goes. A compaction mints one too, and wiping there would throw away work mid-turn. The two are only separable if the ledger records why the mint happened.

Recommendation: yes on clear and startup, no on compact and resume — and where the source cannot be read, continue the chain. A bench that keeps too much is recoverable; one that empties during a compaction is not.

Answered 07:46 — yes, and with a question back: “is this going to be under the same agent id — ie does /clear change the agent ID? If it is the same agent ID — I imagine enumerating into a different file — {agent-id}-n.wb… if you have a pattern SIMILAR AND BETTER - 100% go with yours!” The enumerator is the right shape for the case it was drawn for, and that case has not been observed: no /clear exists in 600 transcripts here, so whether the id is reused is unmeasured. One directory per id until the hook catches a real /clear; the seq it now records is that enumerator, sitting in the chain rather than in the filename, so a segment can join its conversation without the name having to be parsed.

2 · What happens to every surface already on disk?

None of them has a conversation recorded against it, and there is no way to work out retroactively which agent wrote which file. Showing them as the current agent's is the defect this feature removes; hiding them silently loses work that is sitting right there.

Recommendation: move them into the quarantine, unchanged, and put one line on the empty bench that opens them.

Answered 07:46 — no migration at all. “Treat them all as essentially old data that will never be migrated… WE DO NOT WANT GARBAGE CODE THAT IS TAKING OUT OF DATE AGENTS / PANES AND THEN MAINTAINING THAT CODE… so all old (pre-whatever is current!) panes and agents will simply take this as an unknown and give a BIG MESSAGE: ‘this session is from a stale version of TERMINAL DELIGHT, suggest starting a new session.’” That deletes the migration slice and replaces it with a screen.

3 · Does a live agent that cannot be bound show nothing?

Every other reader in the app already refuses at that point. Extending the refusal to the bench means an agent presenting into a screen that stays empty, which reads as the feature being broken unless the screen says otherwise.

Recommendation: show nothing, and draw the right-hand screen in picture five so the refusal is legible. On this machine today the case does not arise — every live agent binds on the top rung — so this is a screen for a machine without the ledger hook.

Answered 07:46 — “Great - concur.”

4 · What happens to a shell pane that a script drops a surface into?

Not in the sibling's list, and the rule as stated switches it off. A pane with no agent has no conversation to file under, so the demo seeder, workbench-smoke.sh and any script using terminal-delight surface would write into a bench that now refuses to show anything.

Recommendation: a pane that has never held an agent keeps a pane-keyed bench, and the wipe applies only once a conversation has been bound to it. That keeps the script path alive and still gives you the empty bench you asked for, because the panes you mean have all held an agent.

Answered 07:46 — “Sure - concur.”

5 · Do the comments move with the conversation?

Your words name them — transcript, history, comments, everything workbench — and they are the one part that has never been written to disk at all. Including them turns one slice of re-keying into two slices, one of which is new storage with its own format.

Recommendation: yes, as slice 3, after the wipe is working. A conversation that comes back without the notes you left on it comes back diminished, and the notes are cheap to store beside the surfaces they annotate.

Answered 07:46 — “100% - yes comments stay with taht exact agent - session.”

The rotation measurement

2026-09-21, 07:15 and again at 08:20, this machine

What was counted

Every process on this box whose /proc/<pid>/comm is exactly claude: twenty-five. One is --chrome-native-host and holds no conversation, leaving twenty-four.

Sixteen of the twenty-four have an entry in ~/.local/state/terminal-delight/agent-ledger/, and every one of those sixteen processes is alive. The other eight carry --resume <uuid> on their own command line, which is the third clause of the same Declared rung — so all twenty-four resolve without a guess.

The late mints

The hook rewrites <pid>.json on every SessionStart, so its ts is the last mint for that process. Against each process's start time from ps -o lstart=:

  • Twelve: 1–3 seconds. Written at launch and never again.
  • One: 35 911 s — 10.0 hours.
  • One: 121 040 s — 33.6 hours.
  • One: 123 122 s — 34.2 hours.
  • One: 171 674 s — 47.7 hours.

What the second pass changed

The first reading of those four was that the session id had been replaced, and it was wrong. Taking each one's current ledger id, finding the transcript it names in that process's own project directory, and asking the filesystem for the file's birth time gives, for all four, a file born between 2 and 176 seconds after the process started — while the process has been alive for another 67 hours since. An id that had been minted at the 10-hour mark would name a file born at the 10-hour mark. Nothing was replaced; the same id was written again. measured

Pid reuse would produce the same time gap in the other direction — the process would have started after the ledger wrote. All four started well before, so reuse is ruled out.

What it still does not say

Which of /clear, in-pane /resume or compaction fired each late mint. The payload carries that in source and the hook was discarding it; it records it now.

Whether a /clear mints a new id. Scanning the 600 most recently written transcripts for a user message that is exactly /clear, or carries a <command-name>/clear</command-name>, finds none at all — so the behaviour cannot be observed on this machine's history. unknown

Whether compaction writes a new transcript file. Forty-two transcripts in this repository's project directory each carry exactly one session id equal to their filename, and none contains an isCompactSummary marker, so this corpus cannot answer it either way. unknown
