One pane, one conversation

What the fix decides, and what its tests actually prove — terminal-delight, pull request 576, green on every check

Your bench was showing another agent's work because five separate parts of Terminal Delight each asked which conversation is this pane in? on their own, one pane at a time, and all five ended on the same last resort: the newest file in that project folder. With fourteen agents in one repository that is one answer shared by everybody.

There is now one place that answers, it answers for the whole window at once, and — the part that matters — it is allowed to say it does not know. A pane it cannot place shows nothing instead of its neighbour's deliverable.

The four rungs, and who is allowed to stand on them

What the machine says now

Three things the live run found that reasoning had not

Codex could still hand one transcript to two panes. Codex conversations are found by reading the top of each file for a folder name — as a substring — so a pane sitting in /home/parker and a pane in /home/parker/PROJECT both matched the same newest file while each one looked alone. The same bug, in the half nobody was looking at. Two panes pointing at one transcript are now both demoted to a guess unless one of them named it.

A pane can have two agents under one shell — and the wrong one was winning. One of yours does. Looking properly at it: the older agent is suspended (you pressed ctrl+Z), the newer one is the one your keystrokes reach, and the lookup that turns a pane into an agent was walking the shell's children and taking the first it found — which is always the one you left behind.

It passed for a reason that had nothing to do with what it claimed to check — which is exactly the shape of a test that will wave a future regression through. And one the mutation exercise could not have caught

The first CI run went red on a test that passes on this machine and cannot pass on a busy one. The end-to-end feed test drives a made-up pane with process id 4242, and after this change that pane's binding turns on whether the process can be read — an unreadable agent is the single case where the resolver falls back to the pane's own resume line. Here 4242 was free, so the pane bound and the test passed. On the runner a real process was sitting on it, the fallback was correctly refused, nothing was pushed, and the test failed.

The assertion was true about the feed and false about the world it assumed. It now uses a number above the kernel's process-id ceiling, which nothing can ever hold, with the reason written beside it. Worth saying plainly: the only reason this surfaced as a failure rather than a twenty-minute stall is that the same test had been given a deadline earlier in the branch — before that, it waited on a channel forever and took the whole suite with it.

Is reusing a terminal poor hygiene?

No — and after this it is not even a risk. Shutting an agent down and starting a fresh one in the same terminal is the normal way to use it, and the machinery is built for it: the pane keeps its identity, the new agent writes its own ledger entry at startup, the old entry is removed when that session ends or swept when its process is gone. Nothing carries over.

The one habit worth keeping is about overlap rather than reuse: an agent you suspend with ctrl+Z is still alive, still holds its conversation, and until this change was the one your pane was being read from. If you are finished with an agent, exit it. If you suspend one on purpose to come back to it, that is fine now — the pane follows the keyboard.

What is yours to decide

  • The wall now clears a card it cannot attribute rather than drawing probable bars. That is a visible change and the one its own code comment asks for — a wrong fatigue bar is a shutdown decision taken on another agent's evidence. If you would rather see a probable bar than an empty card, say so and it is one line.
  • Codex has no real fleet pass. It gets the honest half: alone in a folder is certain, sharing one is not. A full pass means reading rollout headers properly and is its own piece of work.
  • Nothing here reaches your running window until you relaunch. The live repair from earlier tonight — the hook, plus the forty-odd bindings written by hand — is what is holding your panes apart right now.
