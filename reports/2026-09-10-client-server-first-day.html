The split shipped — and its first real day

terminal-delight · client-server split · 2026-09-10 · ship + migration + first-day bugs

The client-server split is merged, installed, and proven live. This very session migrated itself onto it — a terminal host now owns the PTYs and the window is a mortal viewer. That part is real: PR #328 merged to main, the new build installed, and the migration reconstructed all 13 panes of the live session, hosted.

Then twenty minutes of real desktop use found three hosted-mode bugs the gates never tested. None of them lose work — content and input survive every time. They are rough, not dangerous: agents can't introspect the terminal, quiet panes re-paint themselves and wipe their theme, and fresh test agents don't cleanly survive a close.

Recommendation: flip the opt-out we already built (TD_NO_SESSIOND=1 — serverless on the same binary, not a rollback) for a stable night, harden hosted mode against these three, and re-enable when solid. The split stays on main either way.

ELI5

We gave every terminal a quiet caretaker process so the work survives when its window dies. It works — this conversation literally moved onto the caretaker while running.

But the caretaker has three manners problems the test bench didn't catch, because the bench scripted one clean kill and never sat with a real desktop. The agents can't see the terminal anymore; panes re-draw themselves on a loop and snap the theme back; and freshly-opened test agents don't survive a close the way the migrated ones did.

Nothing is lost in any of it — it's cosmetic-to-annoying, not data-destroying. Turn the caretaker off with one switch for a calm night, fix the three manners, turn it back on.

The three first-day bugs

root-caused #355 · Agents lost the terminal-delight MCP

Every agent that used mcp__terminal-delight__* (Codex, and this session's own tools) lost them. The agents run fine; they just can't introspect TD.

root cause The MCP relay finds its window by walking up the process tree to a ctl socket. The split made panes children of the host, not the window — so the walk hits the host (no ctl socket) and never reaches the window, which is now a sibling. The relay can't find a window, so the handshake dies. Fix: resolve the attached window via the session, not process ancestry.

root-caused #356 · Panes re-paint on a loop and wipe their theme

Your "a pane keeps closing every 2 minutes" and "re-theme it and it snaps back" are the same bug — and it's a re-paint, not a close, which is why nothing is lost.

root cause The divergence guard re-snapshots a pane when the client replica's grid-hash disagrees with the host's. On quiet panes it's firing on a genuine mismatch (verified it is NOT the TD_GUARD_FORCE_MISMATCH debug flag) — the replica is really drifting from the host. Fix: find why a quiet replica drifts (and whether theme application rewrites grid cells so the hash mismatches).

ambiguous Fresh agents restarted instead of surviving

Test agents came back re-spawned, not still-running. But whether that's a bug or the kill-on-close-is-intent behaviour depends entirely on what was closed (a tab kills by design; only a whole-window death should survive).

settle it Run the visible counter (for i in $(seq 1 999); do echo $i; sleep 1; done), close the whole outer window, reopen. Counter higher → survival works. Restarted → real bug, filed then.

The honest meta

The gates were green but incomplete. The survival harness scripted one gui-kill on one scene; it never exercised a long-lived quiet pane, a client-side theme change, MCP across the split, or a fresh agent in a fresh window. Real desktop use found all four paths in twenty minutes. That's not the work failing — it's the gate not measuring what production does. Exactly why "installed, not built" was always the finish line, and why testing it live was right.
