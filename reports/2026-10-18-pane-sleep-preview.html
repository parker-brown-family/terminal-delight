Hidden panes wake less often.
CPU savings remain uncertain.

Terminal Delight keeps your agent terminals running when their panes are off screen. We reduced how often those hidden panes check their status. The behavior tests confirm fewer callbacks; the CPU measurements show a small quiet saving and no clear benefit while agents print.

Hidden panes were checking even when nothing changed.

Each pane had a timer for routine status checks and pending window-size changes. It woke every 150 ms while hidden. A second 800 ms timer also woke in panes whose programs belong to TD’s separate terminal host, even though those panes had no local process to inspect.

Visible panes retain their ordinary 150 ms clock and their 33 ms CRT clock. Keyboard focus does not decide whether a pane is visible.

We gave real events their own wakeups.

The routine timer also delivers resizes and recognizes when an agent finishes. Slowing it without preserving those deadlines could leave a new tab asleep or delay a resize. The change therefore wakes immediately on pane activation and waits only until the next real deadline.

The real-pane tests answered a hidden colour query without advancing housekeeping, detected a hidden permission prompt, preserved the latest resize during a drag, and returned to the fast visible clock. The native GUI check switched tabs, displayed fresh streamed output, and reconnected to the old host with both test terminals intact.

That removed callbacks, but the CPU saving stayed small.

We then compared normal production binaries with thirty hidden test programs, first quiet and then printing Codex-style working status twenty times per second. In the first run, window CPU was 3.7% lower while quiet and 0.4% lower while printing. The baseline already includes reel removal.

The observed median differences were 1.4 percentage points of one CPU while quiet and 0.2 while working. The identical-binary control differed by up to 3.3 and 3.2 points respectively. Whole-machine speed, battery life and input-latency changes remain unmeasured.

Reversing launch order gave 2.8% lower while quiet and 1.8% higher while working. Both complete runs are shown above; none of their twenty pairs was excluded.

We kept the bounded change after trying to break it.

A small or uncertain CPU gain calls for a limited change. Hidden status checks retain their one-second fallback; agent execution and output stay live. Before shipping, we deliberately removed each protection to see whether the tests would catch the resulting fault.

Implemented: bounded hidden sleep

Hidden housekeeping keeps a one-second fallback. Pane activation and resize changes wake it. Agent execution and the terminal byte pump continue independently.

Candidate validated; live installation is pending.

The measurements do not justify making status updates slower than this. Further CPU work needs to identify where the remaining time is spent.

Pairs, controls and limits

Each build ran in its own process with thirty hidden synthetic Codex workers and one visible quiet pane. Both windows shared one private hidden workspace, monitor and size. Both hosts used the same production baseline binary. The native compatibility check separately used the executable of the still-running older host.

All five quiet pairs precede the five working pairs: pausing a worker leaves its old status footer on screen, so alternating conditions would mislabel the quiet case. Both builds were sampled simultaneously. Five seconds of settling preceded each ten-second observation; working output rates had to match within 5%. Startup, executable identity, geometry and stream counts were checked before accepting a pair. No CPU pair was excluded.

Both normal production binaries were compiled sequentially from the same checkout path, with no test features. Before comparing them, two identical-baseline-binary pairs per condition measured control variation: the largest absolute window difference was 3.3 CPU percentage points while quiet and 3.2 while working. This small control describes the observed variation; it is not a statistical confidence interval.

Every working interval also read the parsed counter from all thirty hidden panes after sampling. Fresh writer output alone would not prove that the terminal still processes it.

The result is a controlled window-process measurement. It does not measure a whole-machine speedup or a cumulative improvement over every earlier TD fix. Earlier percentages cannot be added to these. Timer periods and test deadlines describe scheduling rules, not a measured keyboard-latency distribution.

The first full suite failed: placing the new test-module declaration at the top cut existing source guards short, producing22 failures. Moving it into the established bottom test block restored those guards. Eight other source readers now recognize the top-level test boundary rather than an indented test-only field; their assertions remain unchanged. A passing unmodified routing guard and a deliberately rejected F1 bypass verify that repair. The first F1 control was discarded because it hit the reader cutoff instead of the routing assertion; the accepted control requires the specific routing assertion. The same run hit the unchanged known intermittent host identity failure. Its isolated result and the fresh full-suite results are retained beside the original failure; the fork/exec explanation remains inferred.
