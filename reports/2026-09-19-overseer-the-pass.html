The changelog collision is a process defect, not three accidents

Every agent appends its entry to the top of ### Fixed under [Unreleased]. With a merge every five minutes, two agents appending within the same window always conflict, and the conflict is always semantically empty: both entries are correct and neither replaces the other.

It has fired three times today. #548 fix/changelog-dedup was a pull request to remove a duplicated entry; 76b44eb resolved another by hand with the message "both dial entries stand, in the order they were fixed"; pane 86 found a third and noted in its own scrollback that "if both land the duplicate is a no-op".

How this was established

Everything above came from three instruments and no guesses about state I could not read. The git facts are git worktree list, git cherry, git rev-list --count, git merge-base --is-ancestor, and git merge-tree --write-tree chained through git commit-tree to simulate a merge order without touching a working tree. The pull request facts are gh pr view --json mergeable,mergeStateStatus,statusCheckRollup,files. The pane facts are the terminal's own census, per-pane scrollback search, and per-pane transcripts, with the transcripts used only for panes whose session id is not shared with another pane.

What is not established: what panes 84, 82 and 73 are doing; whether GitHub re-queues a required check after each merge to base; and whether the two clean pull requests have been reviewed by anyone, since reviewDecision is empty on all four.
