File drop

Dragging a file out of the file manager and onto the workbench prompt scores three out of ten. Three of the four legs it needs are already built and carry tests: the compositor hands gpui a list of paths, the bench already un-bends a pointer into a named control, and the composer already types into the agent's own line. What is missing is one listener and a rule about what text a dropped file turns into.

The part worth deciding before anyone writes it is narrower than the feature sounds. gpui accepts a drag only when every URI in it is a local file, and destroys the rest before Terminal Delight is told anything happened — so an image dragged off a web page, which is the first thing anybody tries, does nothing and can only be made to work by patching the pinned renderer.

Verdict

recommended

A · A file into the prompt

3/10

One on_drop on the pane's root, the existing warp inverse to ask whether the pointer was over the composer, and the existing typing route to put the path in the line. Three files, no new state, no renderer patch, nothing the session host has to be told.

Its cost: it accepts local files and nothing else, forever, unless tier C is also built. A person who drags a picture off a web page gets silence.

bigger

B · Terminal Delight's own things

6/10

Dragging a surface card, a tab or a selected path from the scrollback into the prompt. The codebase already hand-rolls six drags of this shape, so the pattern is settled — what is not settled is what a card means as text, and that question stays wrong quietly.

Better at: the gesture people actually invent once the prompt accepts anything at all — moving something you are already looking at into the sentence.

not recommended

C · Anything a browser can drag

7/10

An image off a page, a link, selected text. Needs a second patch to the pinned Zed checkout beside the CRT one, plus a policy for downloading a remote thing to disk before a path can be typed.

Better at: the one case a person will assume already works. It fails silently when the patch falls off the next revision bump, which is the failure shape this repo has already paid for once.

Paste already loses a filename with a space

The clipboard path joins external paths with a single space and quotes nothing (app/src/pane/bench.rs:1315), so pasting two files, or one called Screenshot 2026-09-18.png, produces a line nobody downstream can split back. A drop would inherit that unless the quoting decision is made once and shared.

inferred from the source; not reproduced by pasting. Invalidation: if copying a space-containing file in Nautilus and pressing paste on a bench produces a quoted path, the clipboard entry is already quoted upstream and this is not real. Not filed as an issue — say the word and it becomes one.

Yours to decide

1 · Which drag did you have in mind?

Everything above assesses a file coming in from outside. If what you pictured was dragging one of the bench's own cards, or a tab, into the prompt, that is a different build with a different number — six rather than three, and its hard part is deciding what a card means once it is text.

Recommendation: the file, now. Tier B earns its cost only once you can name the thing you want to drag and what you expect to appear in the line.

2 · Should a shell pane take drops too?

The ask was the workbench prompt. The same listener can serve the terminal face for one extra branch, and typing a dropped path is what every other terminal on this machine does.

Recommendation: yes. It is a branch, not a feature, and leaving it out makes the behaviour depend on which face a pane happens to be showing.

3 · Quote the path, or type it bare?

Bare matches what paste does today and reads cleanly for an agent. Quoted survives a space and can be pasted into a shell. The two can disagree only if the decision is left in two places.

Recommendation: single-quote when the path holds whitespace or a shell metacharacter, bare otherwise, in one function that paste also calls.

// app/src/pane/bench.rs — beside bench_paste, which it deliberately resembles
pub(super) fn bench_drop(
    &mut self,
    paths: &gpui::ExternalPaths,
    window: &mut Window,
    cx: &mut Context<Self>,
) {
    if self.bench.face() != crate::workbench::Face::Workbench {
        return;                      // slice 4 replaces this with a terminal-face branch
    }
    let Some((hit, flat)) = self.bench_hit_at(window.mouse_position()) else {
        return;
    };
    if !matches!(hit, Hit::Composer | Hit::Arm) {
        return;                      // a drop on a card is not a drop on the line
    }
    // bench_click ARMS and returns when the line is cold, so arm first and
    // then place the caret — otherwise the first drop lands at the end.
    if self.wb_compose.is_none() {
        self.wb_compose = Some(crate::workbench::Line::new());
    }
    self.bench_click(flat, cx);
    window.focus(&self.focus_handle, cx);
    self.bench_typed(crate::workbench::dropped_text(paths.paths()), cx);
}

What it deliberately does not touch

No host protocol field, no new message, no gpui patch, no change to the zone system, and no gpui click handler on a bench element — the rule the bench keeps because the picture is bent and the layout tree is not.

How it would be proved

and what cannot be proved on this machine

The three legs that can be tested

The decision. dropped_text is a pure function in a file that already holds 98 tests, so quoting, several files, an empty list and a path with a newline in it are table rows. This is the part that can actually be wrong in a way nobody notices.

The registration. A source-grep guard in the pane's own tests, in the shape the pane already uses for its mouse buttons: the root div must register a drop listener, because a handler nothing dispatches to is the failure this repo has shipped before. Strip comments before grepping and then break the line on purpose and watch the test fail — a grep gate can otherwise be satisfied by the comment explaining the code it is checking for.

The route. The caret and the typed bytes are already covered by the paste tests that exercise bench_typed.

The leg that cannot

No ydotool, no xdotool, no dragon-drop on this box, and wtype types keys and cannot hold a drag. The app has no gpui test harness — zero uses of gpui::test or TestAppContext in app/src — so a synthetic FileDropEvent has nowhere to be injected without building one. Verification of the gesture itself is a hand dragging a file out of Nautilus onto a pane.

Invalidation, before anyone writes a line

The whole assessment rests on the compositor leg working in this window. Put a temporary print in the drop listener, drag one file from Nautilus onto a workbench pane, and look:

  • Path printed → the three-out-of-ten holds and the rest is our code.
  • Nothing printed at all → the drag never became a FileDropEvent here, the work starts at the compositor leg instead, and the number is wrong by a lot.
  • Printed but at the wrong pane or the wrong zone → the hitbox-hover question in the first figure's gutter line is real and the listener needs the position from the last drag motion rather than from the window.

Method and limits

what this assessment structurally cannot see

Method

Source reading, in two trees: this repository at the tip of chrome/phosphor-legibility, and the pinned Zed checkout at rev abbe85a that app/Cargo.toml names. Presence and absence claims come from grep over app/src; behavioural claims are inferences from reading the two dispatch paths end to end.

What it misses

Nothing was compiled and nothing was run, so every timing, every feel and the build cost of the change are unestablished. The incremental build cost of touching pane.rs in particular is not measured here, and that file is 477 KB.

X11 has the same event path — gpui handles the X drag-and-drop atoms and emits the same events — but only the Wayland side was read carefully, and this machine is a Wayland session.

The tree is shared. Another session has app/src/skin.rs modified in the working directory right now, and the branch this was read from is not main, so a line number here can move under someone else's commit.

Whether Nautilus is the app the drag will actually come from is an assumption — it is the only graphical file manager installed, but a drag can start in any application, and the only thing that matters is whether it offers a file list.

Not established

That the pane's hitbox reports as hovered on the first frame of a drag. That a drag over a pane with an open menu or the launcher behaves as described. That Nautilus sends anything at all for a trashed or remote file. Each would take one drag to settle.
