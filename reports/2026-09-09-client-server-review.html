Two Passes, One Overlap

Two adversarial reviews of this branch produced eight findings and agreed on one of them. Seven stand at the tip, two more were found here, and the biggest of the eight turns out to be pointing the wrong way — the wire both reviewers wanted locked down is the only route an upgrade has. Every open question is answered on this page rather than handed back. What is left is smaller than it looked: two lines of behaviour, two paragraphs of documentation, and three harness legs.

The comparison that settled it

herdr is the same product, shipped: a Rust binary that owns coding agents' terminals so they outlive the window. Thirty-seven thousand stars. Its socket API takes "one request per line" with no handshake and no token, its trust model is the socket file, and its README states the survival boundary in its first bullet — the layout comes back, "the original processes do not survive" a restart. Two of the three open questions dissolve against that: the stateless wire is the shipped answer, not a breach, and the two lifetimes belong on the label rather than in a design note. What herdr does not have is the undo window on a close, which as of this morning is ours.

Read this before the findings

Neither review saw the tip, and neither saw the gate it is now measured against. The first pass read 09ebe2b, the second b46fa8f four commits later, and the tip is 139e27e — eighteen and fourteen commits on. Two of those commits matter to the findings rather than being cleanup: 3963320 moved the resume line onto spawn-pane so the host types it, and 139e27e amended Gate 1 so a close defers instead of killing. The second of those reshapes the top finding of the first review. Every line reference below was re-anchored at the tip by hand.

Read first

  1. 1 Shutdown throws away the layout, and nobody had noticed. The verb a client can actually call stops the host without a final checkpoint, losing up to five minutes of work. This is also the missing half of ask the old host to checkpoint and stand down, which is why the approved upgrade path could not be built. Two lines, and it unblocks the version fix.
  2. 2 The two-writers bug is client-side and was never a protocol problem. A version refusal and an absent host come back as the same error, so the client opens a serverless window beside a live host. Tell them apart and the second writer never exists. A typed error and one branch.

  4. 4 The host will spawn terminals until the machine runs out. No cap exists anywhere in host.rs, and the window's four-pane limit does not reach the protocol. The plainest real defect on the list. A refusal at spawn_pane and a test that sends one too many.
  5. 5 Stop reviewing this branch; give the harness three more legs. Two passes overlapped on one finding in eight. Everything that actually mattered here was caught by something that could fail on its own. Three legs, each proven by breaking it first.

What happened when each invalidation criterion was run

Each finding below carries the check its author wrote to disprove it. That check was run first, at the tip. A finding that dies is a result.

REVERSED

The wire has no connection state

measuredfound by both · downgraded here

The facts below stand; the conclusion does not. Both reviews read a stateless wire as a defect. It is the design, it matches what the category leader ships, and enforcing a handshake would break the upgrade path this branch still needs to build. What survives is a documentation defect: two approved promises that no code keeps. The decision is carried below.

Invalidation run: connect and send a verb cold. handle_control_line at host.rs:1619 parses one JSON line and dispatches whatever verb it carries; Hello is an arm in that match like any other, and its handler discards the client kind outright — let _ = kind; at host.rs:1631. The finding stands.

The branch's own integration test relies on it: host_socket.rs:170 opens a fresh control connection and issues close-pane, then another and issues shutdown, neither preceded by a hello. The gap is codified rather than merely present.

The Gate 1 condition, and why it is already met. Gate 1 deferred remote attach on one named condition: "same uid, therefore authorised" must not leak out of the transport into the protocol. Keep authorisation a checkable property of a connection. The peer-uid check at peer_is_us is exactly that — a property of the connection, checked on every one, before a byte is parsed. It is not a handshake, and it does not need to be. What would violate the condition is a verb that trusts a claim in its own payload, and none does.

Two findings, one root. The second review filed the discarded client kind separately, as window-level steal not being implemented. It is the same line of code. Gate 3 says a Window hello drops the previous GUI connection and tool clients never steal; with the kind discarded there is nothing to implement that against, and pane sinks are replaced individually while both control connections stay live.

Disprove it: send {"verb":"shutdown"} as the first line to a throwaway host. If it returns an error and stays alive, this is wrong.

P1

A version bump leaves two writers on one file

contradictedfirst review only

Invalidation run: read the attach path at the tip. main.rs:19913 attaches; the Err arm at main.rs:19926–19934 catches every attach error and opens a local serverless window, comment included — "Say it plainly and open anyway." Nothing asks the old host to checkpoint, nothing marks the session unavailable. The live host keeps its pseudoterminals and its checkpoint writer while the fallback window writes the same session file directly. The finding stands, at shifted lines.

The approved path in Gate 3 is version break, then graceful shutdown, then TOML recovery. That path cannot be built while item one is open: a peer refused for version skew needs some channel on which to say checkpoint and stand down, and a strict hello gate closes it. The two findings have to be fixed in one pass or they fight.

Disprove it: run a host at protocol 1, launch a client built at protocol 2 against the same session, watch processes and session-file writes. Wrong if the old host exits after a final checkpoint before the new window writes.

P1

The final close never reaches its save

contradictedfirst review only · reshaped since

Invalidation run: both close paths still return above their save. main.rs:8284 (tab close) and main.rs:9259 (pane close) each call cx.quit() and return while permit_shrink.set(true) and self.save(cx) sit below the early return. The host keeps the pre-close layout. The finding stands.

What changed underneath it. Gate 1 was amended at the tip: a manual close now defers rather than kills — one pane held an hour, two or more held four, capped at ten, processes still running, ctrl+shift+z to reopen. The defect is now that the saved layout cannot express the difference between a live leaf and a held one, which is why a closed pane comes back as a respawn. The repair target moved; the code is still wrong.

A third site, and it is not a bug. There is a third cx.quit() at main.rs:9477 that neither review reached. It is the reap path, and it declines to persist on purpose — a shell exiting on its own marks the session degraded so the richer on-disk copy survives for resurrection. That distinction is worth keeping: the branch already retains on natural exit and deletes on manual close, so the amendment is closer to the existing grain than it first looks.

Disprove it: hosted session, one pane, close it through the UI, wait for the process to die, relaunch. Wrong if no replacement is spawned and the saved layout no longer carries the closed leaf.

P2

The host will spawn until the machine stops

contradictedsecond review only

Invalidation run: Host::spawn_pane at host.rs:542 holds the pane table from check to insert, dedupes against a running recipe, and then spawns. Nothing counts the panes it already has, and no cap constant exists anywhere in the file. Gate 3 specifies a generous host cap of 64. The finding stands.

The window's own limits are real but live elsewhere and do not reach the wire — four for a new split, eight for what a tab may hold. Neither is consulted by the host.

Disprove it: send 65 spawn-pane requests to a throwaway host. Wrong if the sixty-fifth is refused truthfully.

P2

Exited panes are never reaped

inferredfirst review only

Invalidation run: the only panes.remove in the file is inside close_pane at host.rs:863. A child exit sets ended and drops the stream; nothing takes the entry out. Restore filters ended panes and starts replacements, so every natural exit can leave a corpse until the twelve-hour idle exit. The finding stands on reading; the growth itself is not measured here.

The amendment above changes what a fix should look like. A pane held for a person and a pane whose child exited are now different things, and reaping them the same way would throw away the undo window before anyone could use it.

Disprove it: spawn and exit short-lived panes for a hundred cycles in one host; compare RSS and list-panes length. Wrong if dead entries are bounded elsewhere.

P2

The concurrency test does not force concurrency

contradictedsecond review only

Invalidation run: two_things_writing_at_once_still_leave_one_good_file at host.rs:3498 starts eight threads, and there is no Barrier anywhere in host.rs. Nothing forces two writers into the vulnerable interval together. The finding stands.

This is a gap in what the test proves, not evidence the lock is wrong. The commit that added the lock records five failures in five runs against its parent, which is real evidence for the lock. What no single green run establishes is the ordering property the test's own name claims.

Disprove it: run it repeatedly against the parent of the writer-lock commit. Wrong if every run fails there.

NEW

Shutdown does not checkpoint

measuredthis pass

In neither review, and it is the piece that makes the version-break repair possible. Request::Shutdown at host.rs:1705 replies ShuttingDown; the control loop calls stop() at host.rs:1148, which sets a flag, rings the upkeep and knocks its own socket to wake the accept loop. The loop breaks, the socket file is removed, the claim is dropped, and the process returns — with no persist_now anywhere on that path.

The twelve-hour idle exit does checkpoint before stopping, deliberately and with a comment saying why (host.rs:1137). The verb a person or a client can actually call does not. Anything asked to shut down today loses up to thirty seconds of layout while a window is attached, and up to five minutes while none is.

This is why the graceful version-break handoff cannot be built as the docs describe it: ask the old host to checkpoint and stand down has no verb that does the first half. The repair is to give stop() the same final checkpoint the idle path already has.

Disprove it: start a host, spawn a pane, send shutdown inside the checkpoint window, and read the session file. Wrong if the pane is in it.

NEW

A comment claims a safety property the function does not provide

inferredthis pass

Not in either review. The host now types a client-supplied resume line into a fresh pane (host.rs:690), and the comment above it says whether a recipe is safe to resume is settled at session::safe_resume_id. That function (session.rs:294) validates an extracted session id — alphanumerics, dashes, underscores, 128 characters — for the purpose of matching a live pane against a transcript. It never sees the recipe string that gets typed, and nothing else validates it either.

The same comment states the mitigation correctly: a same-uid client could open a byte stream and type the identical thing, so no new capability is created. What wants repairing is the sentence. It is worth a line because the commit immediately before the tip is "The dir-logo comment stops promising a safety property the code does not have" — the third instance of that pattern on this branch, and comments are what the next reader trusts.

Decisions, carried

Three questions were open. They are answered here rather than handed back, and the reasoning is on the page so any of them can be overturned by disagreeing with a sentence rather than by reopening the whole review.

The stateless wire stays. It is the upgrade path, not a breach.

Both reviews filed it as P1. The stronger evidence runs the other way. herdr — the same product category, thirty-seven thousand stars — documents its socket API as "send one request per line" with no handshake, no token, and trust resting on the socket file. This branch's own comments at host.rs:2266 and host.rs:2981 argue the same position deliberately.

And the version-break path needs the wire to stay open. A new binary meeting an old host has to be able to say shutdown to a peer it never negotiated with. Enforcing hello would close the only door the upgrade can walk through — the breach and the repair are the same mechanism.

The code was never wrong here. The protocol doc that promises hello opens a connection is wrong, and so is the Gate 3 window-steal policy that has no implementation and no user asking for it. Both get deleted. The wire is already selectively stateful exactly where it needs to be — host.rs:1702 refuses to start watching on a connection that is not watching — which is the pattern to keep.

Do: delete the hello-first line from docs/protocol/session-host-v1.md and the steal policy from Gate 3. Keep the peer-uid check as the boundary. No state machine, no carve-out list, no test rewrite.

Two lines fix the real bug, and neither is on the wire.

Strip the protocol argument away and the two-writers hazard is client-side. main.rs:19926 opens a serverless window on any attach error, so a version refusal looks exactly like an absent host. Tell those two apart and the second writer never exists.

The other line is shutdown, which does not checkpoint — see the finding below. Fix that and a new client can ask an old host to stand down without losing the layout, which is the whole of the approved graceful path.

Do: a typed error out of attach_at so version skew is distinguishable from absence; refuse to open serverless on skew and ask the old host to stand down instead; make stop() checkpoint the way idle_once already does.

No third reviewer. The next finding comes from a harness leg.

Two passes shared one finding in eight, which says review is a leaky instrument on a branch this size. Every defect on this branch that actually mattered was caught by something that could fail on its own: the mutation-tested encoder, the floor-control leg that loses twenty of twenty, the pane-exit leg built because every other leg measured survival and none measured endings.

scripts/td-survival-test.sh already exists and already has four legs. The three findings that need a session launched are three more legs, and a leg proves the thing every time it runs rather than once, in one reader's head.

Do: add close-undo, version-skew and pane-churn legs, each proven by breaking it first. One time-boxed read of the diff since b46fa8f — not the whole branch again — and after that the standing instrument is the harness.

The claim that did die

The second review recorded the branch moving under it as "three cleanup commits" that did not touch its findings. It was ten by then and fourteen now, touching host.rs, hostctl.rs, main.rs, instance.rs, session.rs and the architecture gate doc — and one of them changed the protocol. The reassurance was wrong, which is the ordinary hazard of reviewing a branch that people are still working on rather than any failure of that reviewer.

The whole of the work

Behaviour — four small changes

Give stop() a final checkpoint. Give attach_at a typed error so version skew is not an absent host, and refuse to open a serverless window on skew. Refuse the sixty-fifth pane. Bound the exited-pane table, keeping a pane held for a person distinct from one whose child ended. None of these touches the protocol.

Documentation — two deletions

The hello-first sentence in the protocol contract, and the window-steal policy in Gate 3. Both describe a design nobody built and nobody has asked for, and leaving them standing is what produced two P1 findings against working code. A promise a repository does not keep costs a reviewer a day every time it is read.

Proof — three harness legs

close-undo holds a pane, waits out its window, and requires the process alive at fifty-nine minutes and gone at sixty-one. version-skew stands an old host against a new client and requires one writer. pane-churn runs a hundred exits and requires the table bounded. Each proven by breaking it first, the way floor-control earned its place.

Not doing

No connection state machine. No carve-out verb list. No rewrite of the integration test that opens cold sockets — it was testing the wire correctly all along. No third review pass, beyond one time-boxed read of the diff since the second one.
