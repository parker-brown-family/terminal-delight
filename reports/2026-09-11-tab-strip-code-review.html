Branch Strip Review

Do not merge the current commit. The new strip loses the heading for every newly created group, labels tabs from several projects as though they belong to one project, and does not make long headings single-line. The layout idea holds; these are bounded corrections.

Request changes

Fix the branch identity and heading states, then rerun the existing checks plus three focused regressions. No architectural rewrite is needed.

Findings

inferredP1 · New groups have no visible strip title

app/src/main.rs:6080–6098 · app/src/main.rs:12336–12365

new_group_from writes name: None. group_title then adds a child only in else if let Some(n) = name. The old group chip supplied a fallback; the replacement does not. This is the default creation path, not damaged legacy state.

name: None,
...
} else if let Some(n) = name {
    chip = chip.child(n);
}

Effect: the column that should name the active branch is empty immediately after “＋ new group”. Its click and right-click handlers still exist, but only as an invisible target.

Fix: use the same fallback already used elsewhere (group {gid} or initiative {gid}), or enter rename mode as part of creation.

Invalidation: create a group without naming it and show that readable heading text appears in the fixed column. If it does, this finding is wrong.

inferredP1 · The heading and the tab family disagree

app/src/tree.rs:524–545 · app/src/main.rs:12279–12325 · app/src/main.rs:6366–6378

For an active tab with no initiative, family selects every other tab whose initiative is also None. Project is never compared. The heading takes the active tab's project name, and a new loose tab copies that project but branch_end(None) still sends it to the end of the entire tab list.

let home = places.get(active).and_then(|p| p.initiative);
places.iter().filter(|(_, place)| place.initiative == home)

// heading, separately
.and_then(|t| t.project)

// insertion, separately
None => self.tabs.len()

Effect: with loose tasks under Project A and Project B, selecting an A task draws both projects' loose tabs beneath an A heading. The new tab inherits A but is inserted after B's tabs. That breaks the one-branch label and the “beside its siblings” promise together.

Fix: define one family key and use it for filtering, the heading, and insertion: initiative when present; otherwise project when present; otherwise the unfiled bucket. If the product deliberately treats every loose task as one global family, remove the project heading and the project-sibling claim.

Invalidation: create one ungrouped task in each of two projects. If selecting the first project shows only its tasks under its heading and a new tab lands beside them, this finding is wrong.

inferredP2 · Long headings wrap before they truncate

app/src/main.rs:12279–12365 · gpui/src/style.rs:391–399,481–499 · gpui/src/styled.rs:137–141

The two new heading elements set min_w_0 and overflow_hidden, but leave GPUI's default WhiteSpace::Normal and no text-overflow rule. The framework's own truncate() helper combines overflow clipping, no-wrap, and ellipsis.

Effect: the exact stress state drawn in the chosen spec — a name wider than the sidebar — can wrap and make the mother bar taller instead of staying on one line inside the fixed rail.

Fix: apply .truncate() to both the project-name element and the group-title element. Keep the edit buffer behavior separate if inline editing needs horizontal movement.

Invalidation: render “CLIENT SERVER SPLIT HARDENING” in a 210 px title column and show a single-line clipped or ellipsized heading with unchanged bar height.

hunchP2 · Reorder feedback still mixes filtered and full index spaces

app/src/main.rs:5825–5908 · app/src/main.rs:13689–13706 · existing follow-up “Reordering a tab on a scoped strip resolves its drop slot against the unfiltered tab list”

tab_bounds contains only visible family tabs, but resolve_tab_slot returns their underlying self.tabs indices. The caret is drawn only when that slot equals a visible family index or the full tab count. In a non-contiguous family, the valid slot between two visible tabs can be a hidden index, so no caret is drawn. The group-title drag uses the same slot resolver even though every sibling group is absent from the strip.

This was already deferred for the optional scoped strip. Group filtering is now the normal state, so its invalidation test belongs in this pull request.

Fix: resolve against family-relative insertion positions, translate once at mutation time, and cover a family whose full-list indices are non-contiguous. Decide separately whether the title remains a group-reorder drag handle when its sibling targets are only in the tree.

Invalidation: with underlying order G1, H1, G2, H2, drag G2 between G1 and its next visible sibling. If a caret appears exactly at the landing position in every row and the title cannot reorder against invisible targets, this finding is wrong.
