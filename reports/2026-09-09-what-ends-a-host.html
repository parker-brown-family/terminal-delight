What ends a host

Nothing does. A session host runs until something explicitly tells it to stop — closing its last pane does not, and no test covers the case. It costs about 15 MB while holding nothing, forever. You are one slice away from making that the default for every window you open.

    Behind the flag this costs you one stray host when you experiment. Once hosted is the default, every session you ever open leaves one behind — on a machine already running a dozen worktrees and dozens of agents.

  4. 4

    The obvious answer has a trap in it

    "Exit when the last pane closes" is what the design assumed, and it can kill a host mid-restore — a window that closes panes before opening them takes its own host down with it. That was flagged as least-confident at Gate 3 and never resolved.

What is true today

measuredAn empty host is 15 MB and immortal

Started a host, gave it two panes, closed both, and looked: 17 MB resident with two panes, 15 MB with zero — and still running, with no panes, no client, and nothing that will ever end it. Only an explicit shutdown verb stops one, and nothing in the product sends that.

measuredNothing reaps them, and nothing tests the case

close_pane removes the pane from the table and returns. There is no exit-on-last-pane, no idle timer, no supervisor, and no test anywhere that asks what a host with zero panes does. The lifetime of the most important process in the design is, at present, accidental.

inferredReboot is the only garbage collector

Hosts are setsid-detached and lingering is enabled, which is deliberate — it is how they survive logout, which is one of the events the feature exists to survive. The consequence is that nothing short of a reboot or a manual kill clears an abandoned one.

Your call

1 · What should end a session host?

The four rows above. This is the decision; everything else here is detail.

Recommendation: idle timeout, generous — a host with no client attached and no pane output for something like 12 hours exits and checkpoints on the way out. It keeps the promise for every case you actually described wanting (crash, redeploy, close the lid, come back tomorrow) and forgets only sessions you have genuinely abandoned. "Nothing" is untenable as a default and "last pane" has the restore trap.

2 · Does a host dying quietly need to leave a trace?

If a host exits on idle, the session's file is still on disk and reopening it restores from that file — the same path a reboot takes today. You would not lose work; you would lose the live processes, silently, some hours after you stopped looking.

Recommendation: checkpoint before exiting, and say so in the log. Silent is fine for the common case as long as the state on disk is fresh — which is exactly the guarantee slice 4's save work is about to give you.

3 · Does this gate the flip, or ride behind it?

Slice 5 makes hosted the default. Flipping first means accumulating hosts on your daily machine while the policy is still undecided; deciding first delays the flip by a slice.

Recommendation: gate it. The flip is the moment this stops being one stray process and starts being a habit, and it is much easier to choose a lifetime now than to change one people have gotten used to.

Prior art

why "look at tmux" does not answer it

They all choose "nothing"

tmux, screen, zellij and shpool all keep a server alive until its last session is killed or the machine restarts. None of them time out. So the prior art is unanimous — and, I think, inapplicable.

Because they answer a different question

You opt in to tmux. Typing tmux is an explicit statement that this work should outlive the window, and detaching is a deliberate act, so a server that never dies matches the promise the user made to themselves. The pile is bounded by how often you choose it.

Terminal Delight is proposing the opposite default: every window is hosted, whether or not you meant it, and closing a window is the ordinary way to be done with something. Inheriting "never exits" from tools whose sessions are always deliberate imports a policy along with a mechanism, and it is the mechanism that transfers.

The one that is closest is not a terminal

VS Code's remote server exits after a configurable idle period with no clients attached, precisely because it is spawned implicitly rather than chosen. That is the same shape as this, and it lands on the third row of the table.

Stated as background, not as evidence: this is recollection of how those tools behave, not something I re-verified today.

If you pick idle

the shape, and the one hard part

What it would be

The host already runs an upkeep loop that knows whether a client is attached — that is what the detached backoff uses. Idle exit is one more thing that loop can conclude: no client attached for N, and no pane has produced output in N, so checkpoint and exit.

The hard part, stated plainly

"No output" is a poor proxy for "nothing is happening" on a machine that runs agents. An agent thinking for twenty minutes prints nothing and is very much alive; a shell sitting at a prompt prints nothing and is not. If the timeout is short, this distinction matters and the feature will occasionally kill something you cared about.

Which is the argument for making it generous rather than clever. At twelve hours the distinction stops mattering: no agent thinks for twelve hours, and no session you still want is untouched for twelve hours and unwatched. A long timeout needs no heuristic, and a heuristic is exactly what would eventually get this wrong in a way nobody could reproduce.

What it must not do

Exit while a client is attached, for any reason. A window drawing a terminal is proof the session is wanted, whatever the panes are printing.
