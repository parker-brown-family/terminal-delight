Window died, work kept flying

Parker's Terminal Delight window went away at about 18:52 with ten agents mid-task in it. The agents never noticed. Nothing was resumed and nothing was restarted — the same process ids that started at 13:38 were still running when a new window attached five minutes later, and one of them logged 33 tool events during the minutes there was no terminal on screen to show them.

Findings

The agents kept executing through the loss measured

Every agent in session 1 carries a start time between 13:38:16 and 14:29:49 and has not restarted since. Through 18:52–18:55, with the window gone, one of them ran tool calls and appended 33 entries to its transcript. Terminal output during that stretch went into a pane buffer nobody was looking at, which is exactly what a scrollback is for.

Invalidation: a restarted agent gets a new pid and appends to a transcript with a fresh session header. If any session-1 agent pid postdates 18:51, or any of these transcripts carries a second start record today, this finding is wrong.

Reattaching typed nothing into anything measured

Fifteen of the seventeen pane shells date from 13:38 and 14:0x. Two were created at 18:57:07, and both belong to layout leaves the host had no terminal for — the APPLY tab and the middle OVERVIEW pane. No --resume line was sent, no shell was replaced, and the session recovery log gained no entries at reattach.

Invalidation: ps -o lstart= on the host's children. Any pane shell stamped 18:57 that maps to a leaf which did have a live terminal would mean the attach replaced a running agent, and this finding is wrong.

The host owns the terminals; the window only watches them inferred

The pty masters live in serve --session 1. When its launcher died, systemd re-parented the host to pid 1142 and left the scope running — still billed 3h 23m of cpu and a 14.8 GB memory peak. Nothing holding the shells' controlling terminal went away, so no SIGHUP reached them. This follows from the process tree and from resolve_hosted_in, which ranks a live host with nobody watching above the newest file on disk; it was not separately tested.

The ordinary relaunch did not find the session measured

At 18:53:34 and 18:54:07 the launcher started two windows. Both created new sessions — 7 and tdclipdemo2 — while session 1's host sat unwatched with ten live agents in it. That is the whole reason this needed an agent and an environment variable rather than a double-click, and it is the one part of the night that did not work.

Invalidation: launch the installed binary with no TD_SESSION set, in a workspace with a free host running. If it adopts that host, the adoption tier is fine and the defect is really about which workspace ranks first — retitle it rather than fixing the wrong thing. The probable mechanism, untested, is that the host still believed a window was attached, so the free-host tier skipped it.

The window's death left no evidence at all not established

There is no core dump for terminal-delight today, no journal line (the window's stderr is not captured), and the scope never logged a stop because the host kept it alive. Its control socket ctl-3989717.sock is still on disk. The two-minute bracket above comes from Parker's last keystroke and his first relaunch, not from anything the program recorded.

What would establish it: one line in the session log when a window attaches and another when its connection drops. Then the bracket is a timestamp, and a killed window becomes diagnosable instead of reconstructable.

One OVERVIEW agent is alive in a different window measured

The agent behind the sticky note about the mise crash runs as pid 2132410 on pts/18, under the separate serverless window pid 496413 that has been up since 14:34 — not under the host. It was still writing at 19:01. Its pane in the restored layout is one of the two fresh shells, so that tab looks empty while the work continues somewhere else.

Do not resume that session id in the new pane. Two processes appending to one transcript fork it. Either drive it from the window that owns it, or stop that process first.

Open questions

1 · File the relaunch miss as an issue against the client-server work?

Everything except the front door behaved. A double-click at 18:53 should have landed in session 1 and did not, twice, and the fallback was an agent reading source at 19:00.

Recommendation: yes — with the invalidation criterion above written into the body, so whoever picks it up first proves the adoption tier really is what missed, and retitles it if the fault is in workspace ranking instead.

2 · Should the host log attach and detach?

The session log carries eleven copies of one startup warning from 13:38–13:43 and then nothing for five hours. A window arriving and a window's connection dropping are the two events this record most needed.

Recommendation: yes, one line each, with the window pid. It costs two log statements and it converts "sometime in this two-minute window" into a fact.

3 · Does the escape hatch deserve a front door?

TD_SESSION is documented as the reach-any-session hatch. Recovering a crashed window is a normal thing to want, and today it required knowing that hatch, which binary the host was running, and where the binary lives.

Recommendation: a named verb — terminal-delight attach [session], listing adoptable hosts when called bare. The plumbing already exists; this is a spelling. The cost is one more surface to keep working while the split is still moving.

Behind the record

Method and limits

What this was built from, and what it cannot see

What the evidence is

Four sources, all read after the fact: the live process tree (ps, /proc), the systemd user journal and scope accounting, the Claude transcripts under ~/.claude/projects, and the session state and host log under ~/.config/terminal-delight and /run/user/1000/terminal-delight.

What it structurally misses

Transcript entries prove an agent produced output at a time. They do not prove the pane rendered anything, and they cannot distinguish an agent that was blocked on a full pty buffer from one running freely — nothing here measured pty backpressure. The window's own stderr was never captured, so the strongest claim about its death is a bracket between two of Parker's actions.

What is sampled rather than exhausted

Per-minute counts were taken for the two OVERVIEW agents, not all ten. The other eight were idle panes with single-digit entry counts for the whole afternoon, so they would not change the picture, but they were not charted.

A confound worth naming

Process ids on this machine have wrapped, so a larger pid is not a later process — the host at 3989743 started at 13:38 while pid 496413 started at 14:34. Every ordering claim here uses ps -o lstart=, never pid order.

Three calls I got wrong on the way

Stated in chat before the evidence came in, corrected here

"No shells were respawned"

Two were, at 18:57:07. Both are leaves the host had no terminal for, so nothing live was replaced — but the count went 15 → 17 and the first telling said it did not move.

"Something other than the host is rewriting the session file"

The host holds the open descriptor on 1.toml and is the writer. The eleven changed underneath this host warnings are all stamped 13:38–13:43, before the second window existed at 14:34, so they describe a startup race that morning and not a live conflict. The second window still has the same layout open, which is worth watching, but the warnings are not evidence of it.

"The third OVERVIEW agent may have exited"

It is alive — pid 441735, started 14:29:49, and it wrote 128 transcript entries in the 19:00 hour. Its file had simply been quiet for twenty-five minutes when I looked, and I read quiet as dead.
